# 로컬 음성 대화 무응답 조사 — 2026-10-20

## 관찰과 범위

사용자는 이 PC의 로컬 실행 환경에서 말을 걸었지만 무중의 응답 글과 소리를 모두 확인하지 못했다고 보고했다. `mujoong-live`의 기존 로그·지표·DB를 읽기 전용으로 조사했다. 실행 설정·컨테이너·DB 내용은 변경하지 않았으며 추가 유료 공급자 호출을 실행하지 않았다. 전사 원문·음성·비밀 값은 이 보고서에 포함하지 않는다.

## 확인된 사실

- 해당 로컬 DB의 세션은 1개다. 서버 로그의 상태는 `PREPARING → DEVICE_ACK → WAITING_CHILD → ACTIVE → ABORTED(DISCONNECT)`다. `ACTIVE` 진입은 2026-10-20 04:38:26 UTC, 종료는 04:40:57 UTC다. 연결 종료는 대화 중 무응답 이후에 발생했다.
- CHILD 전사 FINAL·표시 승인 행은 8개다. 입력 경로가 동작했다.
- AI 전사 FINAL·표시 미승인 행은 46개이고, 이 중 21개는 글자가 있다. 표시 승인 AI 행 1개는 참여 대기 시작 시점의 안내이며, 생성 응답 성공 증거가 아니다.
- 폐기 지표는 `mujoong_gate_discard_total{reason="gate_empty"}=44`, `reason="segment_oversize"=1`이다. 종료 시 열린 AI 행을 닫은 것도 미승인 행에 포함될 수 있으므로 행 수와 폐기 지표 수를 같은 것으로 세지 않는다.
- `mujoong_relay_out_seconds_count=0`. 제브 호출 지표와 `realtime.guardrail_event` 행은 모두 0이다. 적어도 이번 세션에서는 제브 이전 검사에서 응답이 막혔다.
- 미승인 AI 행 46개 중 45개의 종료 시각이 CHILD 전사 행의 시작~종료 구간 안에 있다. 시간적 상관관계이며 각 행의 구체적인 폐기 조건까지 입증하지는 않는다.
- `LATENCY_TURN` 46건의 미관측 사유는 모두 `NO_OUTPUT`이다. 코드상 이는 지연 기록의 `firstOut` 부재를 뜻하므로 공급자 음성 수신 자체가 전혀 없었다는 뜻으로 해석하지 않는다. `SEGMENT_OVERSIZE`는 출력 음성 버퍼 상한 초과를 나타낸다.

## 코드 근거와 판단

- `SessionExecutor.onInputTranscriptDelta`는 입력 전사 조각마다 열린 출력 구간을 `sealAndGate(true)`로 닫는다. 같은 입력 묶음의 후속 조각도 이 경로를 반복한다.
- `sealAndGate(true)`는 마지막 출력 이후 800ms가 지나지 않으면 구간을 불완전으로 봉인한다. `OutputGate.inspect`는 불완전·빈 전사·빈 음성·PCM 길이 조건 위반을 모두 `GATE_EMPTY`로 합친다.
- 출력은 `SegmentBuffer`에 음성과 전사를 함께 모은 뒤 검사 통과 시에만 표시·재생된다. 따라서 구간 폐기는 글과 소리가 함께 없었던 증상을 설명한다.
- **확정된 장애 위치**: 공급자 응답 수신 이후의 구간 조립·1차 검사와 표시 승인 사이. **유력한 기여 요인**: 입력 전사 조각의 반복 도착이 진행 중인 출력을 반복 봉인하는 동작.
- **아직 미확정**: 44건 각각의 `GATE_EMPTY` 세부 조건, 공급자 출력의 실제 조각 간격, 연속 출력·전사 시간선·오디오 시계의 영향. 현재 집계만으로 단일 원인을 확정하거나 시간 값을 바꾸지 않는다.

## 수정 후보와 검증 범위

1. 구간 검사에서 완전 여부·음성 바이트 수·전사 존재 여부·봉인 계기만 집계해 `GATE_EMPTY` 세부 원인을 구분한다. 원문과 식별자 없이 진단한다.
2. 가짜 공급자로 동일 입력 묶음의 여러 조각과 출력 조각이 교차하는 회귀 상황을 재현한다. 입력 시작·후속 조각·진짜 끼어들기를 구분하는 수정을 검토한다. 중단된 응답의 꼬리가 새 응답으로 승인되지 않도록 기존 안전 단언을 유지한다.
3. 재현 결과가 구간 끊김 가정의 문제를 가리키면 별도로 응답 경계 설계를 검토한다. 검사 우회·구간 상한 확대·시간 값 임의 변경을 해결로 삼지 않는다.

예상 영향: realtime 실행기·구간 진단·관련 회귀 시험 중심, 약 반나절(조사와 자동 시험 포함)의 작업으로 예상한다. 실제 공급자 출력 경계 설계 변경이 필요하면 추가 산정한다. 자동 검증은 가짜 공급자를 사용하므로 추가 API 비용은 없다. 출력 경계 변경은 미완성·중단된 음성이 새는 위험이 있어 위험도는 중간이며 코드 변경 전 계획 검토가 필요하다. 사용자 로컬 스택 재기동은 이번 조사에 포함하지 않는다.

## 검증

`./gradlew :realtime-activity:test --tests kr.mujoong.realtime.gate.OutputGateTest --tests kr.mujoong.realtime.gate.OutputGenerationTest --tests kr.mujoong.realtime.gate.SegmentBufferGenerationTest`가 성공했다. XML 결과상 실행된 시험은 `OutputGateTest` 17건과 `OutputGenerationTest` 21건으로 총 38건이며 실패·오류·건너뜀은 0건이다. 마지막 선택자는 결과 XML이 없어 실행 증거로 세지 않는다. 이 시험은 기존 폐기 동작을 확인한 테스트 대역이며 장애 수정이나 실제 공급자·기기 재검증을 뜻하지 않는다. 전체 빌드·회귀 검증은 아직 실행하지 않았다.

## 추가 수동 테스트 — 참여 대기 중 사용자 전사가 보이지 않음

사용자가 재시험 후 부모 앱에 입력 내용이 없다고 보고하여 기존 로그와 DB를 추가 조회했다. 새 유료 호출·코드 변경·스택 재기동 없이 조사했다.

- 최근 세 번의 활동(시작 UTC 04:58:19, 04:59:23, 05:01:25)은 모두 `WAITING_CHILD`에 머물렀고 `ACTIVE`에 진입하지 않았다. 앞 두 번은 `GUARDIAN_STOP`으로 끝났으며 마지막은 UTC 05:02:02에 `DECLINED`로 끝났다.
- 마지막 활동의 `JUDGMENT_LIVE` 세 번(UTC 05:01:40, 05:01:46, 05:01:58)은 모두 `lunaOutcome=TIMEOUT`, 약 3999ms다. `JOIN_RE_PROMPTED`의 사유는 `UNCLEAR`다. 이는 입력 전사가 참여 판정까지 도착했음을 보여 주지만 실제 발화 의미나 참여 의사를 입증하지는 않는다.
- `SessionExecutor.onInputTranscriptDelta`는 `WAITING_CHILD`에서 전사를 묶되 저장하지 않는다. 확정된 전사는 `JoinFlow.onJoinReply`의 참여 분류에만 사용한다. 따라서 이 상태에서 부모 앱에 발화 내용이 없는 것은 표시 데이터가 생성되지 않는 코드 경로로 설명된다. 마지막 `DECLINED` 경로는 세션 전사도 지운다.
- 이번 증상은 앞선 `ACTIVE` 이후 출력 구간 폐기와 발생 위치가 다르다. 참여 확인을 통과하지 못한 원인과 응답 구간 폐기는 각각 검증해야 한다. 판정 지연의 세부 원인은 아직 확인되지 않았으며 시한만 늘리거나 `DECLINED`를 사용자의 실제 거부 의사로 해석하지 않는다.
- 분리 확인 방법: 새 활동에서 안내 뒤 짧은 긍정 한 단어를 말하고 전사 묶음 확정까지 잠시 기다린다. `JoinTracker`의 짧은 긍정 분류는 모델 판정 없이 참여를 수락한다. `ACTIVE` 전환 여부를 먼저 관찰한다. 이 방법도 전사 인식 성공이나 이후 AI 응답 재생을 보장하지 않는다.

### 짧은 긍정 재시험의 추가 결과

사용자가 새 자유대화에서 “응” 한 단어로 재시험했지만 인식되지 않았다고 보고했다. UTC 05:06:22 시작 활동은 `WAITING_CHILD`에 머물렀다. 판정 DB에는 UTC 05:06:35의 `J1 / JOIN_UNCLEAR / ABSTAINED / TIMEOUT / 4000ms / REPROMPT_JOIN`과 UTC 05:06:39의 `SESSION_EXITED`가 있다. 후자는 보호자 종료 시 취소된 판정으로, 로그의 TIMEOUT 분류와 구분한다.

따라서 적어도 비어 있지 않은 확정 전사가 분류까지 도착했지만, 짧은 긍정으로 매칭되지 않고 불명확 판정으로 갔다. 실제 전사 원문은 참여 전 비저장 정책으로 남지 않아, 발음·인식 결과·조각 묶기 중 어느 것이 원인인지는 아직 확정할 수 없다. “응”이 정확히 전사됐는데 분류기가 거절했다고 단정하지 않는다. 구두점은 정규화에서 제거하므로 구두점만을 원인으로 단정하지도 않는다.

`./gradlew :realtime-activity:test --tests kr.mujoong.realtime.dialog.JoinTrackerTest` 실행은 성공했다. 기존 시험의 합성 문자열 “응”은 ACCEPT로 분류된다. 이는 실제 음성 인식 성공 증거가 아니다. 다음 수정 계획에는 원문 없는 입력 수신·전사 조각 개수·묶음 길이·긍정 매칭 여부·분류 코드 진단과 참여 판정 시간 초과 조사를 함께 포함해야 한다. 같은 사용자 수동 시험의 반복만으로 사라진 전사 원문을 복원할 수는 없다.
