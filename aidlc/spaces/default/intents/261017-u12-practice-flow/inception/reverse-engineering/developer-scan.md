- `SessionInternalController.toCommand`(`session/web/SessionInternalController.java` 164줄)는 `InternalBody.check(body.activityType() == ActivityType.FREE_TALK, "activityType")`로 PRACTICE 시작을 거절한다(주석: "U1 Realtime은 자유대화만 실행한다(연습 프로토콜은 U5)"). 거절 단언 시험이 두 곳에 있다: `web/RealtimeInternalApiIT.java` 228줄(`FREE_TALK` → `PRACTICE` 치환이 `VALIDATION_FAILED`), `session/web/SessionInternalControllerU4bTest.java` 81~83줄(`practiceStaysClosedAtTheControllerUntilU5bOpensIt`).
- 시작 본문 타입 `StartBody`(같은 파일 61~72줄)에는 `practice` 필드가 없다. 스키마 `internal-session-start-request.schema.json`에는 `practice`(anyOf object/null)가 있고 core `RealtimeSessionClient.startPractice`(208~245줄)는 본문에 `practice`를 실어 보낸다. realtime은 `FAIL_ON_UNKNOWN_PROPERTIES`가 꺼져 있어 `practice`를 조용히 버린다.
- `StartSessionHandler.plan(...)`(318~343줄 부근)은 `SessionExecutor.Plan`의 `practiceJson` 자리에 `null`을 넘긴다(`..., command.activityType(), approved, null, command.guardianId()`).
- 결과: `Plan.practiceJson()`은 운영 경로에서 항상 null이고, `PracticeContext.practiceJson`을 채우는 곳은 시험(`SessionHarness.practiceJson`, 예: `PracticeExtensionU4bTest` 45줄)뿐이다. 지시서의 "realtime은 practice JSON 원문을 `PracticeContext.practiceJson`에 그대로 넘긴다"는 `afterActiveWon`(`SE` 1168~1169)까지만 맞고, 그 앞 HTTP → `Plan` 구간에서 끊겨 있다. 이 사실은 지시서 · `docs/units/u11` · U13 문서 어디에도 없다.
- 영향 파일(변경 시 단언 변경 대상): `SessionInternalController`, `StartSessionHandler.StartCommand` · `plan`, `RealtimeInternalApiIT`, `SessionInternalControllerU4bTest`, `U8SessionStartEndpointTest`/`U8SessionStartReceiveTest`(approvedSpeech 수신), 계약 `contracts/internal-api.yaml`(`activityType: FREE_TALK` 예시만 있음).

### 1. 연습 통제(`controlsOutput()` true) 아래 새 발화 폐기 분기 · 제브 연습 모드
- `SE.sealAndGate`(약 2985~3030줄): 구간이 봉인되면 ① `services.gate().inspect(sealed)`(금지 패턴), ② `practiceControlled = practice != null && practice.controlsOutput()`(3004줄)이고 `pendingPracticeSpeech == null` 이거나 `!pendingPracticeSpeech.matches(sealed.transcript())`이면 `discard(sealed, GATE_PATTERN, false)`(3005~3008줄) 후 return. 즉 **연습이 출력을 쥔 동안 승인 발화(`speak`)와 공백 제외 원문이 같지 않은 모든 GPT-Live 출력은 버려진다.** ③ 같으면 `guardrail.onVerbatimSkipped(SOURCE_PRACTICE_SPEECH, …)`(3010~3012줄)만 하고 `recheckAndSend`.
- 연습 통제가 아닌 세션만 `guardrail.verbatimSource(...)` 또는 `guardrail.begin(sealed, GuardrailRequest.Mode.FREE_TALK, null)`(3023줄)로 간다. **`SE`에서 `begin`은 이 한 호출뿐이고 모드는 항상 `FREE_TALK`이다.** `PRACTICE_PEER` · `PRACTICE_COACH`를 쓰는 운영 호출자는 없다(`GuardrailRequest.Mode` 정의, `LiveContentResources`의 모드 검증, 시험만 참조).
- 제브 연습 모드 수신 준비는 있다: `GuardrailCoordinator.begin(sealed, mode, practiceSpeechId)`(258줄)가 모드와 연습 발화 id를 받고, 무효 사유 `PRACTICE_CHANGED`(542~543줄: 요청의 `practiceSpeechId`가 null이 아닌데 `env.practiceSpeechId()`와 다르면), 두 번째 막힘에서 모드가 `FREE_TALK`이 아니면 `env.practiceBlocked(new GuardrailBlockedEvent(..., retried=true))`(585~592줄) → `SE.GuardrailEnv.practiceBlocked`(약 1832~1838줄)가 `Kind.GUARDRAIL_BLOCKED` 사건을 안전 편지함에 넣는다. 이 경로를 도는 시험은 `session/GuardrailPracticeEventTest`(`@Tag("u13")` 5개)다.
- 막힘 처리: 첫 막힘은 `env.sendReplay(lastInstruction)` 또는 `sendRetryFreeTurn`(`InstructionTemplates.Retry.RETRY_FREE_TURN`)으로 한 번 재지시한다(`blocked`, 570~617줄). 재지시는 `ReplayableInstruction`으로 기억된 마지막 서버 지시(판정 뒤 다음 행동 · 응답 시작 지시)만 다시 보낸다(`sendInstruction(…, replayable=true)`는 `requestResponse`에서만 참, `SE` 2071~2074).
- 같은 이유로, 연습 통제 중 **`instructProvider`/`requestResponse`로 낸 GPT-Live 새 발화도 `sealAndGate` 3004~3008줄에서 폐기되고(코드 읽기), 그 앞 `outputHeld()`(2078~2081줄: `practiceHold && ACTIVE`)가 참이면 조각 자체를 구간에 넣지 않는다**. `practiceHold`는 `speak()`가 거짓으로 풀고(1870줄), 승인 발화가 송신되는 순간 다시 참으로 만든다(`recheckAndSend` 3081~3085줄). `instructProvider`(1927~1944줄) · `requestResponse`(1946~1953줄)는 `practiceHold`를 건드리지 않고, 풀려면 `holdOutput(false)`(1963~1972줄)를 따로 불러야 한다.
- 같은 폐기 분기는 연습 중 판정 6(J6) 휴식 확인의 `REST_ACK_ONLY` 지시 출력에도 적용된다(`decideStopJudgment` 2559~2570줄이 `practiceHold = false`로 막음을 풀고 지시를 보내지만, 응답이 봉인되면 `pendingPracticeSpeech == null`이라 3004~3008 분기가 폐기한다 — 코드 읽기 결과이며 실행 시험은 없다. `StopJudgmentExecutorTest` 245줄은 지시가 송신되는 것까지만 단언한다).
- 제브 사건 소비: 레거시 `RuntimePracticeExtension.onExtensionEvent`는 `PLAYBACK_FACT` · `TIMER_FIRED` · `u5b-*` 이름의 `ASYNC_RESULT`만 처리하고 `GUARDRAIL_BLOCKED` · `JUDGMENT_*` · `HELD_OUTPUT_TRANSCRIPT` · `REST_REQUESTED`는 어느 분기에도 걸리지 않아 무시한다(마지막에 `return signal()`).

### 2. `announceRoleSwitch` · `playApproved` · approvedSpeech 경로
- `PracticeOutputPort.announceRoleSwitch`(`SE` 1999~2006줄): `practiceActive()`가 아니면 `refusePractice("announceRoleSwitch","NOT_ACTIVE")`, 그 밖에는 주석("자리와 거절 규칙만 있다")만 있고 항상 `return false`. 인터페이스 기본값도 `false`(`PracticeSessionExtension` 304줄). 운영 · 시험 호출자는 `SE` 안 정의뿐이다.
- `playApproved(code)`(`SE` 1897~1925줄 부근): `plan.approvedItem(code)`가 비어 있으면 `reportMissing(code)`(세션당 코드별 1회 `APPROVED_CONTENT_MISSING` 이벤트) 후 **곧바로 `PLAYBACK_DONE` 사건을 편지함에 넣고 `true`를 돌려준다 — 소리 없이 끝난다**(1905~1914줄). `plan.approved()`는 시작 패키지 `approvedContent`(음성 있는 승인 문구)만 담는다(`StartSessionHandler.plan` 330~337줄). `approvedSpeech`(음성 없는 승인 발화, 예: `HELP_OFFER` · `D_REST_ACK_START` · `D_REST_ACK` · `COACH_SWITCH` · `PEER_RETURN`)는 `Plan`에도 `PracticeContext`에도 들어오지 않는다(`PracticeContext.approvedContentCodes = plan.approved().keySet()`, 1168~1169줄).
- `approvedSpeech`가 실행기에 닿는 길은 `StartSessionHandler.pinContent`(273~291줄) → `LiveContentRegistry.pin`(세션 계획에 `approvedSpeech` 맵 고정)뿐이다. 레지스트리를 쥔 협력 객체는 `ApprovedVerbatimPort.of(liveContent)`(`RealtimeRuntimeConfig` 108줄, 제브 원문 일치 확인용 `matchedSource`만 노출)다. **`LiveContentRegistry.plan(sessionId).approvedSpeech()`를 읽는 운영 호출자는 `matchApproved` 내부 외에 없고, 확장점 · 실행기에는 레지스트리 접근이 없다.**
- `LiveContentRegistry.registerScript(sessionId, scenarioRef, scriptVersion, sentences)`의 운영 호출자는 없다(호출은 `LiveContentRegistryTest` 92 · 153줄, `GuardrailApprovedSkipTest` 37줄뿐). `matchApproved`는 `approvedSpeech` 값과 등록된 `SessionScript.sentences` 값이 ASCII 공백 제외 원문과 같으면 `MATCHED`를 돌려준다(연습 통제 세션에서는 이 레지스트리 경로가 아니라 `pendingPracticeSpeech.matches`가 쓰인다).
- 승인 발화 코드 허용 목록(core `StartActivityService` 94~97줄): 연습 `HELP_OFFER` · `D_REST_ACK_START` · `D_REST_ACK` · `COACH_SWITCH` · `PEER_RETURN`, 자유대화 `D_REST_ACK_START` · `D_REST_ACK`. 텍스트는 core `DevSeedRunner` 시드에서 온다(`SeedIds.CONTENT_COACH_SWITCH` · `CONTENT_PEER_RETURN`).
- 음성 있는 승인 문구 재생 능력과 별개로, **`speak(PracticeSpeech)`가 승인 원문을 읽히는 유일한 경로**다: `PracticeInstruction.forSpeech`가 "speech만 그대로 읽고 다른 말, 정답, 시범, 도움을 덧붙이지 않는다" 고정 문장 + `{partnerRole, speech}` JSON(상한 64,000자)을 만들고 `sendInstruction(SERVER_SEND, …)`로 보낸다(`SE` 1861~1878줄). `PracticeSpeech.kind`의 타입이 레거시 `PracticePorts.OutputKind`(`SCENARIO` · `HELP_QUESTION` · `CUE`)다.
- 지시 선 형식: 서버 발화는 `session.instructions.append` 하나(`ProviderRequestFactory.practiceInstruction` 165줄, `InstructionTemplates` 머리 주석: "응답 요청 type이 없어 모든 서버 발화가 지시로 시작", 맞장구 `INTERJECTION_LEAD` · 범위 닫기 `SCOPE_CLOSE`, `NextAction.{HOLD_REASK, REST_ACK_AND_RETURN, REST_ACK_ONLY}`, `Retry.RETRY_FREE_TURN`, `ResponseStart.{FIRST, CONTINUE}`).

### 3. `PracticeSessionExtension.Factory`의 생성 위치와 `practiceJson` 전달 시점
- 인터페이스 `PracticeSessionExtension.Factory.create(UUID sessionId)`(`PracticeSessionExtension.java` 336~341줄). 실행기가 생성자에서 한 번 부른다: `this.practice = plan.activityType() == PRACTICE ? requireNonNull(services.practice().create(plan.sessionId())) : null`(`SE` 582~584줄). 이 시점에 `plan`(`practiceJson` 포함)은 이미 있으나 `create`는 `sessionId`만 받는다. 세션 행 조회가 필요한 운영 `Factory`는 `sessions.find(session).orElseThrow().guardianId()`를 람다 안에서 부른다(`PracticeRuntimeConfiguration` 56~64줄, 생성 시점에 DB 조회).
- `practiceJson`은 `afterActiveWon`(`SE` 1160~1171줄)의 `PracticeContext(plan.sessionId(), plan.practiceJson(), plan.approved().keySet(), plan.rawAudioConsent(), now)`로 `onActive`에 처음 들어간다. `RuntimePracticeExtension.onActive`는 이 문자열을 `JsonCodec`으로 `Package(goals[])`로 읽는다(`Goal`: `goalSelectionId` · `order` · `displayName` · `behaviorKey` · `behaviorVersion` · `judgmentCriteria` · `firstScenario`). 목표 순서가 `1..n`이 아니거나 첫 목표 `firstScenario`가 null이면 `IllegalArgumentException`("연습 순서 오류" · "첫 상황 없음")이다.
- 운영 `Factory` 빈은 `PracticeRuntimeConfiguration.practiceFactory`(`@ConditionalOnMissingBean`) 하나다. 없으면 `RealtimeRuntimeConfig`가 `ObjectProvider<Factory>`로 받아 `NoOpPracticeSessionExtension.FACTORY`를 쓴다(`runtime/RealtimeRuntimeConfig.java` 91줄). 출력권(`controlsOutput()`)이 있는 확장의 예외는 `practiceFailure`가 세션을 `SERVER_RESTART`로 실패 종료시키고(`SE` 1375~1383줄), 출력권이 없는 확장의 예외는 자유대화로 이어 간다(`practiceFailed = true`).
- 시험이 `Factory`를 쓰는 곳(시그니처 변경 시 영향): `testing/SessionHarness`(`practice` 필드 기본 `NoOp…FACTORY`) · `testing/RecordingPracticeExtension.factory` · `session/{GenerationSendExecutorTest, PracticeExtensionU4bTest, GuardrailTurnIT, JudgmentExtensionPortTest, JudgmentFaultExecutorTest}` · `practice/{PracticeRuntimeRaceTest, PracticeConfigurationTest}` · `RealtimeRuntimeConfig` · 기타 `Services(…)` 생성 시험들(`DbPoolWaitMonitorTest` · `DrainingLifecycleTest` · `MetricSnapshotJobTest` · `RealtimeMetricsScrapeIT` · `RealtimeLogHygieneIT` 등이 `Factory` 문자열을 포함).

### 4. 레거시 포트 연결 지도와 CI `u5b-scope` 하한
- 연결: `PracticeRuntimeConfiguration.practiceFactory` → `RuntimePracticeExtension`(생성자 인수: `PracticeRepository` · `MujoongClock` · `EvaluationClock` · `TimerDriver` · 호출/정산 `Executor` · `PracticeProperties` · `ScenarioPort` · `EvaluationProvider` · `CueProvider`). `RuntimePracticeExtension.onActive`가 `ResponseEvaluator`(← `EvaluationProvider`)와 `PracticeProtocol`(← `OutputPort` 익명 구현 · `ScenarioPort` · `EvaluationPort` 람다)을 만든다. `CueProvider`는 `requestSpeech`의 `CUE` 분기에서만 `calls.execute`로 부르고 결과를 `u5b-cue` 비동기 결과로 돌려받아 `StageOutputPolicy.cue(...)`로 거른다. 상황은 `PracticeScenarioClient.prepare`(내부 POST `/internal/practice/scenarios`, 요청 `{sessionId, goalSelectionId, kind, previousScenarioId}`)로 받는다. 이 클래스의 `Scenario` 레코드는 `scenarioId · kind · scenarioText · partnerRoleText · triggerScript · validation`만 읽고 `scriptVersion` · `scenes` 등 새 필드는 읽지 않는다.
- 기본 빈: `EvaluationProvider`(`failedFuture(IllegalStateException)`) · `CueProvider.UNAVAILABLE` · `PracticePorts.ScenarioPort`(`PracticeScenarioClient`) · `PracticeRepository`(`JdbcPracticeRepository`, V4 표) · `PracticeProperties`(`mujoong.timing.practice`).
- 레거시를 단언하는 시험(`@Tag("u5b")` 27파일, `practice/` 31파일 중 대부분): `PracticeRuntimeConfigurationTest.realProvidersRemainUnavailableInsteadOfReturningFabricatedSuccess`(33~42줄: `cueProvider().generate`와 `evaluationProvider().evaluate(null)`이 `IllegalStateException`을 원인으로 실패) · `RuntimePracticeExtensionTest` · `PracticeRuntimeRaceTest` · `PracticeProtocolTest`(11) · `ResponseEvaluatorTest` · `EvaluationDeadlineIT` · `EvaluationRecoveryTest` · `StageOutputPolicyTest` · `HelpConsentPolicyTest` · `PracticeRecordProjectorTest` · `PracticeRecordRecoveryTest` · `RecordCapturePracticeRecoveryTest` · `PracticeSettlementIT` · `PracticeRepositoryIT` · `PracticeDeletionIT` · `PracticeMigrationIT` · `PracticeScenarioClientTest` · `PracticeSpeechTest` · `PracticePlaybackTimingTest` · `PracticeStopConfirmRaceTest` · `PracticeExecutorIntegrationTest`(`practice/` 아래, 지시서는 `session/`이라 적었으나 실제 위치는 `practice/`) 등. `session/PracticeExtensionU4bTest`는 `RecordingPracticeExtension` 대역으로 확장점 계약을 단언한다(레거시 클래스 비의존).

- CI `u5b-scope`(`ci.yml` 140~188줄): `needs.changes.outputs.backend == 'true'`일 때 `./gradlew :realtime-activity:test :realtime-activity:jacocoTestCoverageVerification -PincludeTags=u5b -PcoverageScope=u5b -Pmujoong.test.db=docker`, 이어서 core `-PcoverageScope=u5b-core`. 범위 파일 `backend/coverage-scope/u5b.txt`는 32개 운영 파일(`practice/` 29개 + `session/PracticeRecordRecovery` + `voice/PracticeSpeech` + `voice/PracticeInstruction`)이다. `ci-gate`는 `needs`에 `u5b-scope`를 포함하고 실패 · 취소만 불허한다(건너뜀 허용, `ci.yml` 514~536줄). `voice/PracticeSpeech`를 바꾸면 이 범위 분모가 함께 움직인다.
- 레거시 클래스를 비우거나 지우면 위 시험 · 범위 하한에 직접 걸린다(범위 측정은 빈 목록 · 없는 파일이면 실패).

### 5. `ExtensionEvent.Kind`별 운영 호출자 · 판정 · 생각 중 · 되묻기
| Kind | 운영에서 내는 곳 | 레거시 확장의 처리 |
|---|---|---|
| `PLAYBACK_DONE` | `SE.playApproved`의 패키지 밖 코드(1911줄), PLAYBACK_MARK 완료(3288줄) | 처리 분기 없음(무시) |
| `PLAYBACK_FACT` | `practicePlayback`(1444줄: 음성 재생 시작 · 완료 · 실패 · 중단) | 처리(`protocol.playback`) |
| `TIMER_FIRED` | `onPracticeTimer`(1473줄) | 처리(`timers.fire`) |
| `ASYNC_RESULT` | `PracticeOutputPort.post`(2029줄) | `u5b-*` 이름만 처리 |
| `JUDGMENT_RESULT` · `JUDGMENT_ABSTAINED` · `HELD_OUTPUT_TRANSCRIPT` | `afterExtensionJudgment`(1601~1637줄) ← `requestExtensionJudgment` ← `requestJudgment` 능력. **`requestJudgment`를 부르는 운영 코드는 없다**(시험 `JudgmentExtensionPortTest` 등만) | 무시 |
| `GUARDRAIL_BLOCKED` | `GuardrailEnv.practiceBlocked` ← `GuardrailCoordinator.blocked`는 모드가 `FREE_TALK`이 아닐 때만. 운영에서 연습 모드 `begin`을 부르지 않으므로 보내지 않는다 | 무시 |
| `REST_REQUESTED` | `afterStopJudgment`의 J6 `REST` 결과 + 출력권 연습 + ACTIVE(2606~2610줄). **운영 트리거가 있는 유일한 새 Kind** | 무시 |
- `requestJudgment`(`SE` 1994 · `requestExtensionJudgment` 1566~1600): ACTIVE 아님 → `refusePractice`(PRACTICE_EXTENSION_FAILED 이벤트) · J1/J6/`point==null`/`transcriptSeq` 범위 밖 → 이유 없이 false · 최근 확정 전사 4개(`JudgmentCoordinator.RECENT_LIMIT = 4`) 밖 → false · J2 · J3 · J5의 `criteria`에서 `coreFunction` · `judgmentCriteria`를 문자열로 꺼내 `JudgeRequest.Criteria` 생성(실패 시 false) · `preflight`가 READY 아니면 `recordSkipped(…, NextAction.DELEGATED_TO_EXTENSION)` 후 false. ### 13. 연습 상태 기계가 기댈 기존 능력 · 금지 능력 요약(사실)
- 확장이 낼 수 있는 능력(`PracticeOutput`): `playApproved` · `instructProvider(text ≤ 500자, 제어 문자 금지)` · `requestResponse`(`ResponseStart.CONTINUE` 지시) · `cancelResponse`(`bumpOutput(PRACTICE_DISCARD)`) · `holdOutput` · `schedule`/`cancel`(이름 붙은 시계, 기술 일시정지 · 종료 확인 · J6 열림 동안 멈춤: `practiceProgressPaused` 1507줄) · `post`(어느 스레드에서나) · `speak(PracticeSpeech)` · `cancelSpeech` · `requestJudgment` · `announceRoleSwitch`(빈 틀) · `setThinking`.
