## 2. 설계 상세

### 2.1 레지스트리 두 개와 상태 소유 (SCD-1, SCD-2)

Realtime 안에 레지스트리 두 개를 메모리로 둔다. 영속 진실은 DB(세션 행 · 연결 행)이고 메모리는 그 사본과 시계다. 재시작하면 BR6.13이 DB를 정리하고 메모리는 비어 시작한다. 이 구조는 단일 인스턴스를 전제한다(2.2). 동시 활성 세션 상한 설정은 두지 않는다 — 넘을 때의 거절 코드가 계약에 없으므로 활성 세션 수를 지표로만 본다(J76, 관측 지표 등재는 observability-design.md에 요청).

**표 2.1-A. 상태 소유**

| 상태 | 영속 진실(DB) | 메모리 사본 | 메모리에만 있는 것 | 재시작 때 | 일관성 규칙 |
|---|---|---|---|---|---|
| 세션 | 세션 행(상태 · status_version) | 세션 레지스트리 항목(실행기 + 상태) | 구간 버퍼 · 안전 시한 예약 · 입력 대기열 · 출력 레인 · 기록기 칸 · 공급자 연결 | 비종료 세션을 FAILED(SERVER_RESTART)로 닫고 메모리는 비워 시작(BR6.13) | 실행기가 유일한 전이 실행자이고 DB 조건부 UPDATE가 최종 중재자(BR6.8). 레지스트리에 없는데 DB가 비종료인 세션(또는 실행기가 죽은 세션)은 재시작 직후 외에는 이상 상태다 — reliability-design.md 2.1 시한 표의 '고아 세션 점검' 행(maintenance 주기 `mujoong.session.orphan-check-interval` 30초)이 FOR UPDATE로 읽어 FAILED(SERVER_RESTART)로 전이하고 ERROR 로그와 SessionStateChanged를 쓴다. 실행기가 최상위 예외로 죽을 때의 1차 처리는 performance-design.md 2.1 생명주기 4번이다 |
| 기기 연결 | 연결 행(connection_id · state · last_seen_at) | 소켓 레지스트리 항목 | 소켓 핸들 · 출력 레인 · 마지막 메시지 시각 · 시계 환산 입력 | CONNECTED · UNSTABLE 행을 DISCONNECTED로(BR6.13) | 시작 명령은 DB가 CONNECTED이고 레지스트리에 그 connection_id가 있을 때만 통과(BR6.6 ②) |
| 속도 제한 | 없음 | Core 카운터 맵 | 전부 | 초기화 | 키 수 상한 10,000(`mujoong.limits.rate-counter-max-keys`, BR1.6) |
| 묘비 | 없음 | Realtime 맵 | 전부 | 비워짐. 늦게 만들어진 세션은 재취소로 닫힘(BR6.14) | 10분 TTL(`mujoong.session.tombstone-ttl`, BR6.7) |
| Core observedAt | 사본 갱신 시각(BR6.14) | Core 조회 성공 시각 | 조회 성공 시각 | 사라지고 사본 값을 쓴다 | 두 값 중 늦은 값(BR6.15) |

**표 2.1-B. 레지스트리 구조와 연산**

| 레지스트리 | 구조 | 연산 | 동시성 | 크기 |
|---|---|---|---|---|
| 세션 | 동시성 맵 sessionId → 항목, 보조 맵 보호자 → sessionId · 기기 → sessionId | 선등록(INIT) · 조회 · 제거 | 키 단위 원자 연산만. 전역 락 없음 | 활성 세션 수(종료 즉시 제거) |
| 소켓 | 동시성 맵 deviceId → 연결, connectionId → 연결 | 교체(HELLO_OK) · 조회 · 제거(닫힘) | 키 단위 원자 연산 | 기기 수의 두 배(≤ 60) |

**HELLO_OK 연결 교체 절차 (BR3.7).**

순서는 ① HELLO 수락 → ② 트랜잭션(행 `FOR UPDATE`, connection_id 교체, 이벤트)을 커밋 → ③ 레지스트리 교체와 옛 소켓 4001 요청 → ④ HELLO_OK 송신이다(3.3 재점검 결정 R3-7). 옛 연결을 4001로 닫는 일은 커밋 뒤에만 한다 — 기기 웹은 4001에서 자동으로 다시 접속하지 않으므로(T19Off) 커밋 전에 닫으면 교체가 실패했을 때 기기가 꺼진 채 남는다.

1. 수락. 연결 핸들러가 HELLO를 검증해 수락한다. 이 시점에는 소켓 레지스트리도 DB도 바뀌지 않는다.
2. 트랜잭션. 그 기기의 연결 행을 `FOR UPDATE`로 잠그고(첫 접속은 upsert) 행의 connection_id · state · since를 새 값으로 덮고 DeviceStatusChanged를 같은 트랜잭션에 쓴 뒤 커밋한다. 잠금은 기기 단위라 다른 기기와 경합하지 않는다.
3. 레지스트리 교체와 옛 소켓 닫기. 커밋되면 소켓 레지스트리의 deviceId 키를 새 연결로 교체하면서 이전 값(옛 연결)을 받아, 그 연결이 살아 있으면 4001 닫기를 요청한다(옛 연결의 송신기가 비동기로 처리).
4. HELLO_OK를 새 연결로 보낸다.
5. 트랜잭션이 실패하면 옛 연결은 그대로이고(레지스트리 불변, 4001 요청 없음) 새 연결을 1011로 닫는다. 기기는 5초 뒤 다시 접속한다.
6. 옛 연결의 닫힘 처리는 `where device_id = ? and connection_id = ?`가 0행이라 기록 없이 버려진다.

2번 커밋과 3번 교체 사이 수 ms 동안 시작 명령이 오면 DB는 새 connection_id인데 레지스트리는 옛 것이라 BR6.6 ②가 거절한다. Core는 이를 423 DEVICE_NOT_STABLE로 번역한다. 기기 교체 직후의 순간이라 허용한다. DeviceReleased 처리(BR3.8)는 레지스트리에서 기기의 연결을 찾아 4401로 닫고 DB를 `device_id` 조건으로 OFFLINE 처리한다.

### 2.2 단일 인스턴스를 깨는 지점 (SCD-3)

수평 확장은 쓰지 않는다. 수직 확장만 쓰고 Core · Realtime은 인스턴스 하나씩이다. 아래 표는 수평 확장을 시도하면 깨지는 곳이며 코드는 해당 클래스에 표식을 둔다(2.3). 재설계 방향은 지금 구현하지 않는 메모이고 필요해지면 별도 결정(ADR)으로 다시 설계한다.

**표 2.2-A. 깨지는 지점**

| 번호 | 상태 · 위치 | 수평 확장 시 깨지는 모습 | 규칙 | 재설계 방향(구현하지 않음) |
|---|---|---|---|---|
| SI-1 | Realtime 소켓 레지스트리(연결 객체의 마지막 메시지 시각 · 환산 입력 포함) | 시작 명령이 소켓 없는 인스턴스로 가면 423이 되고, 연결 대체(4001)가 옛 소켓을 못 닫으며, DeviceReleased의 4401이 닿지 않는다 | BR6.6 · BR3.7 · BR3.8 | 기기 쿠키 해시로 같은 기기를 같은 인스턴스에 고정 라우팅 + 연결 행에 인스턴스 표지 + 인스턴스 사이 명령 전달 |

| SI-5 | Core 속도 제한 카운터 | 한도가 인스턴스 수만큼 늘고 재시작하면 초기화된다 | BR1.6 · BR2.6 | DB 카운터 또는 Nginx 앞 방어선으로 중앙화 |

**DB가 승자를 정해서 이 목록에 없는 것.** 세션 전이 조건부 UPDATE(BR6.8), Inbox 선점 UPDATE(BR5.7), 멱등 키 유일 색인(BR6.2), 기기 토큰 확인(verify-token은 캐시 없음, BR3.4), 보호자 세션(Spring Session JDBC)이다. 마이그레이션은 배포 단계의 일회성 역할이라 앱 수와 무관하다(BR8.1).

### 2.3 표식과 기동 가드 (SCD-4)

| Outbox · Inbox 폴러(앱당 직렬) | 느린 상대(건당 3초)가 뒤 이벤트를 늦춘다 | 재시도 대기 행이 뒤를 막지 않는다(BR5.2). 발송 폴러와 재호출 폴러는 다른 스레드. Realtime의 시계 · 전이는 폴러와 무관하고 늦어지는 것은 Core 사본뿐 | 가장 오래된 PENDING 나이, 이벤트 전달 지연 |

### 2.5 동시 세션 비교 판정 (SCD-6)

NFR7.1의 판정은 한 세션만 돌 때를 기준값으로 두고 두 세션 동시 값의 증가를 본다. 종단 NFR5.2 값은 응답 길이 편차가 지배하므로 참고로만 적는다.

| 항목 | 정의 |
|---|---|
| 지표 A | 턴별 relay = relayInMs + relayOutMs(턴 로그) |
| 지표 B | 턴별 t3 − t2 |
| 기준값 | 단독 실행(L3)의 모든 턴에서 같은 지표의 nearest-rank p95. 표본은 시나리오당 20턴 이상 × 3회 |
| 비교 대상 | 동시 실행(L4)에서 동시에 실행된 것으로 센 턴. 두 세션의 턴 구간(t0 ~ t3)이 겹친 턴만 센다 |
| 판정(단독 기준 표본 ≥ 100) | 동시 p95 ≤ 단독 p95 × 1.2 |
| 판정(단독 기준 표본 < 100, 보통 60) | 동시 턴의 90% 이상이 단독 p95 × 1.2 이내 |
| 합격 | 지표 A와 B가 모두 합격. NFR5.2 종단(말 끝 → 첫 소리)은 같은 표에 참고로 기록 |
| 같이 적는 것 | 표본 수, 겹친 턴 수, 단독 · 동시 p50 · p95 · 최댓값, 실행 조건(커밋 · 키 값 · 공급자 종류) |

계정당 세션 1개(BR6.3)라 보호자 2명 · 기기 2대가 필요하고 부하 시험 전용 시드 세트 1 ~ 2를 쓴다. 같은 대본을 쓰며 L3와 L4 사이에 앱을 다시 띄우지 않는다. 실공급자 응답 길이가 턴마다 달라 지표 A · B에는 공급자 구간이 들어가지 않는다(relayOut은 구간 확정 이후, t3 − t2는 게이트 통과 이후). 상대 기준의 잡음 문제는 열림 1에 있다.

### 2.7 데이터 증가 모델 (SCD-9)

NFR7.7의 가정(세션 100건 × 이벤트 5개 + 기기 30대 × 상태 변경 하루 20회 × 7일 = 이벤트 약 4,700건, 건마다 Outbox 1행 + Inbox 1행 = 약 9,400행)을 표별로 나눈다.

| 표 | 증가 원인 | 시연 기간 행 수 추정 | 보존 | 정리 |
|---|---|---|---|---|
| realtime_outbox_event | 세션 전이 500 + 상태 변경 4,200 | 약 4,700 | 행은 유지, 페이로드는 전달 즉시 비움 | 실패 행 7일 뒤 비움 |
| core_inbox_event | 위 이벤트의 수신 | 약 4,700 | 같음 | 같음 |
| core_outbox_event · realtime_inbox_event | DeviceReleased 등 드문 제어 이벤트 | 수십 | 같음 | 같음 |
| core_device | 쿠키 없는 첫 요청마다 1행 + 등록 30 | 최대 약 1만(IP 하나가 시간당 20회를 7일 동안 발급해도 3,360) | EXPIRED는 7일 | 10분 점검 작업이 만료 표시와 7일 지난 EXPIRED 행 삭제를 함께 한다 |
| realtime_device_connection | 기기당 1행 | 30 | 계정 삭제까지 | — |
| core_activity · realtime_activity_session | 세션당 1행 | 각 100 | U4 | — |
| realtime_session_event | 세션당 약 15행 | 약 1,500 | U4 | — |
| realtime_session_stop_expression | 세션당 1행 | 100 | U4 | — |
| realtime_transcript | 세션당 약 40행(20턴 × 2) | 약 4,000 | U3 | — |
| 보호자 세션 표 | 로그인마다 | 수십 | 유휴 30일 만료 | 라이브러리 정리 |

합계는 약 2만 5천 행으로 10만 행 가정의 4분의 1이다. 행 평균 0.5 ~ 1KB로 저장 용량은 50MB 미만이다. 분할 · 샤딩은 쓰지 않는다.

**행 수 점검.** 표마다 `select count(*)`로 센다(10만 행 미만이라 비용이 작다). 상태별 분포는 Outbox `select status, count(*) ... group by status`, 가장 오래된 PENDING은 `select min(created_at) ... where status = PENDING`으로 본다. 어느 표든 5만 행을 넘으면 수동 점검 항목으로 올리고(제안), 10만 행 가정이 깨지면 전달이 끝난 행 자체의 정리 정책을 후속 유닛에서 정한다(NFR7.7). 시연 뒤 표별 행 수를 기록한다.

### 2.8 정리 작업 (SCD-10)

| 작업 | 앱 | 주기 키 | 대상 | 방식 | 근거 |
|---|---|---|---|---|---|
| 만료 코드 표시 | Core | `mujoong.cleanup.device-expiry-interval` 10분 | UNREGISTERED이고 code_expires_at이 지난 행 | 배치 UPDATE로 EXPIRED | BR1.4 |
| 만료 기기 행 삭제 | Core | 같은 작업 | EXPIRED이고 `mujoong.cleanup.expired-device-retention` 7일이 지난 행 | 배치 DELETE | BR1.4 |
| 실패 행 페이로드 비우기 | 양 앱 | `mujoong.cleanup.messaging-interval` 하루 1회 | FAILED · DEAD이고 `mujoong.retention.failed-payload` 7일이 지났고 purged_at이 비어 있는 행 | 배치 UPDATE로 payload를 `{}`로, purged_at 채움 | BR5.11 |
| 성공 행 페이로드 비우기 | 양 앱 | 작업 아님(전달 · 처리 직후 같은 트랜잭션) | PUBLISHED · PROCESSED · IGNORED | — | BR5.11 |
| 보호자 세션 만료 정리 | Core | 라이브러리 기본 주기 | 만료된 세션 | 라이브러리 | NFR9.2 |
| 전달이 끝난 Outbox/Inbox 행 삭제 | — | U1에 없음 | — | 10만 행 가정이 깨지면 후속 | NFR7.7 |

규칙: 인스턴스가 하나라 중복 실행이 없고 모든 작업이 멱등이다. 배치 크기는 `mujoong.cleanup.batch-size`(1,000, 제안)이며 배치마다 풀 연결을 반납하고 다음 배치로 간다. 배경 작업 동시 점유 상한(performance-design.md 2.6)을 따른다. 실패하면 WARN 로그를 남기고 다음 주기에 다시 한다. 시각은 앱 Clock이고 앱 시작 직후에 바로 돌리지 않고 한 주기 뒤에 처음 돈다(기동 부하 방지). 계정 삭제 참가자(BR2.10 · BR5.14)는 이 작업과 별개이며 삭제 지휘가 부른다.

### 2.9 수평 확장이 필요해지는 신호

수평 확장은 범위 밖이다. 다음 중 하나가 보이면 수직 확장(인스턴스 크기)을 먼저 보고, 그래도 안 풀릴 때 별도 결정으로 다시 설계한다: 동시 활성 세션이 시연 상한(2)을 넘는 운영이 필요해졌을 때(활성 세션 수 지표), 호스트 CPU 평균이 60%를 넘는 시나리오가 반복될 때, 가용성 요구가 99.9%로 오를 때(블루-그린은 단일 인스턴스 전제와 맞지 않는다, J61). 첫 재설계 순서는 Core의 속도 제한 · observedAt(DB 이전)이고 Realtime은 기기 고정 라우팅 + 세션 임대다.
