## 2. 배경과 해석

### 2.1 요구별 뜻

| ID | U1에서의 뜻 | 걸리는 곳 | 후속 유닛 몫 |
|---|---|---|---|
| NFR7.1 | 1차 판정은 한 세션만 돌 때의 NFR5.1(relayIn + relayOut)과 t3−t2를 기준값으로 둔 두 세션 동시 값의 증가다. 종단 NFR5.2 값에는 공급자 응답 길이(provider_response_duration)와 구간 확정 조용 시간이 섞여 응답 길이 편차가 비교를 지배하므로 t2−t1은 쓰지 않고 종단은 참고로 함께 적는다. 표본은 시나리오당 20턴 이상이고 한 세션 3회 + 두 세션 동시 3회라 단독 기준 표본이 보통 100 미만(20턴 × 3회 = 60)이므로, 그때는 동시 실행 턴의 90% 이상이 단독 실행 p95(nearest-rank)의 1.2배 이내인지로 판정한다(RD-13). 계정당 세션 1개(BR6.3)라 보호자 2명 · 기기 2대가 필요하고 부하 시험 전용 시드(FD 보강 A6)의 2세트를 쓴다. | BR6.3 · BR6.8 | U3 · U4: 연습 · 공백 시계가 더해진 뒤 재측정 |
| NFR7.2 | 부하 구성의 예상치: 외부 폴링은 D0 상태 확인(30기기가 모두 D0에 있는 최악이면 30 ÷ 2초 = 15 RPS) + 12 진행(세션 2 ÷ 2초 = 1 RPS) 약 16 RPS, 앱 사이 호출은 연결 상태 보고(30기기 ÷ 10초 = 3 RPS) + 12 조회 중계 1 RPS 약 4 RPS, WSS는 HEARTBEAT(30기기 ÷ 5초 = 초당 6회 last_seen_at 갱신). 40 RPS는 약 2.5배 여유를 둔 상한 시험값이다. CPU는 시나리오 평균, 메모리는 5분 평균이 아니라 최댓값으로 판정한다(RD-12). 30쌍은 계정당 기기 1대(BR2.4)라 보호자 30명이 필요한데 dev 시드(BR8.4)는 한 명이고, 코드 발급이 IP당 1시간 20회(BR1.6)라 21번째 기기부터 429이므로 일반 등록 경로로 만들 수 없다. 그래서 부하 시험 전용 시드(A6)를 DB에 직접 넣고 기기 토큰 해시를 미리 계산하며, `bootstrap.rate-limit`은 그 환경에서만 설정으로 올린다(prod 값은 20회/시간 그대로). 같은 NAT 뒤 기기 21대 이상 동시 등록도 같은 한도에 걸린다(운영 주의는 security 5절). | BR4.8 · BR6.15 · BR1.3 · BR1.6 · BR2.4 · BR8.4 | 후속 유닛이 컨테이너(Neo4j 등)를 더하면 메모리를 다시 잰다 |
| NFR7.3 | 격리의 근거는 세션 행마다 조건부 UPDATE(BR6.8)와 세션별 메모리 시계(BR6.12 ④)다. 세션 사이에 공유되는 자원은 2.3절 표의 요구를 지킨다. | BR6.8 · BR6.12 · BR3.7 | U4: 공백 · 참여 대기 시계도 같은 격리 |
| NFR7.4 | 수직 확장만 쓰는 근거는 단일 인스턴스를 전제한 메모리 상태다(2.2절). 외부 저장소(Redis)로 풀지 않는다(ADR-002: MVP 보류). 문서는 2.2절 표를 설계 문서에 옮기고, 코드는 해당 클래스에 '단일 인스턴스 전제' 표식(주석 또는 어노테이션, 방식은 3.3)을 둔다. Compose는 서비스당 1개로 둔다(3.4). | BR1.6 · BR2.6 · BR6.6 · BR6.7 · BR6.12 | 수평 확장은 범위 밖. 필요해지면 별도 결정 |
| NFR7.5 | 지연 = 봉투 occurredAt(업무 트랜잭션 시각) → 수신 앱 처리기가 PROCESSED로 커밋한 시각. 수신 앱이 계산해 타이머로 남긴다(두 앱이 한 호스트라 같은 시계). 정상 상태 = 상대 앱이 살아 있고 미전달 건수가 한 배치(20건) 이하. 기기 30대가 동시에 붙는 순간(DeviceStatusChanged 30건)이 가장 큰 순간 부하다. | BR5.2 ~ BR5.8 · BR4.8 | U2 ~ U7: 자기 이벤트도 같은 경로 |
| NFR7.6 | 풀 상한은 앱별 설정으로 읽는다. 긴 HTTP · 공급자 대기 중에는 DB 연결을 쥐지 않는다(짧은 트랜잭션, JPA를 쓰면 open-in-view 끔, ADR-006 7.1). 풀 대기 100ms 초과 횟수를 카운터로 남기고 수동 점검 기준(J68: 100ms 초과가 5분 이상, 마지막 점검 이후 최댓값으로 읽는다 — observability 3.2와 같은 해석)에 쓴다. | BR8.1 · BR5.7 | 후속 유닛: 같은 풀을 나눠 쓴다 |
| NFR7.7 | 증가 가능한 U1 표: Outbox/Inbox 4개, realtime_device_connection, core_activity, realtime_activity_session, 전사. 참고 산정(입력은 가정): 세션 100건 × 이벤트 5개 + 기기 30대 × 상태 변경 하루 20회 × 7일 = 이벤트 약 4,700건이고 건마다 Outbox 1행 + Inbox 1행이라 약 9,400행으로 10만의 1/10 안팎이다. 전달이 끝난 Outbox/Inbox 행 자체는 U1이 지우지 않고(BR5.11은 payload만 비움) 가정이 깨지면 행 정리 정책을 후속에서 정한다. | BR1.4 · BR5.11 · BR5.14 | 후속: 전사 · 기록 표는 보존 정책 |
| NFR7.8 | 지표 7종: JVM 힙, GC 정지, 스레드 수, 열린 WSS 연결 수(Realtime), 풀 활성 · 대기, Outbox 미전달(PENDING) 건수, 가장 오래된 PENDING 나이(J68 수동 점검: 마지막 점검 이후 최댓값이 60초 초과). 이름은 3.3, 노출은 내부 엔드포인트만(NFR4.15). | BR5.2 · BR5.13 | observability 문서와 이름 합의 |

### 2.2 단일 인스턴스 전제 목록 (NFR7.4)

| 위치 | 상태 | 수평 확장 시 깨지는 모습 | 규칙 |
|---|---|---|---|
| Realtime 소켓 레지스트리 | 살아 있는 기기 연결 connection_id → 소켓 | 시작 명령이 소켓 없는 인스턴스로 가면 423이 되고, 연결 대체(4001)가 옛 소켓을 못 닫는다 | BR6.6 · BR3.7 |
| Realtime 세션 시계 | 세션별 마지막 기기 메시지 시각(40초) | 다른 인스턴스가 받은 HEARTBEAT를 못 봐 ABORTED(DISCONNECT)가 오발동한다 | BR6.12 ④ |
| Realtime 10분 묘비 | Core가 취소한 sessionId | 다른 인스턴스로 간 늦은 시작이 거절되지 않는다 | BR6.7 |
| Core 속도 제한 카운터 | bootstrap IP당 1시간 20회, 등록 실패 보호자당 10분 10회 | 한도가 인스턴스 수만큼 늘고 재시작하면 초기화된다 | BR1.6 · BR2.6 |
| Outbox 발송 폴러 | 앱당 하나가 PENDING 행을 직렬 발송 | 두 인스턴스가 같은 행을 보낸다(수신 쪽 멱등이 흡수하지만 전송이 중복된다) | BR5.2 · BR5.5 |
| 정리 · 점검 작업 | 10분 정리, 하루 한 번 payload 정리, 연결 점검 | 중복 실행으로 경합한다(멱등이라 결과는 같다) | BR1.4 · BR5.11 · BR4.8 |
| Core observedAt | 12의 stale 판정 기준(메모리 허용) | 인스턴스마다 값이 달라 stale이 흔들린다 | BR6.15 |

DB가 정한 승자(조건부 UPDATE, Inbox 선점 UPDATE), Spring Session JDBC, verify-token(캐시 없음)은 DB 기반이라 이 목록에 없다. 마이그레이션은 배포 단계의 별도 역할이 한 번 실행하므로 앱 수와 무관하다(BR8.1).

### 2.3 세션 사이 공유 자원 (NFR7.3)

| 공유 자원 | 결합 위험 | 요구 |
|---|---|---|
| Outbox · Inbox 폴러(앱당 직렬) | 느린 상대 호출(제한 3초)이 뒤 이벤트를 늦춘다 | 재시도 대기 행이 뒤를 막지 않는다(BR5.2). Realtime의 시계 · 전이는 폴러와 무관하고 늦어지는 것은 Core 사본뿐이다 |
| 시한 점검 작업 | 블로킹 호출이 있으면 다른 세션 시한이 밀린다 | 시한 발동은 세션별 작업이고 DB · 공급자 호출로 시계 스레드를 막지 않는다. 스레드 수는 동시 세션 수보다 크게 둔다(3.3) |
| DB 연결 풀 | 한 세션의 느린 질의가 풀을 비운다 | 앱당 10, 대기 100ms 경고(NFR7.6) |
| 소켓 레지스트리 | 전역 락 | 동시성 맵을 쓰고 잠금은 기기 행(`FOR UPDATE`, BR3.7) 단위로만 건다 |
| 공급자 연결 | 공유 풀이 있으면 한 세션이 다른 세션을 막는다 | 세션마다 별도 연결(BR7.2) |
