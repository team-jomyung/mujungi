## 2. 정할 것

### Q1. 가용성 · 복구 · 배포 중단의 수치

A. 시연 운영 기간 7일 롤링 가용성 99.0% 이상(계획된 배포 제외, 외부 프로브 성공률). 컨테이너가 죽으면 Compose `restart: unless-stopped`로 5분 이내(목표 1분) 복구하고 헬스체크가 통과해야 트래픽을 받는다. 계획 배포의 서비스 중단은 60초 이내이고 진행 중 세션은 재시작 규칙대로 FAILED로 끝나도 된다
B. 99.9% 이상, 무중단 배포(블루-그린)
C. 목표를 두지 않는다
X. Other (please specify)

[Answer]: A — **Mode:** 대리 판단. EC2 1대 · 팀 5인 · 시연 중심이라 99.9%나 블루-그린은 비용만 늘고 검증할 수도 없다(단일 인스턴스를 전제로 하는 소켓 레지스트리 · 메모리 시계가 있어 블루-그린은 두 인스턴스 동시 기동 자체가 위험하다, NFR7.4). C는 Operation 가드레일(SLO는 수치로)과 어긋난다. 재시작 뒤 정합은 이미 BR5.12 · BR6.13이 정했다. 3.2 재점검에서 '헬스체크가 통과해야 트래픽'은 Compose depends_on service_healthy가 보장하는 기동 순서와 기동 직후 차단까지로 좁히고(실행 중 readiness 실패는 앱이 503을 직접 답한다), 외부 프로브는 호스트 밖에서 3종을 1분마다 부르는 방식으로 정했다(RD-8). **J61**.

### Q2. 백업 · 복원

A. PostgreSQL 전체 논리 백업을 매일 03:00(KST) 한 번, 같은 호스트의 별도 볼륨에 7일 보관한다. RPO 24시간, RTO 60분, 복원 절차 문서 + 리허설 1회. 오프호스트 복사는 이 단계에서 두지 않는다. 시연 데이터는 합성 데이터에 한하고, 실제 보호자 · 아이 데이터를 다루기 전에 백업 보관과 NFR12('삭제 완료 뒤 복구 수단 없음')의 충돌을 사람이 해소한다(열린 질문)
B. 백업하지 않는다
C. 오프호스트(S3 등) 복제와 시점 복구(PITR)까지
X. Other (please specify)

[Answer]: A — **Mode:** 대리 판단. 앱 재배포나 디스크 사고로 시연 데이터를 잃는 위험은 값싸게 막을 수 있어 B는 부적절하다. C는 일정(구현 7일)과 비용 밖이고 오프호스트 복제본이 NFR12의 삭제 완료 보장과 더 크게 충돌한다. A의 충돌(삭제된 계정 데이터가 최대 7일 백업에 남음)은 숨기지 않고 NFR12.4로 올려 사람 결정에 남긴다. **J62**.

### Q3. 서버 응답 지연 목표 (REST · 중계)

A. 보호자 · 기기 REST 서버 처리 p95 300ms 이내, 12 진행 조회(Realtime 중계 포함) p95 500ms 이내(내부 호출 제한 1초 이내). 음성 중계 증가분 p95 0.5초 · 말 끝 → 기기 첫 음성 p95 2.5초는 요구사항 NFR5 그대로 두고 U1은 측정 로그를 책임진다
B. 지연 수치를 REST에는 두지 않고 NFR5만 쓴다
C. p99까지 목표로 둔다
X. Other (please specify)

[Answer]: A — **Mode:** 대리 판단. 폴링 2초 주기와 내부 호출 제한(J26)이 이미 있어 REST에도 수치가 없으면 '느리다'를 판정할 근거가 없다. p99는 시연 규모에서 표본이 작아 의미가 없다. 300 · 500ms는 시작값이고 11/2 측정으로 조정한다. **J63**.

### Q4. 화면 첫 로드 · 켜기 지연 목표

A. /device D0는 코드 표시까지 p95 3초(와이파이), /parent 04는 Android Chrome 중급기 4G에서 LCP 2.5초 이내, T19 「켜기」→ 대기(HELLO_OK)는 p95 2초 이내
B. 화면 지연 목표를 두지 않는다
C. Lighthouse 점수 90 이상
X. Other (please specify)

[Answer]: A — **Mode:** 대리 판단. 아이 기기에서 「켜기」 뒤 오래 기다리면 사용 경험이 깨지고 D0는 보호자가 보는 첫 화면이다. 점수형 목표(C)는 측정 환경에 따라 흔들려 시험 기준으로 쓰기 어렵다. 수치는 11/2 측정 항목이다. **J64**.

### Q5. 용량 가정과 확장 방식

A. 시연 규모 상한: 보호자-기기 30쌍, 동시 활성 세션 2(NFR7), 폴링 합계 40 RPS 이하. 이 안에서 호스트 CPU 평균 60%, 메모리 70% 이하. 확장은 수직만이고 Core · Realtime은 인스턴스 1개씩(수평 확장 시 깨지는 곳 — 소켓 레지스트리 · 세션 시계 · 속도 제한 카운터 — 을 문서에 명시). DB 연결 풀은 앱당 최대 10
B. 수평 확장이 가능하도록 소켓 레지스트리 · 시계를 외부 저장소(Redis)로
C. 용량을 가정하지 않는다
X. Other (please specify)

[Answer]: A — **Mode:** 대리 판단. 제약은 'EC2 1대 · Compose'이고 ADR-002는 Redis를 MVP에 도입하지 않는 쪽이다. B는 구조를 키워 일정을 넘긴다. 단일 인스턴스 전제를 숨기지 않고 NFR7.4에 적는 것이 안전하다. **J65**.

### Q6. 보안 수치 (TLS · 헤더 · 비밀 · 점검)

A. TLS 1.2 이상 · HTTP는 301 · HSTS max-age 180일 · 인증서 자동 갱신(Let's Encrypt). 보안 헤더: CSP(default-src 'self' + 필요한 connect 대상), nosniff, Referrer-Policy strict-origin-when-cross-origin, frame-ancestors 'none'. 비밀은 서버 환경 변수 또는 권한 600 비밀 파일에만 두고 CI는 CI 비밀 저장소를 쓴다. 저장소 비밀 스캔과 의존성 취약점 점검(high 이상 0 또는 사유 기록)을 CI에 둔다. 속도 제한은 BR1.6 · BR2.6 값을 따르고 요청 크기 상한(REST 64KB · WSS 텍스트 8KB)을 둔다
B. 헤더 · 점검은 후속 보안 유닛에 미룬다
C. WAF · 침입탐지까지 둔다
X. Other (please specify)

[Answer]: A — **Mode:** 대리 판단. 아동 음성 서비스이고 NFR9가 Must이며 인터넷에 열리는 시연 서버다. 헤더 · 비밀 스캔은 비용이 거의 없다. 후속 유닛은 U1의 Nginx · 쿠키 · 설정 골격 위에 얹히므로 지금 정하지 않으면 유닛마다 달라진다. C는 EC2 1대 시연에는 과하다. **J66**.

### Q7. 관측 방식 (로그 · 지표 · 추적)

A. 구조화 JSON 로그(최상위 여섯 필드(ts · level · traceId · component · event · ownerHash) + attrs(사건 코드별 허용 키 표 — 숫자 · 열거값 · UTC 시각만)), 전사 · 원음 · 토큰은 attrs에도 불가. traceId를 보호자 REST → 내부 HTTP → 이벤트 봉투까지 전파. Micrometer + Actuator 지표(세션 종료 사유별 카운터 · 시한 발동 카운터 · 이벤트 전달 지연 · 풀 사용률 · 열린 연결 수 · 지연 구간 시각)를 내부 엔드포인트로만 제공. 분산 추적 백엔드(OpenTelemetry 수집기)는 두지 않는다
B. 분산 추적과 중앙 로그 수집(ELK · Loki)을 도입한다
C. 로그만 남기고 지표는 두지 않는다
X. Other (please specify)

[Answer]: A — **Mode:** 대리 판단. 앱이 둘 · 호스트 하나라 traceId 전파와 구조화 로그면 한 요청을 추적할 수 있고 수집기를 따로 운영할 비용이 시연 규모에 맞지 않는다. 지표 없이는 NFR5 · NFR7 측정(11/2)을 할 수 없어 C는 안 된다. 3.2 재점검에서 로그 필드 표현을 'NFR5.4의 시각 · 종료 사유 · 재시도 횟수를 담을 수 있게 최상위 여섯 필드 + attrs'로 고쳤다(RD-6, 사람 확인 항목). **J67**.

### Q8. 경보 · 대응 체계

A. 자동 외부 경보는 두지 않는다. 헬스체크 실패는 Compose 재시작으로 처리하고 운영자는 스모크 스크립트와 지표 엔드포인트를 수동으로 본다. 수동 점검 기준을 수치로 둔다: 5분 창 WARN 이상 로그 10건 초과, 이벤트 PENDING 최장 나이 60초 초과, FAILED 이벤트 1건 이상, 풀 대기 100ms 초과가 5분 이상(네 기준 모두 마지막 점검 이후의 최댓값으로 읽는다). 점검 주기는 시연 당일 하루 2회
B. Slack 등 외부 알림 서비스를 연동한다
C. 기준을 정하지 않는다
X. Other (please specify)

[Answer]: A — **Mode:** 대리 판단. 연동할 알림 서비스 계정 · 비밀이 이번 범위에 없다(비밀값을 문서에 쓰지 않는 제약). 그래도 Operation 가드레일은 경보 기준을 SLO보다 먼저 걸리게 수치로 두라고 하므로 C는 안 된다. 외부 경보는 후속 단계 열린 질문으로 남긴다. 3.2 재점검에서 '마지막 점검 이후 최댓값' 읽기를 덧붙였다: 지표 게이지는 재시작하면 0이 되어 하루 2회 순간값으로는 지난 사건을 못 보기 때문이며, 분 단위 지표 스냅샷 사건 METRIC_SNAPSHOT이 그 값을 로그에 남긴다(RD-14). **J68**.

### Q9. 검증 방법 (시간 주입 · 부하 · 측정)

A. 시간 값은 주입 가능한 `Clock`으로 읽고 시한 시험은 실제 시간을 기다리지 않고 값을 줄여 경계값(직전 · 직후)을 확인한다. 통합은 Testcontainers(PostgreSQL), 단위는 JUnit 5, 구조는 ArchUnit(앱 간 스키마 의존 금지), 화면은 Vitest. 11/2 측정(NFR5 · NFR7)은 서버 안의 구간 로그와 자체 WSS 부하 스크립트로 한다(외부 부하 도구 도입 없음)
B. 실제 시간으로 시험한다
C. 측정은 11/2에 따로 정하고 지금은 정하지 않는다
X. Other (please specify)

[Answer]: A — **Mode:** 대리 판단. NFR6이 '주입 시험'을 요구하고 B는 4분 · 6분 시한 시험이 불가능해진다. C는 U1이 지연 구간을 어떻게 남길지 정하지 못하게 한다. 도구 이름은 3.5에서 확정할 시작값이다. **J69**.

### Q10. 기술 스택 (버전 · 도구)

A. 백엔드 Java 21 LTS · Spring Boot 4.1.x(첫 볼트 호환성 검증 실패 시 3.5.x로 전환) · Gradle 8.14+(멀티 프로젝트: core-api · realtime-activity · 공통 계약), PostgreSQL 16, Flyway, Spring Security + Spring Session JDBC, springdoc, Jackson 3. 프런트 Node.js 22 LTS · Next.js(App Router) · React · TypeScript · TanStack Query v5(/parent) · Vitest · ESLint · Prettier. 운영 Docker Compose · Nginx · Let's Encrypt(certbot). 공급자 연결은 SDK 대신 표준 WebSocket 클라이언트로 시작하고 SDK 지원 범위는 3.5에서 확인(ADR-002)
B. Spring Boot 3.5.x로 시작한다
C. 프런트 앱을 둘로 나눈다(/parent · /device 별도)
X. Other (please specify)

[Answer]: A — **Mode:** 대리 판단. ADR-002의 기본 후보를 그대로 쓰되 '첫 볼트에서 호환성 검증' 조건을 요구사항으로 남긴다(검증 실패 대체안을 미리 정해 일정 위험을 줄인다). 프런트 2앱(C)은 ADR-003이 별도 결정 대상으로 남겼고 화면 설계(`/parent`, `/device` 한 앱)가 기준이다. PostgreSQL 16은 호환성 문제가 가장 적은 안정 버전을 고른 시작값이다. **J70**.

### Q11. 지원 브라우저 · 기기 범위

A. /device = 데스크톱 · 노트북 Chrome 최신 2개 버전(시연 기준), Android 태블릿 Chrome은 되면 좋음, iPad Safari 범위 밖. /parent = Android Chrome 최신 2개 버전(통합시험), iOS Safari 16.4+에서 U1 화면 렌더만 확인(푸시 · 공유 보장 없음). 마이크는 HTTPS + 「켜기」 사용자 제스처 뒤에만 요청, PWA · 서비스 워커 없음
B. 모든 브라우저를 지원한다
C. Chrome만 지원하고 iOS는 렌더도 확인하지 않는다

## 3. 답 분석

- **모호함:** 질문 12개의 답 자체는 닫혔다(수치는 시연 규모의 시작값이고 11/2 측정(OQ10)으로 조정한다고 K4에 적혀 있다). 그러나 문서를 쓰고 재점검하는 동안 사람이 정하거나 확인해야 하는 항목이 더 생겼으므로 '모호함 없음 · 열린 항목 4건'으로 요약하지 않는다. 사람 확인 게이트는 아래 '후속 질문'의 표와 각 문서 `## 5`의 사람 항목 전부를 본다.
