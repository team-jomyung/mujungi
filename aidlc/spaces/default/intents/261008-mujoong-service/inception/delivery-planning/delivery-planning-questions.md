## 3. 정할 것 — Construction 진행 방식

### Q7. Construction 반복 순서

A. 기록된 그대로 unit-major · serial을 유지한다. skeleton: on이므로 U1이 3.1 ~ 3.5와 스켈레톤 확인을 먼저 끝내고, 그다음 U2 → U3 → U4 → U5 → U7 → U6 순서로 유닛마다 3.1 ~ 3.5를 돈다
B. stage-major(모든 유닛의 3.1 → 모든 유닛의 3.2 …)로 바꾼다 — skeleton: on이면 이때도 U1이 먼저 3.5까지 간다
X. Other (please specify)

[Answer]: A — **Mode:** 대리 판단. 기록된 선택을 바꿀 까닭이 없다(단계 파일: 기록된 선택은 보존). 주의: 사람 지시("계속" 뒤 3.1 ~ 3.4를 유닛 7개 전부 진행하고 3.5는 시작하지 말 것)는 skeleton: on과 함께 쓸 수 없다. 엔진은 U1의 3.5(스켈레톤 코드)와 확인을 마치기 전에는 U2의 3.1을 열지 않는다. 그래서 "계속"을 받으면 U1의 3.1 ~ 3.4까지만 하고 멈춘다. 일곱 유닛 설계를 코드보다 먼저 받으려면 사람이 (가) U1의 3.5를 허락하거나 (나) 스켈레톤을 끄고 stage-major로 바꾸는 결정을 해야 한다 — `bolt-plan.md` 6절. **J38**.

### Q8. Construction 검증 명령(완료된 유닛마다 돌리는 실제 프로젝트 확인)

A. 아직 실행할 코드가 없으므로(그린필드) 지금 정하지 않고 비워 둔다. 엔진은 첫 유닛 체크포인트 전에 사람에게 묻는다. 후보는 `bash scripts/verify.sh` — Docker Compose를 올리고 시드를 넣은 뒤 Playwright로 보호자 · 기기 두 브라우저를 띄워 D0 코드 → 05a 등록 → 04 안정 → 08 시작 → 기기 가짜 마이크(녹음 파일) 음성 1턴 → P1 → ENDED까지 확인하고, 각 앱의 단위 · 계약 시험을 돌린다. 스크립트는 U1의 3.5가 만든다
B. 지금 임시 명령을 넣는다
X. Other (please specify)

[Answer]: A — **Mode:** 대리 판단. 단계 파일이 그린필드에서는 사람이 선택을 미룰 수 있다고 하고, 임시(가짜) 명령은 금지한다. 검증 명령은 사람이 승인해야 기록되므로 "3.5 전에 사람이 정할 것"에 올린다. **J39**.
