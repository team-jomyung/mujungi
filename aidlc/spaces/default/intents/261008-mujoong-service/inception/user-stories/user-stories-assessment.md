# User Stories 실행 판단

> User Stories(2.4) · 2026-10-08 · 입력: `../requirements-analysis/requirements.md`

## 결정

**Execute** — 사용자 스토리를 작성한다.

## 근거

- **사용자 대면 기능이 전부다.** 요구사항 FR1~FR6은 화면 설계 v1.5j 카드 25장(보호자 /parent 23장 + 아이 기기 /device 2장)과 1:1로 대응하며, FR7(서버 · AI 처리)도 보호자 · 아이가 보고 듣는 결과로만 드러난다.
- **페르소나가 둘 이상이다.** 보호자(모든 화면 조작)와 아이(음성 참여 · 켜기/끄기만)가 전혀 다른 접점과 능력을 갖고, 운영자(데모 준비)와 전문가(PDF 수신)가 주변에 있다.
- **업무 규칙이 복잡하다.** 세션 상태 11개 · 종료 사유 8개 · 시간 규칙 6종(NFR6) · 연습 2안+제브 흐름이 화면 분기표에 얽혀 있어, 수용 기준으로 풀어 두지 않으면 Functional Design과 테스트가 흔들린다.
- **5인이 담당을 나눈다.** A 계정 / B 음성 / C 연습 / D AI / E 결과가 7일 안에 병렬로 만들므로, 차선 단위 스토리가 Units Generation과 Delivery Planning의 재료가 된다.

## 스토리가 가장 값어치 있는 곳

1. **12 활동 진행 · 17 활동 끝** — 자유대화 · 연습 공통 화면에 종료 · 장애 · 공백 · 미확인 규칙이 모두 모여 있어 분기표를 수용 기준으로 고정해야 B · C · E가 같은 그림을 본다.
2. **아이 기기 음성 흐름** — 화면이 없는 사용자(아이)의 스토리는 분기표가 아니라 요구사항 FR5에서만 나오므로 여기서 Given/When/Then으로 풀어야 D의 AI 계약과 B의 음성 구현이 맞물린다.
3. **기기 등록(05a · D0)** — ADR과 어긋났던 흐름이라 보호자 쪽과 기기 쪽 두 스토리로 양끝을 적어 둔다.

## 묶는 단위

화면 설계의 차선(LANE) 여섯 개를 그대로 에픽으로 쓴다: 처음 한 번과 홈 · 기기 · 자유대화와 활동 진행 · 연습 · 기록과 리포트 · 아이 기기 웹. 수용 기준은 화면 분기표 한 줄을 한 줄로 옮긴다(Given 화면·상태 / When 단추·사건 / Then 어디로).
