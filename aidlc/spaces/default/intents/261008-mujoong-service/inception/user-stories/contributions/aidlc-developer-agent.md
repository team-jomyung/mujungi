### 2. 수용 기준의 모호 · 어긋남 (상태 전이 · 시간값 · 경계)

- 2-1. AC3.1.6 · AC4.1.3 "진행 세션 없음" — **수정** — "진행 중 = REQUESTED · PREPARING · DEVICE_ACK · WAITING_CHILD · ACTIVE · CLOSING 중 하나. ENDED · ENDED_UNCONFIRMED · ABORTED · DECLINED · FAILED는 막지 않는다. 거절 사유는 세션 있음 / 기기 안정 아님(불안정 · 끊김 · 응답 없음 · 없음) / 동의 없음 셋으로 구분되어 08 · 18에 보인다(응답 코드는 Contract Design)". 근거: 개발 명세는 ENDED_UNCONFIRMED 뒤 "다음 시작 전 04 기기 칸이 다시 확인"이라 적어 새 시작을 허용하는데, FR2.3의 "종료 미확인 세션으로 중복 시작되지 않는다"는 막는 것으로도 읽힌다. 서버 구현자가 둘 중 하나를 골라야 한다.
- 2-2. AC3.2.3 · AC3.2.4 "12 처음" — **수정** — 각각 "WAITING_CHILD", "PREPARING(DEVICE_ACK 대기)"로 상태 이름을 쓴다. 근거: "처음"은 REQUESTED~WAITING_CHILD 네 상태를 다 가리킨다.
- 2-3. AC3.4.3 "기기 종료 확인이 없으면 17 정리 끝으로 바꾸지 않는다" — **수정** — "기기 종료 확인이 없으면 '종료 확인됨'으로 표시하지 않고 미확인 표시를 유지한다. 결과 정리는 확보된 기록으로 진행하며 정리 끝 · 「오늘 기록 보기」는 결과 작업 상태로 정한다". 근거: AC5.2.6은 기술 문제 세션에도 27이 있다고 하고(= 정리가 돈다), 지금 문장은 ENDED_UNCONFIRMED · ABORTED에서 정리를 돌리지 말라는 뜻으로도 읽힌다.
- 2-4. AC3.6.1 종료 사유 → 17 문구 — **수정(표)** — GUARDIAN_STOP → 보호자 끝냄 / CHILD_STOP → 아이가 끝냄 / SILENCE → 말이 없어 자동 종료 / DISCONNECT → 연결 끊김 / UNCONFIRMED → 기기 응답 없이 끝냄 / CONSENT_WITHDRAWN → (17에 오지 않음 · 로그아웃) / DECLINED → (P3 · 17에 오지 않음) / FAILED → (시작 전은 08 · 18; **진행 중 서버 재시작(A7)은 어느 문구?**). 근거: 사유 8개 중 5개만 문구가 있고, A7은 FAILED에 "기기 응답 없이 끝냄" 문구를 빌려 쓰고 있어 UNCONFIRMED와 구분이 안 된다. 또 AC3.2.8은 "말이 없어 자동 종료", AC3.6.1은 "자동 종료"로 다르다 → FR7.9 문구로 통일.
- 2-5. AC3.6.2 17 표시 상태 — **추가(AC3.6.9)** — `검증: 17 표시는 세션 상태 × 결과 작업 상태로 정해진다. 마무리 중 = CLOSING; 정리 중 = (ENDED | ENDED_UNCONFIRMED | ABORTED) 이고 결과 작업 REQUESTED · RUNNING; 정리 끝 = READY; 정리 실패 = FAILED(자동 3회 뒤). 미확인 표시(confirmed=false)는 세션 상태에서, 정리 상태는 결과 작업에서 따로 온다`. 근거: 17이 두 상태 기계를 합쳐 보이는 유일한 화면인데 대응표가 없어 AC3.4.3 · AC3.6.2 · AC1.4.13이 서로 다르게 읽힌다.
- 2-6. AC1.4.13 "종료 확인 없는 세션을 종료 완료로 표시하지 않는다" — **수정** — 04에는 "종료 완료" 상태가 없다. "ENDED_UNCONFIRMED · ABORTED 세션은 지금 활동 칸에서 '진행 중'으로 보이지 않고, 대화 기기 칸이 기기 상태를 다시 조회한다; 미확인 표시는 17 · 27에서 한다"로. 근거: 개발 명세 ENDED_UNCONFIRMED 행.
- 2-7. AC2.1.3~2.1.6 기기 상태 5단계 — **수정 · 추가** — (a) 불안정 → 안정 복귀 조건이 없다. **추가 AC2.1.10**: `불안정은 최근 5분 창의 끊김이 2회 미만이고 최근 heartbeat 지연이 1초 이하로 돌아오면 안정이 된다(창 · 값은 NFR6 시간 계약)`. (b) 회색 "응답 없음"은 개발 명세에서 "연결은 있는데 명령 응답 없음(세션 패키지 20초 · 종료 명령 30초)"이라 세션 밖에서는 판정할 수 없다 — 세션이 끝난 뒤 회색이 언제 풀리는지(다음 heartbeat?) 적어야 한다. (c) 아이가 「끄기」로 끈 기기(개발 명세 REGISTERED_OFFLINE)는 5단계 중 어디인가. "끊김 · 전원 · 와이파이를 확인해 주세요"는 일부러 끈 기기에 맞지 않는다. 근거: Device 상태 7개(UNREGISTERED · REGISTERED_OFFLINE · CONNECTED · UNSTABLE · DISCONNECTED · UNRESPONSIVE · RELEASED)와 표시 5단계의 대응이 어디에도 없다. 대응표 자체는 Domain Design에 넘기되, AC에는 "서버 상태 이름"을 적어 두어야 시험을 쓸 수 있다.
- 2-8. AC3.2.11 · AC1.7.2 "보호자 서버가 기기 상태를 받지 못함" — **수정** — "서버의 기기 상태 마지막 수신(last_seen_at)이 N초(NFR6 시간 계약)를 넘으면 '기기 상태 확인 불가' + 마지막 확인 시각". 근거: 감지 조건이 없으면 구현도 시험도 못 한다. 알림 AC1.7.2도 같은 값으로 발동해야 중복 발송(AC1.7.5)을 막을 수 있다.
- 2-9. AC3.2.8 · AC6.6.5 "연속 공백" — **수정** — "공백 = 마지막 아이 발화 전사(또는 활동 시작 뒤 첫 안내 재생 완료) 이후 아이 발화가 없는 시간. AI 재생 · 게이트 대기 · 장애 구간은 세지 않는다". 근거: FR7.9는 "확인 가능한 연속 공백"이라고만 하고 기준점이 없다. ADR session-state도 "재생 대기를 무응답으로 세지 않는다".
- 2-10. AC6.3.3 · AC6.3.4 · AC6.3.7 재권유 횟수 — **수정** — "무응답 재안내 1회와 거부 시 대안 제안 1회는 각각 1회이며 합쳐 안내는 최대 3번(처음 · 재안내 · 대안)이다. 20초 기준점은 승인 문구의 기기 재생 완료 보고(playbackMark) 뒤다". 근거: AC6.3.7 "재권유가 1회를 넘지 않는다"가 둘을 합친 1회인지 각각인지 읽는 사람마다 다르다. 타이머 시작점이 없으면 NFR6 주입 시험을 못 쓴다.
- 2-11. AC6.3.6 ACTIVE 진입 — **수정(비고)** — "ACTIVE는 참여 응답 확인 시점이며 아이의 첫 발화 자체가 아니다(거부 · 주제 거부 발화는 ACTIVE가 아님)". 근거: 개발 명세 상태표는 "ACTIVE: 아이 첫 발화"로 더 느슨하다. 스토리가 기준이므로 비고로 못 박는다.
- 2-12. AC6.6.2 "상태 복원 가능" — **수정** — "복구 가능 = 기기 WSS만 끊기고 음성 모델 연결과 세션 맥락이 살아 있는 경우. 음성 모델 연결이 끊기면 새 모델 세션으로 이어 붙이지 않고 기술 종료(DISCONNECT)로 간다 — 또는 Domain Design에서 달리 정하면 그 규칙". 근거: ADR session-state "종료된 공급자 실시간 세션을 새 세션으로 이어 붙이지 않는다". 지금 문장은 두 장애를 한 묶음으로 다뤄 40초 재접속을 모델 끊김에도 적용하는 것으로 읽힌다(지식 문제, 결정은 Domain Design).
- 2-13.
