# User Stories 실행 판단

## 결정

**Execute** — 사용자 스토리를 만든다.

## 까닭

이번 작업은 AI 공급자 연결 같은 내부 작업이 많지만, 그 결과가 사람이 직접 겪는 동작을 바꾼다.

- **아이(6~12세):** 연습 대화 흐름이 바뀐다. "부족하면 도움 강제, 새 상황 항상 진행"에서 되묻기 · 도움 제안 · 집중 연습 · 선택적 변형으로 바뀐다(FR3 · FR4 · FR5). GPT-Live 새 발화는 재생 전에 안전 검사를 받는다(FR6).
- **보호자:** 결과 칩('되묻기 뒤')과 장면 수 표시가 바뀐다(FR7). 연습 목표 후보를 Luna가 아이 기록에서 새로 만든다(FR8).
- **운영 · 개발 담당:** 실제 공급자 실호출 검증, 설정 기본값, 실기기 검증 절차가 생긴다(FR1 · FR6 · FR12).

## 고려한 요소

- 프로젝트 유형: 기존 시스템 수정(brownfield). 요구사항 FR1~FR12, NFR1~NFR7.
- 사용자 쪽 범위: 아동 기기 음성 경험, 보호자 앱 결과 · 목표 화면.
- 복잡도 신호:
  - 상태 기계 개편
  - 판정 보류 · 실패 시 막힘 규칙
  - 과거 기록 호환
  - 외부 공급자 세 곳(Luna · 제브 · GPT-Live)과 Neo4j
- 요구사항 검토 지적 R-01 · R-02 · R-03 · R-04를 스토리의 인수 기준으로 구체화할 필요가 있다.

## 스토리가 가장 값어치를 내는 곳

1. 유연한 연습 흐름의 인수 기준. C §8.2의 장면별 기대 동작을 Given/When/Then으로 쓴다.
2. 제브 가드레일의 차단 · 통과 사례. C §8.1을 1:1로 옮긴다.
3. Luna가 만든 목표 후보가 보호자 화면 · 연습 상황 생성 · 결과까지 이어지는 흐름(R-01).
4. 운영 안전 기본값(R-02)과 외부 의존이 막혔을 때의 '완료' 정의(R-06).
