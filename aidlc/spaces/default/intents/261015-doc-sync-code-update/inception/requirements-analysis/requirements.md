# 요구사항 — 문서 기반 코드 갱신 (261015-doc-sync-code-update)

> 처음 요청: "업데이트 된 문서를 기반으로 코드 업데이트 작업 시작." [desc]
> 범위 규모: classic · Standard · 기준 코드 `feat/doc-sync-code-update` = `main` `72d7034`
> 질문 · 답: `requirements-analysis-questions.md`(Q1~Q10, 가정 13개 수락) · 코드 대조: `gap-report.md`(같은 폴더)

## 1. 의도 분석

2026-10-15에 무중의 **AI 모델 역할이 확정**됐다. 기존 문서들이 그날 고쳐졌고(D), 새 기술명세서 v0.3 · AI 동작 명세 v0.2(A · B)와 Luna · JEV 구현 인계서 v2(C)가 들어왔다 [desc][Q1].
- GPT-Live: 아이와 실시간 음성 대화
- GPT-6-Luna: 연습 상황 생성, 진행 중 판정, 활동 뒤 분석
- 제브(Jev): 아이에게 들려줄 GPT-Live 새 발화의 가드레일
- Neo4j: 화용 지식 그래프

지금 코드는 이 역할을 거의 반영하지 못한다(`gap-report.md` 0~11절).
- 실제 AI 공급자 연결이 없다(기본 빈이 모두 실패를 돌려줌).
- 진행 중 판정 포트, 제브 포트, Neo4j 어댑터가 없다.
- 연습 흐름이 "부족하면 도움 강제, 새 상황 항상 진행"이라 새 문서들과 다르다.

이 작업의 목표는 다음 세 가지다.
1. 문서가 정한 모델 역할을 코드에 반영한다.
2. 실제 공급자 연결을 합성 자료로 검증한다.
3. 실기기 검증 절차까지 준비한다(C의 P0~P5) [Q2].

### 1.1 문서 우선순위 (이 작업에서 정한 것)

1. 화면 설계 v1.5j가 가장 앞선다(CLAUDE.md).
2. A · B와 C가 부딪히면 **C를 따른다.** C가 말하지 않는 부분은 A · B를 따른다 [Q1].
3. 예외: 목표 후보 생성(Q6)과 새 씨앗 저장(Q10)은 사람이 명시적으로 A · B 쪽을 골랐다.
4. 진행 중 판정은 C가 말하지 않으므로 A · B(J1~J6 Luna 판정)를 따른다 [Q3].

## 2. 기능 요구사항

### FR1. Luna 공급자 연결 (P1)

- **FR1.1** 시스템은 GPT-6-Luna를 openai-java Responses API와 구조화 출력(JSON Schema)으로 호출하는 어댑터를 core-api와 realtime-activity에 둔다. 모델 이름은 `OPENAI_ANALYSIS_MODEL` · `OPENAI_JUDGE_MODEL`(기본 `gpt-6-luna`), 키는 `OPENAI_API_KEY`에서 읽고 코드에 박지 않는다 (A §5.8 · §11.3, 가정 7).
- **FR1.2** 서버는 응답의 스키마와 인용을 검증한다. 스키마가 맞지 않으면 1회 다시 요청하고, 그래도 맞지 않으면 작업 실패로 처리한다. 결과 행마다 `model`과 `prompt_version`을 저장한다 (A §5.8).
- **FR1.3** U5a `TextAiProvider`와 U6 `ResultTextProvider`의 기본 빈(지금은 항상 실패)을 설정으로 켜고 끌 수 있는 실제 어댑터로 바꾼다. 설정이 꺼져 있으면 지금과 같은 실패 경로를 유지한다 (C §5.1 · §5.2, gap §5).
- **FR1.4** 공급자 요청마다 보낸 필드 이름 목록을 감사 로그로 남기고, 요청 · 응답 본문은 로그에 남기지 않는다. 아이 이름은 '아이'로 바꿔 보낸다 (A §7.1, B §1.3, R-F14).

### FR2. 연습 상황 생성과 Luna 자체 검토 (U5a, P1)

- **FR2.1** 연습 상황은 다음 순서로 만든다: (그래프 맥락이 있으면 구조 맥락 · 변형 계획 조회) → Luna 생성 → **생성과 분리한 Luna 자체 검토 요청** → 서버 독립 검사(`TextAiGateway` · `ScenarioContentPolicy` · 금지 표현 · 중복 지문 · 기회 일치). 생성 응답 안의 자기 평가만으로는 통과시키지 않는다 (C §5.1, A §7.4).
- **FR2.2** 자체 검토 결과는 `APPROVE` / `REJECT` / `UNCERTAIN`과 승인된 사유 목록(J7 항목 `ANSWER_INCLUDED` · `EARLY_CUE` · `PRESSURE`를 포함)으로 받는다. `REJECT` · `UNCERTAIN` · 응답 누락 · 스키마 실패 · 시간 초과는 승인으로 보지 않는다. `APPROVE`여도 서버 검사에 실패하면 막는다 (C §5.1 · §8.3).
- **FR2.3** 반려되면 허용된 횟수 안에서 다시 생성하고, 그래도 실패하면 기존 `SCENARIO_GEN_FAILED` 처리로 끝낸다. 반려된 상황은 발급 · 노출 · 재생하지 않는다 (C §5.1).
- **FR2.4** 생성 결과에 새 연습 흐름이 쓰는 대본 필드를 더한다: 장면 설명 · 상대 역할 · 기회 문장 · 상황 다시 설명 · 집중 연습 요점 · 표현 예시 · 변형 장면, 장면마다 관계 · 자리 · 화제 (B §9.3, 가정 6).
- **FR2.5** U5a 전체 시간 예산 15초(생성 + 자체 검토 + 서버 검사 + 재생성)를 늘리지 않는다. 실측해서 넘으면 대안(미리 생성 · 캐시 등)을 보고한다 (C §5.1).
- **FR2.6** Luna 상황 생성물과 자체 검토 결과는 제브로 보내지 않는다 (C §2 · §3.1, 가정 1).

### FR3. 진행 중 판정 J1~J6 (P2)

- **FR3.1** realtime-activity에 새 `JudgeClient` 포트를 두고 Luna를 부른다. 기존 `EvaluationProvider`와는 별개다 (A §5.8, C §0 · §4.3, 가정 4).
- **FR3.2** 판정 지점과 선택지는 A §7.3을 따른다.
  - J1 시작 응답: 참여 / 휴식 요청 / 거부 / 무관·불명확 / 판독 불가
  - J2 기회 문장 직후: 충분히 전달 / 일부 전달 / 도움 요청 / 상황 이해 못함 / 무관 발화 / 판독 불가
  - J3 되묻기 뒤: 전달됨 / 여전히 부족 / 도움 요청 / 판독 불가
  - J4 도움 동의: 수락 / 거절 / 불명확
  - J5 다시 해 보기: J2 선택지 + 코치 표현 그대로 따라 함
  - J6 종료 의도: 종료 명확 / 불명확 / 종료 아님 / 휴식 요청

  판정 질문 · 선택지는 버전 파일로 관리하고 세션 동안 고정한다 (A §7.3 · §7.8).
- **FR3.3** 판정 결과는 1 · 2순위와 확률로 받는다. 1순위 확률이 하한보다 낮거나 두 순위 차이가 작으면 판정 보류로 본다. 하한과 차이는 설정값이다 (A §5.8 · §7.3).
- **FR3.4** 제한 시간은 2초다. 시간 초과나 형식 오류는 재시도 없이 판정 보류로 본다. 판정 보류는 교정이 따르는 행동('일부 전달' 등)으로 바꾸지 않는다 (A §13, D ADR-005, 가정 4).
- **FR3.5** 기본 · 등록 종료 표현과 일치하면 판정 없이 종료 처리한다. 판정 턴 중 종료 표현이 나오면 판정을 멈춘다. 명시적인 도움 · 휴식 · 종료 요청은 서버가 바로 처리한다 (A §3.2 · §3.5, C §4.2).
- **FR3.6** 판정마다 진행용 판정 기록(`judgment_live`)을 남긴다. 담는 것: 판정 지점, 세션 · 목표 · 장면, 입력 전사 참조, 선택지 버전, 1 · 2순위와 확률, 보류 여부 · 사유, 걸린 시간, 다음 행동 지시, 보류된 출력 전사. 이 기록은 보호자 화면과 리포트에 쓰지 않는다 (A §7.3).
- **FR3.7** 다음 행동 지시에는 판정 라벨 · 확률 · 판정 기준을 넣지 않는다 (A §4.3, FR-F15).

### FR4. 유연한 연습 상태 기계 (P2)

- **FR4.1** 연습 진행은 A §4.3의 단계로 바꾼다: `SCENE_INTRO` → `OPPORTUNITY` → `REASK` → `HELP_OFFER` → `FOCUS` → `RETRY` → `SCENE_WRAP` → (선택) `VARIANT` → `NEXT_GOAL` / `CLOSING`. 도움이나 변형 장면을 반드시 거치지 않는다 (A §4.3, C §4.1, Q3).
- **FR4.2** 자연스럽게 되물어 해결되면 집중 연습을 강제하지 않는다. 예: "그거 줘" → "어느 색?" → "파란색" (C §4.1 · §8.2).
- **FR4.3** 상황을 이해하지 못하면 표현을 교정하기 전에 상황부터 쉽게 다시 설명한다. 무응답이면 1회 다시 안내하고, 그래도 없으면 그 장면은 미실시로 둔다 (A §4.3, C §8.2).
- **FR4.4** 집중 연습은 코치 역할로 바꿨다고 알리고 시작하며, 동의 뒤 표현 예시를 줄 수 있다. 친구 역할에서는 정답을 미리 말하지 않는다. 복귀할 때는 "다시 친구 역할로 돌아갈게"처럼 알린다. 기존 `CueProvider`의 전역 정답 예시 금지는 역할별 정책으로 나눈다 (A §4.3, C §4.3, 가정 5).
- **FR4.5** 변형 장면은 다음 조건이 모두 맞을 때만 제안한다: 쓸 수 있는 변형이 있고, 시간 · 참여 의사가 남았고, 목표당 10분(ACTIVE 시간) 전이고, 집중 연습이 길어지지 않았다. 10분이 되면 변형 없이 그 목표를 정리한다 (A §4.3 · §13).
- **FR4.6** 기존 `EvaluationProvider` · `ResponseEvaluator` · `CueProvider`는 새 흐름에서 떼어 낸다. 연결되지 않은 이 포트들 때문에 새 연습이 멈추지 않게 한다 (C §4.3 · §8.2).
- **FR4.7** 역할(친구/코치)과 제공한 도움(종류 · 내용 · 표현 예시 여부 · 동의 응답 · 시각)을 기록한다. 장면 노출 이력은 장면을 실제로 시작할 때 남긴다 (A §4.3).
- **FR4.8** 자유대화는 상태 기계 없이 GPT-Live 자동 응답으로 진행한다. J1과 J6만 판정한다 (A §4.3).

### FR5. 판정 턴 출력 보류 (P2)

- **FR5.1** 판정 턴에는 출력 게이트를 닫는다. 그동안 받은 GPT-Live 자동 응답 음성은 기기로 보내지 않고 버린다. 버린 출력 전사는 진행용 판정 기록에만 남기고, 대화 기록과 보호자 앱 중계에는 넣지 않는다 (A §3.2 · §3.3).
- **FR5.2** 판정 뒤 다음 행동 지시를 GPT-Live에 넣는다. 그 지시 뒤의 응답만 게이트를 통과한다. 지시 방식은 지금 선 형식(`session.instructions.correct` + `session.response.create`)을 쓴다 (Q5, 가정 7).
- **FR5.3** 아이 말이 끝난 뒤 10초 안에 응답이 준비되지 않으면 판정 보류로 보고, 무난한 되묻기나 맞장구를 지시한다 (A §3.2).
- **FR5.4** 판정 턴 중 음성 대화 장애가 나면 그 판정을 버리고 '장애 취소'로 기록한다. 제한 시간이 지난 뒤 온 전사 · 판정은 진행에 쓰지 않는다 (A §3.2).

### FR6. 제브 가드레일 — GPT-Live 새 발화만 (P3)

- **FR6.1** 제브용 새 포트를 둔다. 기존 `EvaluationProvider` · `GateDecision`과 섞지 않는다. 요청 출처는 `GPT_LIVE_GENERATED` 하나이고, 모드는 `FREE_TALK` · `PRACTICE_PEER` · `PRACTICE_COACH`다 (C §3.1, 가정 1 · 3).
- **FR6.2** 실제 어댑터는 A §5.7의 주소(`POST https://api.typesafe.ai/v1/systemone`)와 고정 모델 버전을 설정 기본값으로 둔다(`jev-latest` 금지). 키는 `JEV_API_KEY`, 제한 시간 기본값은 800ms다. 공급자의 실제 응답은 어댑터에서 내부 형식으로 바꾼다. 내부 형식: `decision` ∈ `ALLOW/BLOCK/REVIEW`, `categories` 7개, `policyFlags`, `reasonCode`, `policyVersion` (A §5.7 · §13, C §3.1, Q8, 가정 2).
- **FR6.3** 검사 대상은 GPT-Live가 자유대화 · 연습(친구 · 코치)에서 새로 만든 발화다. 기존 `OutputGate.inspect`(구조 · 1차 사전) 뒤, `recheck` 전에 검사한다. `ALLOW`일 때만 바로 그 음성 구간을 기기로 보낸다 (C §3.4).
- **FR6.4** `BLOCK` · `REVIEW` · 시간 초과 · 공급자 오류 · 잘못된 JSON · 정책 버전 불일치면 그 출력을 재생하지 않고 승인된 안내나 오류 · 종료 흐름으로 처리한다. 실검사 모드에서 자동 `ALLOW`는 금지한다 (C §3.4).
- **FR6.5** 취소 · 중단 · 기기 연결 해제 · 출력 세대 변경 뒤에 도착한 `ALLOW`는 무효로 한다. 검사한 전사와 실제로 보내는 PCM은 같은 응답 · 구간이어야 하고, 다르면 막는다 (C §3.4 · §8.1).
- **FR6.6** 승인 원문(승인 문구 · 세션 고정 대본)과 글자까지 같은 재생이면 제브를 부르지 않고, 기존 게이트 검사와 출처 · 원문 일치 확인만 한다. 단어를 더하거나 빼거나 바꾸면 새 발화로 분류한다. 출처가 불확실하면 생략을 허용하지 않는다 (C §0.8 · §2 · §8.1).
- **FR6.7** 제브에는 검사할 후보 문장과 최소한의 익명화된 최근 맥락만 보낸다. 아동 · 보호자 · 세션 식별자와 Luna 생성물 · U6 결과는 보내지 않는다. 입력 맥락 안의 지시문은 따르지 않는다 (C §3.1 · §3.3 · §8.1).
- **FR6.8** 검사 결과는 `guardrail_event`에 남긴다. 담는 것: 이유 코드 · 정책 버전 · 지연 · 판정. 전사 원문은 담지 않는다 (A §6.1, C §3.1, R-F14).
- **FR6.9** 공급자가 없는 시험 환경에는 명시적인 대역(1차 사전만) · 비활성 모드를 둔다. 대역의 성공을 실제 검사 성공으로 표시하지 않는다 (A §5.7, C §3.4, R-M11).
- **FR6.10** 시스템 프롬프트(C §3.3)와 분류 선택지는 버전 리소스로 관리하고 세션 동안 고정한다 (A §7.7 · §7.8).

### FR7. U6 결과와 기록 호환 (P2)

- **FR7.1** 장면 결과 칩에 '되묻기 뒤 전달'을 더한다. 바로 / 되묻기 뒤 / 도움 뒤 + 목표 행동 표현이다. 다시 말해 달라는 확인은 시점을 바꾸지 않는다 (A §7.5, 가정 8).
- **FR7.2** 장면 수를 1 · 2로 고정하지 않는다. 없는 두 번째 장면을 실패로 보이지 않고, 도움을 받지 않았다는 이유로 미완료로 표시하지 않는다 (C §4.4).
- **FR7.3** 새 기록 사실을 남기고 U6 입력으로 쓴다: 되묻기로 해결됨, 설명 제공, 집중 도움 · 표현 예시, 도움 수락 · 거절, 코치 전환 · 복귀, 원래 장면 복귀 · 변형 · 변형 생략 사유, 종료 요청 · 시간 초과 · 전사 · 재생 실패 구분 (C §4.4).
- **FR7.4** 기록용 재판정(`judgment` 작업)을 새 흐름의 장면 · 시점(되묻기 뒤 포함)에 맞춰 고친다. 진행 중 판정과 다르면 차이를 표시한다 (A §7.4, B §9.5).
- **FR7.5** 과거 U5b 결과는 버전으로 구분해 원래 의미대로 계속 읽는다 (C §4.4 · §8.2).
- **FR7.6** 결과 작업 재시도를 추가 최대 3회(5 · 15 · 30초)로 맞춘다 (A §7.6).
- **FR7.7** U6 결과 · 리포트의 2차 검사는 기존 Luna `classify` · `OutputChecker`를 유지하고 제브로 보내지 않는다 (C §5.2, 가정 1).

### FR8. 목표 후보를 Luna가 생성 (U6)

- **FR8.1** 목표 후보는 미리 정한 목록에서 고르지 않는다. Luna가 아이 기록(전사 · 경험 구조화 · 장면 기록)에서 후보를 만든다. 후보마다 추천 이유 · 근거 발화와 시각 · 목표 행동 표현 · 4요소를 담고, 4요소가 모두 있어야 후보가 된다. 근거가 부족하면 '후보 없음'으로 한다. 연령은 쓰지 않는다 (B §9.6, A §7.4, Q6).
- **FR8.2** 후보마다 그래프 씨앗 요약 목록에서 가장 가까운 씨앗(`skill_ref`, 없으면 `NONE`)을 붙인다. 서버는 `skill_ref`가 목록에 있는 id이거나 `NONE`인지 검증한다 (A §7.4 · §6.4).
- **FR8.3** 자유대화 뒤 `skill_ref`가 `NONE`인 후보로 새 씨앗을 만든다. 허용 값 · 개인 정보와 원문 겹침 · 금지 표현 · 중복 · 불변 문장 길이를 검사하고, 실패하면 1회 다시, 또 실패하면 `NONE`을 유지한다. 씨앗 생성이 실패해도 결과 상태는 바꾸지 않는다 (A §7.4 · §7.6, B §9.6).
- **FR8.4** 보호자 선택 없이 AI가 목표를 확정하거나 자동으로 담지 않는다. 기존 승인 행동 정의는 과거 기록 읽기와 안전 기준으로 남긴다 (C §5.2, 화면 설계 v1.5j).
- **FR8.5** 목표 후보 · 저장 목표 · 리포트 · 보호자 화면은 화면 설계 v1.5j의 해당 화면과 문구를 따른다. 화면 설계와 B가 다르면 화면 설계를 따른다 (CLAUDE.md, 가정 12).

### FR9. 지식 그래프 Neo4j (P4)

- **FR9.1** core-api에 Neo4j 어댑터를 둔다. 기능: 아이 그래프 초기화 · 씨앗 요약 목록 · 목표의 구조 맥락(`skill_context`) · 변형 계획 · 만든 씨앗 쓰기와 지우기. 모든 질의는 `child_id`로 범위를 한정한다 (A §6.4, Q10).
- **FR9.2** 공통 씨앗 · 어휘는 사람이 넣어 준 `aidlc/spaces/default/knowledge/social-comm-poc.zip`의 온톨로지 · Cypher 스키마 · 씨앗 자료에서 적재한다. 적재 스크립트와 그래프 버전(`KgVersion`)을 둔다 (A §6.4, Q7).
- **FR9.3** 그래프에는 원문 전사 · 보호자 입력 원문을 넣지 않는다. 원문과 세션 출처는 PostgreSQL에만 둔다 (A §6.4, C §6.3).
- **FR9.4** 아동 · 계정 · 기록을 지우면 그 아이의 그래프와 만든 씨앗도 지운다. 기존 삭제 참여자 구조에 그래프를 더한다 (A §6.5).
- **FR9.5** 그래프가 꺼져 있거나 장애 · 시간 초과(2초)일 때, 또는 `skill_ref=NONE`이면 구조 맥락 없이 기본 상황 생성이 안전하게 동작한다. 빈 그래프 응답을 '지식 기반 개인화 완료'로 표시하지 않는다 (A §6.4 · §13, C §6.2).
- **FR9.6** 그래프 맥락이 있으면 변형 장면 보존 판정을 한다: 기본 장면의 불변 문장 · 보존 조건 충족, 같은 기술 판정, 전이 거리, 바뀐 요소. 실패하면 A §7.4의 재생성 규칙을 따른다 (A §7.4, B §9.3).
- **FR9.7** 시험 · 개발용 메모리 대역을 둔다 (A §6.4 · §11.2).

### FR10. 승인 콘텐츠와 버전 고정

- **FR10.1** 판정 지점(J1~J7) 질문 · 선택지와 가드레일 질문 · 분류 · 시스템 프롬프트를 버전 리소스로 관리한다. 세션을 시작할 때 버전을 세션 계획에 고정한다 (A §7.8, C §3.3).
- **FR10.2** 승인 문구 · 세션 고정 대본은 출처 · 버전 · 원문과 함께 보관해, FR6.6의 원문 일치 확인에 쓴다 (C §2).

### FR11. 계약 · 설정 정비

- **FR11.1** 판정 시간 값을 두 앱 `application.yml`의 `mujoong.timing.*`, `contracts/timing.md`, `frontend/src/shared/timing/timing-defaults.json`에서 같은 커밋으로 함께 고친다(R-M5). 대조 시험(`TimeLiteralScanTest` 등)을 통과해야 한다.
- **FR11.2** `contracts/ai-io.md`에 새 포트(Luna 판정 · 자체 검토 · 제브)의 입출력 계약과 금지 필드를 적는다. 바뀐 오류 코드는 `ErrorCode`와 `contracts/errors.md`에 함께 더한다(R-M6 · R-M10).
- **FR11.3** 새 비밀 이름(`OPENAI_API_KEY` · `JEV_API_KEY` 등)을 비밀 이름 검사 목록 전부(`ci.yml` 번들 검사, `infra/ci/image-checks.sh` 등)에 같은 커밋으로 더한다(R-M9).
- **FR11.4** DB 변경은 새 번호 마이그레이션(core V8~, realtime V5~)으로만 한다. 기존 표의 제약을 강화하면 `infra/migration-approvals.txt`에 근거를 적는다(R-M2 · R-M3).

### FR12. 실호출 · 실기기 검증 (P5)

- **FR12.1** Luna · 제브 실제 어댑터를 합성 자료로 제한된 실호출로 검증한다. 키는 사람이 이 PC의 환경 변수로 넣는다. 결과는 테스트 대역 · 합성 대화 · 실제 API로 나눠 보고한다 (Q4 · Q8, R-M11 · R-F13 · R-F15).
- **FR12.2** GPT-Live도 같은 조건으로 실제 연결을 확인한다. 확인한 선 형식에 맞춰 코드 · 가짜 공급자 · 시험(u1~u4b)을 한 번에 고친다. 키 이름 통일(`PROVIDER_API_KEY` → `OPENAI_API_KEY`)도 이때 정한다 (Q5, A §5.6).
- **FR12.3** 실기기 검증 절차와 확인표를 만든다. 실제 기기 실행은 사람이 하고 결과를 기록으로 넘긴다. 개발은 기기 시뮬레이터 끝-끝(`bash scripts/verify.sh`)까지 책임진다 (Q9).
- **FR12.4** 실호출 · 실기기 결과에 따라 남은 미구현과 실패를 보고서로 남긴다 (C §7 P5).

  - Luna 자체 검토 실패
  - 서버 검사 실패
  - 판정 보류

  - 제브: 출처별 호출 수(새 발화 / 원문 재생 생략), 지연, 차단 · 시간 초과 비율
  - 판정: 보류율 · 지연

- **NFR6 호환:** 과거 기록 · 결과 · 리포트를 원래 의미대로 읽는다. 기존 계약 · 동의 · 삭제 · 재생 증거(`PLAYBACK_MARK`)를 유지한다 (C §4.3 · §4.4).
- **NFR7 운영 격리:** 사용자의 수동 테스트 스택 `mujoong-manual`과 그 볼륨을 건드리지 않는다. 검증은 별도 Compose 프로젝트(`mujoong-verify`)로 한다 (R-F12).
