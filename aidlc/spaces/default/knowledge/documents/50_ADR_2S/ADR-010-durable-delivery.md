① 개정: Core/Realtime의 내부 HTTP 즉시 명령과 Broker 없는 Outbox/Inbox 영속 전달, 멱등·커밋 후 ACK·앱별 복구 계약을 신규 ADR로 정리했다. 문서 연결의 현재 완료 상태를 정리했다.
② 대체: 단일 프로세스의 결과 요청/완료 호출과 영속 기록 없는 단발 HTTP는 대체된 이전 선택/미채택 대안으로 남기고, v0.2 영속 전달 방향을 적용했다. 문서 반영을 아직 예정으로 적은 표현은 현재 상태로 대체했다.
③ 남은 TBD: 스키마·필드·Endpoint/DTO·내부 인증, 선점/lease·순서·재전송/보존 한도, 철회 경합 원자성과 장애/중복·실제 복구 시험. 문서 연결 완료와 구분해 유지한다.

# ADR-010 앱 간 영속 전달

- 상태: **Proposed**. 내부 HTTP + Transactional Outbox/Inbox, Broker 없음은 audit와 v0.2를 적용한 현행 방향이다. API·물리 스키마·구현·운영 검증 완료를 뜻하지 않는다.
- 관련: [ADR-002 기술 기본값](ADR-002-technology-defaults.md), [ADR-005 세션 이벤트·복구](ADR-005-session-events-timeouts.md), [ADR-007 모듈 경계](ADR-007-module-boundaries.md), [ADR-008 인증·접근 제어](ADR-008-auth-access-control.md), [통신 계약](architecture/protocol.md), [데이터 모델](architecture/data-model.md), [결과 파이프라인](architecture/result-pipeline.md)
- 개정 기준: `ref/mujung-architecture-update-audit-v1.1.md` §2·§3·§7·§8. 보조 근거는 `ref/2-spring-architecture-v0.2.md` §§2·4~10과 `ref/2-spring-cross-validation-v0.2.md` CV-02~04·07~10·14다.
- 문서 범위: 앱 간 영속 전달의 맥락·결정·대안·결과. 실제 메시지 형식은 protocol, 데이터 참조는 data-model, 결과 실행·체크포인트는 result-pipeline이 상세화한다.

## 1. Context

Core API Spring과 Realtime Activity Spring은 실행 특성·상태 소유권에 따라 분리한 두 실행 앱이다. Core가 ResultJob·결과·리포트를, Realtime이 ActivitySession·목표 등록·연습·판정을 변경한다. Result Worker는 Core 내부이고 Outbox Sender와 Inbox Processor도 각 소유 앱 내부 작업이다.

같은 PostgreSQL 물리 1개를 사용해도 다른 프로세스의 Repository나 업무 테이블을 직접 수정해서는 안 된다. 단일 Spring 안에서 사용한 메서드 호출·일반 프로세스 내부 이벤트만으로 요청과 완료 사실을 다른 JVM에 전달할 수 없다. 한쪽의 업무 커밋과 상대 전달 사이에 장애가 생기거나 응답이 유실되어도 복구할 기록이 필요하다.

필요한 통신에는 서로 다른 수명이 있다.

- 활동 시작·종료·준비 취소와 현재 상태 조회는 즉시 명령/조회 계약이 필요하다. STOP을 사후 결과 대기열 뒤에 넣지 않는다.
- 유실되면 안 되는 결과 요청·완료·정책 변경 사실에는 영속 기록과 재전달·중복 처리 계약이 필요하다.
- 결과를 생성하는 AI 호출, 상대 앱의 영속 수신, 업무 반영, 기기 실제 재생은 서로 다른 사실이다. 하나의 ACK로 묶으면 잘못된 완료와 재실행을 만들 수 있다.

이 ADR은 audit가 요구한 v0.2 영속 전달 결정을 문서화한다. 전송 성공·독립 가용성·정확히 한 번의 외부 AI 실행을 실증한 문서가 아니다.

## 2. Decision

### 2.1 두 전달 경로와 실행 소유권

| 경로 | 대상 | 현행 계약 |
|---|---|---|
| 인증된 내부 HTTP 즉시 명령/조회 | 활동 생성·종료·준비 취소, 현재 상태/허용 자료 조회, 원격 목표 등록 | 짧은 접수·중복 판별·같은 요청 재확인. STOP은 우선 처리 경로에 둔다. |
| Transactional Outbox + 내부 HTTP Sender + 영속 Inbox/수신 멱등성 | 유실되면 안 되는 작업 요청·완료·정책 변경 사실 | 발신 업무와 Outbox의 로컬 커밋, 영속 수신 후 ACK, 미처리 복구와 같은 업무 효과 중복 방지. |

**초기 Broker는 추가하지 않는다.** Outbox는 업무 변경과 전달 의도를 함께 기록하는 패턴이고 Broker는 선택적 전송/보관 인프라다. 동급 대체 기술로 표기하지 않는다. 향후 Broker를 검토하더라도 쓰기 소유권·멱등·현재 권한·자료 보존 계약은 유지해야 한다.

Sender/Processor와 Core Result Worker를 세 번째 상시 Spring으로 분리하지 않는다. 앱 내부 실행 경로에서 동시 실행을 제한하고, 메모리 대기열을 영속 요청의 유일한 보관소로 사용하지 않는다. 큐/풀·송신량·병렬 처리의 실제 한도는 TBD다.

### 2.2 PostgreSQL·스키마·쓰기 소유권

PostgreSQL은 물리 1개를 유지하고 Core와 Realtime의 소유 스키마·DB 역할·쓰기 권한을 분리한다. 각 앱은 자신이 발신하는 Outbox와 수신하는 Inbox를 소유한다. Core는 Realtime의 ActivitySession·목표/연습 테이블을 직접 수정하지 않으며 Realtime도 Core의 Job·결과 테이블을 직접 수정하지 않는다.

상대 자료는 공개 Query/등록 계약으로 다룬다. 읽기 전용 View 등 예외는 허용 필드·권한·스키마 결합을 별도 설계한다. 물리 DB가 같다는 이유로 두 앱의 업무 변경을 하나의 앱 간 트랜잭션으로 처리하지 않는다.

Flyway는 기존 채택이다. 앱별 스키마에 Outbox/Inbox·중복 판별·업무 참조의 변경을 반영하고, 배포의 단일 마이그레이션 단계/실행 주체와 각 앱의 호환 스키마 validate를 적용한다. 스키마명·DB 계정·권한·Migration 위치/이력·적용 순서·물리 제약은 TBD이며 [data-model.md](architecture/data-model.md)·[ADR-006](ADR-006-demo-deployment.md)에 문서 책임을 연결했다. 물리 설계·배포 구현과 검증은 미완료다.

### 2.3 발신: 업무 변경과 전달 의도의 원자 기록

1. 발신 앱이 자신의 업무 규칙·현재 권한·대상·버전을 확인한다.
2. 업무 변경과 해당 영속 이벤트의 Outbox 기록을 **같은 로컬 DB 트랜잭션**으로 커밋한다. 둘 중 하나만 저장되는 경로를 두지 않는다.
3. 앱 내부 Sender가 제한된 항목을 선점한다. DB 조회/선점 트랜잭션은 짧게 끝내고 내부 HTTP 전송은 트랜잭션 밖에서 수행한다.
4. 수신 ACK가 확인되면 발신 앱이 전달 상태를 영속 반영한다. 응답 유실·발신 앱 중단 등으로 상태가 불확실하면 같은 논리 이벤트를 재전달한다.

재전달할 때 이벤트 식별과 대상·내용의 논리적 동일성을 유지한다. 동일 식별자로 다른 내용을 새 메시지처럼 덮어쓰지 않는다. 상태명·Hash 표현·선점/lease·재전송 간격/횟수·재확인 방식은 TBD다.

수신 앱의 장기 장애·유효하지 않은 메시지·권한 변경을 전송 성공으로 채우지 않는다. 실패·보류·폐기 사유와 복구 가능한 전달 상태를 남긴다. 이 처리의 실제 상태/필드·운영 조치 계약은 TBD다.

### 2.4 수신: 영속 커밋 뒤 ACK

수신 앱은 서비스 인증, 이벤트 식별·내용 결합, 대상·버전·현재 이용 가능성을 검증한다. **업무 반영을 함께 커밋하거나 Inbox를 영속 저장한 뒤에만 수신 ACK를 보낸다.** 메모리 큐에 넣었다는 이유로 ACK를 보내지 않는다.

- 즉시 업무 반영이면 업무 변경과 같은 이벤트의 중복 판별/처리 기록을 하나의 로컬 트랜잭션으로 커밋한다.
- Inbox 후처리이면 우선 영속 수신을 커밋해 ACK하고, 내부 Processor가 업무 변경과 Inbox 처리완료 표시를 **같은 로컬 트랜잭션 또는 동등한 원자성 계약**으로 반영한다. 구체 방식은 TBD이며 둘의 분리 커밋으로 중복 효과를 허용하지 않는다.
- 같은 이벤트가 다시 오면 영속 수신/처리 사실을 확인해 같은 업무 효과를 반복하지 않는다. 미처리 Inbox는 소유 앱의 재시작 후 다시 처리한다.
- 동일 이벤트 식별의 내용 충돌, 잘못된 대상·버전·권한을 정상 중복으로 숨기지 않는다. 거부/보류 응답과 처리 사유 표현은 TBD다.

Inbox를 저장한 수신 ACK는 **처리 책임을 영속 수락한 사실**이다. 결과 준비·목표 등록·활동 전이의 업무 완료, 외부 AI 성공, 실제 기기 재생 완료와 구분한다. HTTP Status/ACK payload·업무 결과 재조회·완료 이벤트의 형식은 TBD다.

### 2.5 논리 식별자·중복·순서·최신성

아래는 v0.2 및 현행 protocol에서 이어받은 **논리 식별자**다. Java 클래스·wire 필드·DB 컬럼·새 API 확정이 아니다. 정확한 이름·필수 조합·수명·보존 기간은 TBD다.

| 논리 역할 / 기존 이름 | 검사 목적 |
|---|---|
| 요청 식별 `requestId` | 같은 상태 변경 요청의 재전송. 검증 주체·동작·대상·내용·기한과 결합하고 응답 유실 후 결과를 재확인한다. |
| 영속 이벤트 식별 `eventId` | 네트워크 재전달에서도 유지하는 하나의 이벤트. 같은 이벤트의 업무 효과 중복을 막는다. |
| 실시간 명령 상관/작업 식별, `activityOpId` / 기존 `opId` | 현재 대화·상황·Cue·판정 작업에 속하는지 확인한다. 명령 ACK 상관과 작업 최신성의 실제 필드 통합 여부는 TBD다. 종료·쉬기 등으로 효력이 무효화된다. |
| 결과 실행 `jobRunId` (`runId` 역할) | 사후 결과 실행 묶음을 구분한다. 이전 실행 완료가 현재 수동 재시도를 덮지 못하게 한다. |
| 목표 후보 `candidateId` + `inputVersion` | 같은 후보/입력으로 재등록할 때 성공 목표·버전/추천 참조를 재확인한다. |
| 권한·정책 `authorizationEpoch` / `policyVersion` | 동의·삭제·권한 변경 뒤 새 이용/반영의 현재성을 검사한다. 실제 원자성 방식은 TBD다. |
| 순서·상태 `streamVersion` / `expectedStateVersion` | 상태 경합·순서 역전을 판별한다. 이벤트 중복 제거와 별도다. |

같은 이벤트인지, 업무 요청이 같은지, 지금 유효한 작업인지, 기대한 결과 실행인지는 서로 다른 검사다. 전역 전달 순서·모든 메시지의 자동 정렬을 가정하지 않는다. 대상별 필요한 순서 범위, 버전 충돌·선행 자료 미수신·처리 불가의 보류/폐기 정책은 TBD다.

종료/쉬기로 실시간 작업 ID가 바뀌어도 허용된 사후 결과를 모두 버리지 않는다. Realtime은 기대한 결과 run·입력 버전·결과 대상·현재 자료 권한을 확인해 결과 참조를 연결한다. 이전 run이 새 결과를 덮거나 종료/`PARTIAL` 활동을 `ACTIVE`로 되살리지 못한다.

### 2.6 결과 요청·완료와 원격 목표 등록

**결과 요청:** Realtime이 결과를 만들 수 있는 종료 사실·유효 입력 참조·기대한 실행을 확인하여 결과 요청 Outbox와 자신의 결과 대기/참조 변경을 같은 로컬 트랜잭션에 기록한다. 정상 종료는 `ENDING` 및 정리 확인을 생략하지 않는다. 유효 기록의 중도 종료는 활동 `PARTIAL`과 결과 준비 상태를 구분한다.

**Core 수신·처리:** Core가 요청을 영속 수신하고 중복 없이 자신의 ResultJob을 생성/연결한다. Result Worker가 허용 입력을 조회하고 DB 트랜잭션 밖에서 생성·검사하며 성공 단계·산출물·등록 참조를 체크포인트로 남긴다. 같은 요청/이벤트의 재전달을 새 AI 생성 시도로 바꾸지 않는다.

**원격 목표 등록:** Core Worker가 생성·검사를 완료한 후보를 Realtime의 `practice` 공식 등록 계약에 내부 HTTP로 요청한다. Realtime이 현재 자료 허용·대상·중복·정의 버전을 검사하고 자신의 스키마에 등록한다. 등록 성공 뒤 응답 유실이면 같은 후보/요청으로 같은 목표·버전/추천을 재확인하며 완료된 AI 단계를 다시 생성하지 않는다. 두 앱 사이 단일 커밋을 가정하지 않고 Core 체크포인트와 Realtime 등록 멱등성으로 복구한다. 연습에서 사용 중인 목표 버전을 새 추천으로 덮지 않는다.

**완료/실패:** Core는 결과·Job의 완료/실패 변경과 완료 전달 Outbox를 같은 로컬 트랜잭션으로 기록한다. Realtime은 영속 수신 후 자신의 업무 계약으로 현재 run·입력·대상·권한을 확인해 참조/상태를 반영한다. 원본 후보 이름 `ResultReady`·`ResultFailed`와 자료 부족의 완료 표현은 메시지 계약에서 검증할 논리 이름이며 새 Endpoint·DTO를 확정하지 않는다.

유효 부분 결과는 기능 요구다. `PARTIAL` 결과가 준비돼도 정상 활동 완료나 `ACTIVE`로 바꾸지 않으며, 미참여·미저장 원문을 만들어 결과를 채우지 않는다. 자료 부족과 기술적 결과 생성 실패도 구분한다. 생성·승인·송신·수신 ACK를 실제 제공으로 계산하지 않고 Realtime이 검증한 전사·Cue·`playbackMark` 관측 참조 중 이용이 허용된 범위만 결과 근거로 쓴다. 상세 처리와 목표 4요소·첫/도움 후/새 상황 구분은 [result-pipeline.md](architecture/result-pipeline.md)가 보존한다.

### 2.7 재시도와 앱별 복구

| 종류 | 복구 원칙 |
|---|---|
| 전달 재시도 | 같은 요청/이벤트·내용으로 재전달/재확인한다. 수신 ACK 유실은 업무 중복이나 새 LLM 생성의 근거가 아니다. 실제 backoff·한도는 TBD다. |
| LLM 기술 재시도 | Core 결과 실행의 남은 자동 실행 한도와 성공 체크포인트를 따른다. SDK/Adapter 재시도를 포함한 실제 외부 요청 수를 숨기지 않는다. 기존 잠정값의 소유 문서는 result-pipeline이다. |
| 생성 내용 수정 | 기술 오류와 다른 내용 검사/수정 이력·누적 한도를 사용한다. 전달 재시도마다 수정 기회를 다시 부여하지 않는다. |
| 보호자의 수동 재시도 | 인증·소유권·현재 자료 허용과 새 결과 실행 묶음을 확인한다. 이전 실패·수정·성공 이력은 보존하고 이전 run의 늦은 반영을 막는다. Job 재사용·수동 한도는 TBD다. |

각 앱은 자신의 미완료 Outbox/Inbox만 복구한다. Core는 자신이 소유했거나 lease가 만료된 미완료 ResultJob을 남은 한도·체크포인트·현재 run과 권한으로 재선점한다. 복제본 기동 때마다 모든 `RUNNING` Job을 `PENDING`으로 초기화하지 않는다. 재선점의 generation/fencing으로 오래된 Worker의 DB 반영을 막는 계약이 필요하며 실제 필드·선점/lease·만료·복구 시점은 TBD다.

Core 재시작은 정상 Realtime ActivitySession을 일괄 오류로 바꾸지 않는다. Realtime은 자신이 소유한 진행 중 음성 활동에 [ADR-005](ADR-005-session-events-timeouts.md)의 오류 정리 정책을 적용하며 기존 실시간 음성 활동을 자동 재개하지 않는다. 종료된 결과 대기/`PARTIAL` 참조와 영속 Inbox는 보존한다. 릴레이 메모리 버퍼를 복원된 것으로 보거나 미확인 기기 재생을 성공으로 채우지 않는다.

| 장애 시점 | 요구되는 복구 사실 |
|---|---|
| 발신 업무/Outbox 커밋 전 장애 | 미커밋 업무 변경·메시지를 완료로 보지 않는다. 원래 요청의 접수 사실을 재확인한다. |
| Outbox 커밋 후 전송 전 발신 앱 장애 | 영속 미전달 Outbox에서 다시 선점/전달한다. 업무를 새로 만들지 않는다. |
| Inbox 커밋 전 수신 앱 장애 | 영속 수신 ACK를 보내지 않는다. 발신자가 같은 이벤트를 재전달한다. |
| Inbox 커밋 뒤 ACK 유실 | 같은 이벤트 재전달을 중복 수신으로 처리하고 기존 영속 수신 사실을 확인한다. |
| Inbox 커밋 뒤 업무 후처리 전 장애 | 미처리 Inbox를 복구한다. 업무 변경·처리완료의 원자성을 지킨다. |
| 업무 반영 뒤 같은 이벤트 재수신 | 처리 기록을 확인해 같은 업무 효과를 반복하지 않는다. |
| 이전 Worker/run의 늦은 완료 | 현재 소유/실행·버전·권한 검사로 현재 산출물을 덮지 못하게 한다. 종료 활동은 부활시키지 않는다. |
| DB·상대 앱 장기 장애 | 상태 확정/전달 실패를 숨기지 않고 남은 영속 기록·안전 조치·미확인을 구분한다. 자동 성공을 보장하지 않는다. |

DB 선점·조회·저장 트랜잭션을 HTTP/LLM 대기 동안 유지하지 않는다. Sender/Worker 포화가 WS·활동 상태 처리 스레드에 긴 작업을 넘기지 않도록 실행 경로를 분리한다. `SKIP LOCKED` 등은 검토할 선점 도구이지 멱등·복구 전체를 제공하는 큐 제품으로 보지 않는다. 실제 구현 도구와 실행 한도는 TBD다.

### 2.8 서비스 인증·현재 인가·철회

내부 HTTP와 영속 이벤트 수신 모두 수신 앱의 서비스 인증을 적용한다. 내부망 자체나 브라우저가 넣은 주체 Header를 신뢰 근거로 승격하지 않는다. 내부 경로는 공개 진입을 차단하고 수신 인증도 유지한다. 구체 인증 방식·비밀 주입/회전·Endpoint/DTO·기한/크기 한도는 TBD다.

Core가 검증한 주체·허용 행위·대상·기한을 전달하고 Realtime은 자신의 활동/기기/주체 결합과 현재 권한을 대조한다. 서비스 인증이나 eventId 지식만으로 사용자 인가를 충족하지 않는다. 개인정보를 담는 Inbox의 새 저장 자체도 현재 이용 허용을 검사하며, 수신 시 확인한 권한을 나중 업무 처리의 영구 허가로 쓰지 않는다.

Core는 동의 변경과 철회 이벤트를 같은 로컬 트랜잭션에 기록해 우선 전달한다. **Outbox 알림만으로 즉시 철회 반영이 보장되지는 않는다.** Realtime과 Core Worker는 새 처리·외부 요청·저장·결과 반영 전 현재 이용 가능성을 검사하고 확인 불가이면 새 이용을 보류·차단한다. STOP·안전 정리를 동의 재확인 실패 때문에 막지 않는다.

철회 효력 시각과 확인/저장/송신 사이 경합은 단순 조회 후 INSERT만으로 해결됐다고 보지 않는다. 동일 DB 권한 fence 또는 동등 원자성 계약, 진행 중 AI/음성 취소의 효과는 G-03 후속 설계·실연동 대상이다. 자료가 보존되어 있다는 사실만으로 새 분석·열람·전달을 허용하지 않는다. Core 장애 중 보호자 직접 Realtime 종료 경로(G-02)는 미해결 대안이며 이 ADR에서 채택하지 않는다.

### 2.9 최소 메시지와 보존·삭제

이벤트는 필요한 식별·버전·최소 참조로 구성하고 전사/보호자 원문을 무조건 복제하지 않는다. 전사 스냅샷·Outbox/Inbox·Job 체크포인트·로그도 동의·보존·삭제 정책의 대상이다. 상대 앱 조회 실패를 핑계로 이용 불가 자료를 메시지에 추가하지 않는다.

**실시간 중계 원음은 임시 메모리에서 사용·폐기하고 Outbox·Inbox·DB·일반 로그·디스크에 우회 저장하지 않는다.** 검사/음성 구간/전사/재생 참조는 raw audio 영속 보관을 뜻하지 않는다. 기존 승인 안내 음성 파일과 실시간 원음을 같은 보존 범위로 묶지 않는다.

삭제/철회 뒤 재전달이 파생 결과·추천·원문을 복원하지 않게 현재 정책/폐기 표식을 확인한다. 메시지보다 중복 제거 기록을 먼저 삭제해 재실행이 발생하지 않도록 보존 기간을 함께 설계한다. 실제 보존 기간·자료별 폐기 표식·정리 순서·최소 기술 처리 기록·D-08의 이전 자료 보존/열람 정책은 TBD다.

개인 운영 데이터와 Core의 공통 지식 경계를 유지한다. Neo4j는 공통 화용 지식 관리/조회 경계로 유지하며, 영속 전달을 이유로 삭제하거나 개인 전사·원음의 전달 저장소로 쓰지 않는다.

## 3. Reason

- 업무 커밋과 전달 의도의 원자 기록으로 발신 앱 중단 뒤에도 미전달 사실을 찾을 수 있다.
- 영속 수신 후 ACK와 Inbox 후처리 복구로 수신 앱 중단·응답 유실을 다룬다.
- 재전달과 업무 멱등성을 함께 사용해 네트워크 중복을 허용하면서 같은 효과의 반복을 막는다.
- 즉시 명령을 사후 결과 작업과 분리해 STOP이 긴 AI·전달 대기를 기다리지 않게 한다.
- 기존 PostgreSQL과 두 앱 내부 실행 경로를 사용하여 초기 Broker·세 번째 상시 Spring 운영을 추가하지 않는다.
- 실시간 작업, 결과 실행, 정책 현재성을 구분하여 유효 사후 결과를 반영하면서 활동 부활·철회 자료 복원을 막는다.

## 4. Alternatives와 대체된 이전 선택

### 대체된 이전 선택. 단일 프로세스의 결과 요청·완료 호출

원본 result-pipeline과 ADR-007은 같은 Spring 안의 요청 Port·완료 이벤트 진입점으로 결과 책임을 분리했다. 당시에는 같은 프로세스에서 호출 가능한 경계였다. 두 실행 앱 전환으로 앱 간 내부 HTTP·Outbox/Inbox 계약이 이를 대체한다. 모듈 소유권·상대 Repository 직접 수정 금지·완료 사실의 순차 반영은 보존한다. 일반 프로세스 내부 이벤트를 다른 JVM 전달 방식으로 그대로 쓰지 않는다.

### Alternative A. 영속 기록 없는 단발 내부 HTTP — 미채택

구현이 단순하지만 발신 업무 커밋 후 요청/완료 전송 실패, 수신 반영 후 응답 유실, 재시작 시 미처리 사실 복구를 충분히 설명하지 못한다. 즉시 HTTP 자체는 채택하며 유실되면 안 되는 사실에는 Outbox/Inbox·멱등 기록을 결합한다.

### Alternative B. 초기 Broker 도입 — 미채택

전송/완충 인프라를 추가할 수 있으나 초기 운영 요소와 장애 경로가 늘어난다. 현재 기본값은 Outbox+HTTP+영속 수신이다. Broker만 추가해 업무 커밋과 전달 의도의 원자성·수신 중복·권한/보존·연결 소유권이 해결되는 것으로 설명하지 않는다. 측정한 처리량·운영 필요에 따른 재검토는 별도 결정이다.

### Alternative C. 공용 Repository/상대 스키마 직접 수정 — 미채택

물리 DB가 하나여서 가능해 보이지만 각 앱의 업무 불변식과 쓰기 소유권을 우회한다. ActivitySession·목표는 Realtime, ResultJob·결과는 Core가 자신의 계약으로 변경한다.

## 5. Consequences

### 장점

- 각 앱의 영속 미처리 사실과 복구 책임이 명확하다.
- 수신 ACK·업무 완료·AI 호출·실제 제공 범위를 구분한다.
- 원격 목표 등록/결과 전달에서 성공 체크포인트와 멱등 재확인을 연결할 수 있다.
- Broker 없는 초기 두 앱 구조와 기존 PostgreSQL/Flyway를 유지한다.

### 단점

- Outbox/Inbox·선점·재전달·중복·상태 경합·처리 사유·보존을 직접 구현하고 관측해야 한다.
- 양 앱의 DB 풀·실행기·Worker·송신 부하가 같은 DB/호스트 자원을 경쟁한다.
- 앱 간 업무가 하나의 원자 커밋이 아니므로 영속 수신 이후에도 업무 대기·실패·부분 성공이 남는다.
- 현재 권한 확인의 Core 의존과 철회·저장/송신 경합, 외부 AI 중복 호출의 비용 가능성이 남는다.

## 6. Risks

### ACK를 완료로 해석

영속 수신 ACK 뒤 Inbox 미처리·업무 거부·결과 생성 실패가 가능하다. 전달 상태와 업무 결과/기기 실제 관측을 분리해야 한다.

### 중복 제거만으로 최신성을 보장

서로 다른 이벤트가 이전 run·삭제 정책·오래된 작업을 참조할 수 있다. 식별자 중복 검사와 대상·버전·현재 권한 검사를 함께 적용한다. 결과 run과 실시간 op 수명을 혼동하지 않는다.

### 원자성·복구를 문구로만 확정

업무 변경/Outbox, 업무 반영/Inbox 처리완료, 결과/완료 Outbox의 실제 트랜잭션 경계와 장애 시험이 필요하다. 영속 기록이라는 이름만으로 유실 방지·외부 AI 정확히 한 번 실행을 보장하지 않는다.

### 전달 적체·보존과 정책 변경

장기 장애의 재전달 적체, 정책 변경 후 새 저장, 삭제 후 재전달 복원, 중복 제거 기록의 조기 삭제를 다룬다. 개인정보 최소화와 복구 가능한 기술 기록의 보존 계약은 실제 정책 설계가 필요하다.

## 7. First Bolt·후속 영속 전달 검증

아래는 미실시 시험 계획이다. 첫 볼트의 작은 연결 흐름과 후속 전체 결과 구현의 범위를 구분하며, 합성·성인 역할극 자료로 장애를 재현한다. 전체 부분 결과 기능 요구를 첫 구현 미구현으로 삭제하지 않는다.

- [ ] 발신 업무/Outbox 중 하나만 커밋되는 경로가 없고 커밋 후 송신 전 장애를 복구한다.
- [ ] Inbox 커밋 전에는 ACK하지 않으며, 커밋 직후 수신 앱 중단과 ACK 유실을 재현한다.
- [ ] 동일 이벤트 재전달·동일 ID 내용 충돌·순서 역전에서 업무 중복과 잘못된 상태 반영을 막는다.
- [ ] Inbox 미처리 복구와 업무 반영/처리완료 원자성을 검증한다.
- [ ] Core 결과/Job 변경과 완료 Outbox를 함께 커밋하고 Realtime이 현재 run만 연결한다.
- [ ] 원격 목표 등록 성공 뒤 응답 유실을 같은 후보로 재확인하고 성공 AI 단계/목표를 중복 생성하지 않는다.
- [ ] 전달·LLM 기술·내용 수정·수동 재시도를 별도 이력으로 구분하고 재시작이 한도를 초기화하지 않는다.
- [ ] Core/Realtime 각각 재시작·오래된 Worker 완료·lease 재선점에서 소유권과 이전 실행 차단을 확인한다.
- [ ] 종료/`PARTIAL`의 유효 결과 참조는 유지하고 늦은 결과로 활동을 부활시키지 않는다.
- [ ] 철회/삭제·현재 권한 확인 불가·내부 인증 실패·공개 내부 경로 접근을 거부하고 안전 정리는 허용한다.
- [ ] Outbox/Inbox/체크포인트/로그에 원음·불필요 원문·비밀이 저장되지 않고 재전달이 삭제 자료를 복원하지 않는다.
- [ ] 생성/승인/송신·ACK·기기 `playbackMark`의 미확인/부분 관측이 결과 근거에서 구분된다.
- [ ] 송신·Worker 적체와 DB/상대 앱 장애에서 실패·보류·미확인·복구 사실을 관측한다. 목표 부하와 실제 한도는 TBD다.

현재 문서 작성·정합성 확인을 구현/운영 시험 통과로 기록하지 않는다.

## 10. Decision Summary

```text
Apps: Core API Spring + Realtime Activity Spring
Workers: Result Worker=Core 내부, Sender/Inbox Processor=각 앱 내부
DB: PostgreSQL 물리 1개, 앱별 소유 스키마·쓰기 역할, 기존 Flyway 보완
Immediate: 내부 HTTP 명령/조회, STOP 우선 경로, 같은 요청 재확인
Durable: 업무 변경+Outbox 로컬 커밋 → 내부 HTTP → 영속 수신 커밋 → ACK
Inbox: 업무 반영+처리완료 원자 반영, 미처리 복구, 같은 업무 효과 중복 방지
Broker: 초기 도입 없음
Identity: 요청/영속 이벤트/실시간 op/결과 run/입력·정책·상태 버전 분리
Result: Core Job/Worker/산출물 → 완료 Outbox → Realtime 현재 run 참조 반영
Goals: Core 생성·검사 → Realtime 공식 등록 HTTP, 동일 후보 재확인/체크포인트
Partial: 유효 기록이면 부분 결과, PARTIAL과 결과 준비 분리, 활동 부활 금지
Retry: 전달/LLM 기술/내용 수정/수동 실행 분리, 이전 성공·실패 이력 보존
Recovery: 각 앱 소유 미처리 복구, lease/이전 실행 차단 상세 TBD
Policy: 내부 서비스 인증+현재 사용자 인가, 철회 알림만으로 즉시 반영 보장 안 함
Privacy: 최소 참조·삭제/보존 검사, 실시간 원음 영속 저장 없음
Evidence: 검증된 실제 제공 범위 사용, ACK/송신을 실제 재생으로 바꾸지 않음
Status: 방향 적용, 구현·운영·장애/부하 실측 미검증; 상세 계약 TBD
```
