① 개정: PostgreSQL 물리 1개·Core/Realtime 앱별 스키마/쓰기 소유권과 기존 Flyway, 고정 ID 기기·활동 할당, Outbox/Inbox·결과 run 및 검사/음성/전사/playbackMark 참조를 반영했다. 문서 연결의 현재 완료 상태를 정리했다.

## 저장소와 공통 규칙

PostgreSQL은 **물리 1개인 주 운영 저장소**이며 Core/Realtime의 앱별 스키마·쓰기 계정/권한을 분리한다. 일반 운영 ID는 기존 UUID, DB 시간은 UTC, 사용자 화면 시간은 KST 기본값을 유지한다([ADR-002](../ADR-002-technology-defaults.md)). 고정 기기 ID의 실제 값/형식은 별도 TBD다. Neo4j는 **2026-10-01 화용 지식 그래프 저장소로 채택 확정**되었다. 개인 아동·활동·전사·평가·결과 기록은 PostgreSQL 운영 데이터로 관리하며 Neo4j를 개인 아동 기록 저장소로 사용하지 않는다. 지식 관계를 PostgreSQL Table과 `KnowledgeAdapter`로 다루는 안은 채택 전 검토했던 대안 이력으로 남긴다. Neo4j의 노드·관계·제약·초기 데이터·Adapter 세부는 후속 설계 대상이며 구현·검증 완료를 뜻하지 않는다. 테이블명, 컬럼명, 제약조건, 인덱스와 삭제·보존 정책은 이 논리 모델만으로 확정되지 않는다.

Flyway는 **기존 채택을 보완**한다. Core/Realtime 소유 스키마별 마이그레이션 책임을 정하고 단일 배포 단계/실행 주체가 변경을 적용한다. 각 앱은 자신에게 필요한 호환 스키마를 검증하며 JPA는 기존 `ddl-auto=validate`를 유지한다. 스키마명·역할/권한·마이그레이션 파일 위치·이력 테이블 분리 여부·적용 순서·실행 주체의 실제 구현은 TBD다. 두 앱이 동일 변경을 서로 경쟁해 적용하거나 상대 스키마를 자동 생성/수정하게 하지 않는다. **채택이 확정된 Spring Session JDBC의 버전에 맞는 framework Session/속성 테이블 스키마**도 Flyway로 관리한다(ADR-008). 이 문서에서 테이블명을 임의 확정하거나 `ActivitySession`으로 대체하지 않는다. 초기화·재실행·만료/Logout·재시작/직렬화 호환성을 첫 볼트에서 시험한다. 인증 Session ID는 활동 ID와 별개이며 인증 Cookie/Session 전체값을 활동 이벤트나 일반 로그에 저장하지 않는다.

### 앱별 쓰기 소유권과 조회 경계

상시 Spring 앱은 Core/Realtime 두 개이며 Result Worker는 Core 내부다. 아래는 앱 책임이며 물리 스키마명·SQL 권한표는 아니다. 공통 Entity·Repository·도메인 Service를 공유해 두 앱이 같은 테이블을 수정하는 방식으로 구현하지 않는다.

| 논리 자료 | 수정 소유 앱 | 상대 앱에서 사용하는 방식 |
| --- | --- | --- |
| Guardian·Google 계정 연결·Child·GuardianChild·Consent·framework Session | Core | Realtime은 내부 인증된 공개 계약으로 필요한 최소 주체/대상·현재 권한/동의를 확인 |
| 승인 콘텐츠 원본/버전·공통 지식 관리/조회 | Core | Realtime은 활동 준비 전에 허용된 승인 버전/참조를 확보·고정. Neo4j를 직접 개인 기록 저장소로 사용하지 않음 |
| Device 사전 시드 등록·VoiceClient 연결 관측·활동 점유/할당·ActivitySession·ActivityContext·SessionEvent | Realtime | Core 보호자 API는 허용 상태 조회/시작·제어 계약으로 위임. 보호자 상태 카드는 연결 관측과 서버 할당 사실을 구분 |
| Transcript·ConversationTurn·동적 목표 정의/버전·목표 목록/선택·Scenario/노출·연습 시도/응답·Cue·Evaluation | Realtime | Core Worker는 허용 Query와 원격 목표 등록 계약 사용. 상대 Repository/테이블 직접 UPDATE 금지 |
| ResultJob·추천 산출물/근거·Result·Report 및 Worker 체크포인트 | Core | Realtime은 영속 결과 요청, 기대 run 확인 후 완료 참조 연결. Core가 활동 상태를 직접 UPDATE하지 않음 |
| Outbox·Inbox·전달/수신 처리 정보 | 해당 발신/수신 앱 | 각 앱 로컬 트랜잭션과 복구 범위. 원음·불필요 원문을 메시지에 복제하지 않음 |

물리 PostgreSQL을 함께 쓴다는 사실은 쓰기 소유권이나 로컬 트랜잭션 경계를 합친다는 뜻이 아니다. 교차 조회는 공개 Query 계약을 기본으로 하며, 읽기 전용 View 등 예외는 허용 필드·권한·스키마 결합을 별도로 결정한다. 앱 간 물리 FK/삭제 순서·정합성 방식도 TBD다. Core와 Realtime이 공유 DB의 상대 데이터에 직접 쓰거나 분산 트랜잭션의 원자성을 가정하지 않는다.

Core의 승인 콘텐츠 버전은 Realtime 활동 준비에 확보하고 해당 활동에 고정한다. 실패 시 준비 실패/시작 거부로 처리하고 임의 인사를 생성하지 않는다. STOP·승인 마무리가 Core의 즉석 콘텐츠 조회를 기다리지 않도록 한다. 추가 KG 조회는 제한된 비동기 준비 경로이며 무거운 교육 판정·KG를 동기 음성 게이트에서 분리하는 것은 우리 설계 권고다.

### 보호자 소셜 계정 연결과 인증 저장

현행 로그인 공급자는 Google만이며 기존 Spring Session JDBC 채택은 유지한다. **`GuardianSocialIdentity`라는 이름과 아래 저장 구조는 논리 설계 제안**이며 확정 DDL은 아니다. `Guardian`과 Google 계정 연결은 Core의 `guardian` 모듈이 소유한다. `auth`는 제공자 인증 검증·Principal·내부 Session을 담당하고 `guardian` 공개 API/Port로 계정 조회·연결을 요청한다. 실제 Port 이름은 TBD이며 다른 모듈 Repository 직접 접근은 허용하지 않는다([ADR-007](../ADR-007-module-boundaries.md)). `Guardian`의 기존 내부 ID·활동 소유권·아동 관계는 계속 유지한다.

- 검증된 제공자 회원번호를 `(provider, provider_subject)`로 식별하고 내부 `guardian_id`에 연결한다. Google OIDC 연결의 검증된 `sub` 등 실제 선택한 인증 방식의 회원 식별자를 사용하며 구체 속성/매핑은 실연동 검증 대상이다. 식별자의 앱별 범위 차이를 고려하며 다른 앱/Client의 회원번호를 그대로 같은 사용자로 가정하지 않는다.
- 최초 소셜 인증 이후 우리 서비스의 보호자 가입/연결이 필요하다. 생성 시점과 재시도·동시 가입의 원자성, 서비스 동의/가입 완료 상태·가입 미완료 Context의 제한 권한·수집 프로필 필드·탈퇴/연결 해제 정책은 **TBD**다. 제공자 동의가 아동 활동의 필수 서비스 동의를 대신하지 않는다.
- 이메일은 제공/동의 여부와 변경 가능성을 고려한 Optional 프로필 후보다. 이메일 일치만으로 기존 보호자 계정을 자동 합치지 않는다. Google 계정 연결/교체·해제 과정에서 어떤 재인증을 요구할지는 **TBD**다. 복수 공급자 연결은 이전 모델의 후속 대안이며 현행 Google 범위에 추가하지 않는다.
- 자체 아이디·비밀번호 가입은 제공하지 않으므로 해당 가입용 Password/Password Hash·비밀번호 재설정 모델을 추가하지 않는다. 제공자별 Client Secret은 서버 설정/비밀정보로 관리하고 보호자 또는 활동 테이블에 저장하지 않는다.
- 제공자 Access/Refresh/ID Token을 항상 DB에 장기 저장해야 한다는 결정은 없다. 기본 로그인 이후 내부 Session을 사용하며, 제공자 API 호출·Refresh·연결 해제에 필요한 Token 처리/보존 여부와 Authorized Client 저장 방식은 목적이 확정될 때 정한다. Token 원문을 일반 로그나 활동 이벤트에 복제하지 않는다.
- Spring Session의 인증 Context·OAuth 요청 연관 정보 저장, 만료·Logout·재시작과 버전별 직렬화 호환성은 첫 볼트에서 검증한다. 정확한 framework 테이블/컬럼·인덱스는 선택 버전 스키마를 확인해 Flyway로 옮기고 이 논리 모델에서 임의 확정하지 않는다.

Google 앱 등록·Callback·실패/가입 흐름은 [protocol.md](protocol.md), 인증·동의·기기 분리 정책은 [auth.md](auth.md)를 따른다.

| 사전 시드 등록 | 허용 고정 ID와 사용 범위. 값/형식·시드 적용/철회·운영 인증 방식은 TBD다. 고정 ID는 비밀 자격증명이나 운영 인증의 증거가 아님 |
| 현재 VoiceClient 연결 | 등록 대상과 현재 WSS 연결의 결합·허용 Origin·heartbeat/기기 상태 관측·연결 교체/늦은 보고 구분. 기기가 보고하는 준비/재생 사실과 서버가 결정하는 점유/할당을 구분 |
| 활동 점유·할당 | 현재 허용 기기·유효 연결·점유·대상 활동/주체·현재 관계/동의 확인 후 Realtime이 원자 할당. 동일 시작 재전송으로 이중 활동/할당을 만들지 않음 |
| 보호자 상태 카드·시작 push | Core의 인가된 상태 조회 결과와 Realtime의 할당/기기 준비 사실을 결합. 시작 접수·push 수신 ACK·아동 참여는 별도 사실. 전체 문구/표시 상태/주기는 TBD |
| 재연결·재시작 | 연결 관측과 보존된 할당/활동 사실을 대조. 미확인 재생을 완료로 채우거나 종료 활동을 자동 부활시키지 않음. Realtime 재시작 후 메모리 음성 버퍼는 복원하지 않음 |

기기 허용·연결·점유·할당 검사는 유지하되 전역 가용 기기 개수만으로 다중 사용자 시작 정책을 만들지 않는다. 고정 ID 데모는 영구 보호자-아동-물리 기기 페어링을 확정한 것이 아니다. 운영 기기 인증·연결 교체/중복 상세는 후속 설계이며 제품 데모의 실제/Mock 범위도 별도 확인 항목이다. 보호자 Cookie/Session과 기기 식별을 섞거나 공급자 키를 브라우저에 저장하지 않는다.

## 영속 전달·결과 실행의 논리 정보

전달 기준은 [ADR-010](../ADR-010-durable-delivery.md), Wire 경계는 [protocol.md](protocol.md)와 맞춘다. **즉시 명령/조회는 내부 HTTP, 유실되면 안 되는 작업 요청/완료·정책 변경은 각 앱 Outbox/Inbox + 내부 HTTP**를 사용한다. Broker는 추가하지 않는다. 일반 Spring 이벤트나 메모리 큐는 다른 JVM에 대한 영속 전달 기록을 대신하지 않는다.

| 논리 정보 | 필요한 계약과 보존 범위 |
| --- | --- |
| 발신 Outbox | 자신의 업무 변경과 같은 로컬 트랜잭션에 송신 의도 기록. 동일 eventId·대상/종류·필요 최소 참조/버전·전송/재전송 사실을 연결. 원음/불필요 원문 금지; 물리 필드 TBD |
| 수신 Inbox·중복 방지 | 내부 인증·대상/정책·eventId 검증 후 영속 저장을 커밋하고 수신 ACK. 업무 효과를 동시 반영하거나 별도 처리 때 업무 상태와 처리 완료를 같은 로컬 트랜잭션으로 반영. ACK를 메모리 접수만으로 보내지 않음 |
| 요청/완료 참조 | Realtime의 결과 요청·기대 run과 Core ResultJob/산출물·완료 통지를 연결. 정상 결과의 RESULT_PENDING 전이 또는 PARTIAL의 결과 요청/기대 run 기록과 요청 Outbox는 해당 Realtime 로컬 트랜잭션으로 함께 저장 |
| `runId`(v0.2 jobRunId)·입력 버전 | 같은 사후 실행 묶음·허용 입력을 식별. 보호자의 새 수동 재시도는 별도 run; 생성 주체/전환 절차·물리 키는 TBD. 전송 재시도/같은 기술 재시도로 새 run을 무작정 만들지 않음 |
| 선점·소유권·lease/fencing | Core Worker/Sender 및 Inbox 처리의 제한된 선점/복구와 오래된 실행의 저장 차단을 연결. 소유자·lease·generation의 실제 필드/시간·원자 조건 TBD. 재시작 때 모든 RUNNING을 일괄 초기화하지 않음 |
| 정책/자료 사용 버전·폐기 표식 | 현재 동의/삭제/자료 이용 가능을 처리·외부 호출·등록·저장·결과 반영 전 재확인. 삭제된 원문을 지연 재전송으로 복원하지 않음. 효력 시각·경합 원자성은 G-03 TBD |

`eventId` 중복 제거는 업무 중복·상태 순서·권한 경합을 모두 해결하지 않는다. 동일 요청의 주체·행위·대상·내용/입력 버전을 대조하고, 결과 완료는 Realtime의 기대 run·입력 버전·결과 대상·현재 이용 가능을 확인한다. **종료로 실시간 `opId`가 무효화됐다는 이유만으로 정상 사후 결과를 전부 폐기하지 않는다.** 이전 run의 늦은 완료는 새 run을 덮지 않으며 결과가 도착해도 종료 활동을 ACTIVE로 부활시키지 않는다.

유효 기록이 있는 중도 종료는 활동 `PARTIAL`과 Core 결과 준비/실패를 별도로 관리한다. 부분 결과 완료는 참조를 연결하고 `PARTIAL`을 정상 활동 완료나 새 진행 상태로 바꾸지 않는다. 미참여·기록 없음·자료 부족·동의 철회·기술 실패는 존재하지 않는 전사/추천/능력 값을 채우지 않는다. 새 준비 상태 Enum/컬럼/API 이름은 이 문서에서 확정하지 않는다.

ResultJob의 성공 단계·허용 입력/모델/명세 버전·검사/등록 참조는 복구 체크포인트다. 전달 재전송, 기술 LLM 재시도, 내용 수정, 보호자의 새 수동 실행은 구분하며 기존 잠정 생성 횟수를 메시지 전송 횟수에 합치지 않는다. 각 앱은 자신의 미완료 Outbox/Inbox와 소유 Job을 복구한다. Core 재시작이 정상 Realtime 활동을 수정하지 않고 Realtime 재시작도 Core 결과 작업을 다시 생성했다고 가정하지 않는다.

Outbox/Inbox·스냅샷·로그·중복 방지 기록도 보존/삭제 정책 대상이다. 원문을 이벤트마다 복제하지 않고 허용된 ID·버전·최소 참조를 전달한다. 중복 방지 기록을 메시지보다 먼저 지워 재실행이 생기지 않도록 보존 기간과 폐기 확인을 함께 설계한다. 내구성과 재처리로 유실 위험을 줄이는 방향이며 영구 장애의 자동 성공이나 외부 AI 정확히 한 번 실행을 보장하지 않는다.

## 출력 검사·음성·전사·실제 재생 참조

기기↔Realtime WSS(음성·제어)와 Realtime↔GPT-Live API(`gpt-live-1`) 주 WebSocket 릴레이 B안의 데이터 경계다. 공급자 입력/출력 원음은 임시 메모리 처리 후 폐기하며 DB·Outbox·Inbox·일반 로그·디스크에 우회 저장하지 않는다. 논리 참조는 실제 음성 파일 저장을 뜻하지 않는다. 기존 승인 안내 음성 파일의 버전/경로는 별도 승인 콘텐츠 자료로 구분한다.

| 논리 관계 | 남겨야 할 사실과 한계 |
| --- | --- |
| 출력 구간 ↔ 대응 전사 | Realtime/미디어 Adapter가 출력 구간을 나누고 동일 음성과 공급자 전사 범위를 대응. 구간 경계·완료 기준·키·단위는 TBD. 짧은 쉼이나 큐가 빈 사실을 전체 질문 완료로 확정하지 않음 |
| 구간/전사 ↔ 검사 | 활동·현재 연결·권한·작업 최신성과 필요한 경량 의미 검사 결과/사유/버전을 연결. 형식/근거 검사·목표 후보 검사·아동 반응 평가와 구분. 필요한 메타데이터의 보존은 정책/물리 모델 TBD |
| 검사 ↔ 승인 ↔ 동일 음성 송신 | 미검사/전사 누락/대응 불명확·실패·시간초과 음성은 폐기하고 대체 안내 경로 사용. 승인된 바로 그 음성만 전달하며 전달 직전 재확인. 재생성한 음성은 새 검사 필요 |
| 취소/차단 ↔ 후속 회복 | 끼어들기·쉬기·종료·철회를 구분하고 서버 버퍼/기기 대기열 취소·늦은 승인 무효를 연결. 폐기 음성도 모델 맥락에 남으며 `session.instructions.append` 교정 ACK는 재생 승인이 아님. 후속 음성도 다시 검사 |
| 송신 ↔ `playbackMark` ↔ 제공 근거 | 기기 플레이어가 관측한 시작/진행/중단/완료 범위를 활동·현재 연결·구간/재생 참조와 대조. 송신·수신 ACK·생성 전사만으로 실제 재생/청취/이해를 확정하지 않음 |

검사 수행·통과는 전달 조건이다. 검사 모델이 모든 위험을 발견하거나 출력 전사가 정확하다는 보장은 아니다. 무거운 교육 판정·KG를 동기 게이트에서 분리하는 것은 우리 설계 권고이며 필수 검사를 생략하라는 뜻이 아니다. 구간/대응/검사기·버퍼 크기/시간·포화/대체 안내·재생성 한도는 TBD다. 미승인 원문을 교정 시스템 지시로 그대로 복사하지 않는다.

`playbackMark`는 기기→Realtime 앱 관측 계약이다. 논리 정보는 아래 차원을 필요로 하며 필드명/타입은 확정하지 않는다.

| 차원 | 데이터 계약 |
| --- | --- |
| 관측 주체 | 실제 플레이어를 관리하는 기기가 관측. 서버 추정·공급자 생성 완료와 구분 |
| 대상 식별 | 활동·현재 연결·앱 출력 구간/재생 대상과 결합. 공급자가 구간별 응답 ID를 자동 제공한다고 가정하지 않음 |
| 위치 단위 | 해당 대상의 관측 재생 범위/중단 지점. 시간·프레임·샘플 등 실제 단위 TBD |
| 송신 시점 | 시작/진행/중단/완료 등 필요한 보고 시점·주기는 TBD. 종료/끼어들기 보고와 연관 |
| 늦은 보고 | 구 활동/연결·구간을 대조하여 참고 가능한 실제 관측만 반영. 무효 승인·종료 활동의 출력/진행을 재개하지 않음 |
| 보고 불가 | 누락/대응 불명확·연결 단절·재시작 뒤 미확인을 보존. 재생 성공이나 정확한 제공 인용문으로 채우지 않음 |
| 활용 | 실제 제공 범위·Cue/도움 후 반응·무응답 기준·중단 근거·사후 결과에 사용. 첫 반응/도움 후/새 상황 구분과 판정 근거 제한 유지 |

기기 관측 범위 자체가 아동 청취/이해를 보증하지 않는다. 전사와 정확히 대응할 수 없는 부분 재생은 확인 가능한 범위·중단 사실과 불확실성을 보존한다. `playbackMark`를 GPT-Live에 그대로 보내면 미재생 맥락이 삭제된다고 가정하지 않으며 공급자 맥락 반영·실연동은 별도 TBD다. 원음 메모리 소멸 후에도 보존할 참조/최소 근거와 삭제 정책을 정하고, 재시작 후 음성 버퍼나 미확인 재생을 복원했다고 표시하지 않는다.

## 전사 조립과 Turn

**전사 공급원 결정은 [ADR-004 §2.14](../ADR-004-communication-voice.md#mvp-transcription)를 따른다.** 2026-10-01 팀 회의에서 MVP는 GPT-Live 전사만 사용하고 별도 STT·병렬 비교는 보류했다. 현재 논리 모델에 추가 STT 결과·두 전사 비교·검토 완료 Canonical Transcript를 필수 저장 대상으로 추가하지 않는다. 2026-10-02 보완에서도 이 결정을 유지하며 Cue의 생성 전사와 실제 제공 근거를 아래에서 구분한다. 다른 v0.4.2 참조 전체의 최신화는 별도 작업이다.


ADR-002 v10은 일반 STT의 `interim/final` 구조를 GPT-Live 전사 이벤트에 그대로 대입하지 않는다. 공급자 fragment/delta가 제공되면 `TranscriptAssembler`가 조각을 모아 화자별 발화를 조립하고 누락·중단 여부를 기록한다. `TurnGrouper`는 조립된 발화를 대화 Turn으로 연결하고 사용자·AI 발화의 관계를 보존한다. 저장이 허용된 참여 이후 구간은 가능한 한 raw delta 전체 대신 조립된 발화 단위를 저장한다. 클래스명·조립 계약은 후보이며 아래 미참여 미저장 규칙을 우회하지 않는다.

`assembly_status`의 v10 후보는 `COMPLETE`, `INTERRUPTED`, `AMBIGUOUS`이며, 실제 상태명과 분류 규칙은 **POC 후 TBD**다. `review_needed`는 공급자 confidence 한 값만으로 결정하지 않고 조립 실패·흐름 중단·Turn 연결 불명확 등 여러 품질 신호를 고려한다. 평가에 쓰는 구체 검수 기준은 동료 GPT-Live/AI 상세 명세에서 확정한다. 현재 `Transcript`·`ConversationTurn`의 공급원은 GPT-Live다. 별도 STT의 도입·비교 데이터 모델은 후속 재검토 대상이며, 그때에도 서비스의 발화·Turn 의미를 유지하는 확장안을 검토한다. 단일 전사 저장을 독립 검증 완료로 표시하지 않는다.

| 참여 확인 전 | 참여 판정에 필요한 일시 처리를 영속 전사 생성으로 연결하지 않는다. 시작 전 미참여로 종료되면 응답 원문을 저장하지 않고 종료 사실·시각만 보존한다. 원문이 이벤트 payload·일반 로그·실험 보고서에 우회 저장되지 않는지도 확인한다. 거부 관련 최소 로그 범위는 D-08이다. |
| 참여 확인 후 | 합의한 데모 보존 범위의 조립 전사와 필요한 상태 근거만 저장한다. 첫 볼트는 합성·성인 자료이며 저장 시험 전에 D-08·NFR-08 정책이 필요하다. |
| 중도 종료·기술 종료 | 종료 사유와 확보 기록을 구분한다. 중도 종료 이전 기록의 보존·삭제는 D-08이며 `PARTIAL`을 이유로 전사 전체를 무조건 보존하지 않는다. |
| 필수 동의 철회·늦은 자료 | 신규·지연 자료의 금지된 수집/이용/저장을 차단한다. 이미 수집한 자료의 판별·폐기·파생 데이터 정책은 D-08과 [auth.md](auth.md)의 경계에서 정한다. 처리·외부 요청·출력 승인/송신·저장·결과 반영 전 현재 이용 가능을 재확인하고 확인 불가이면 새 이용을 보류/차단한다. STOP/안전 정리는 허용 재확인 실패 때문에 막지 않는다. |

원문에 기록된 **v0.7.1 FR-F04**의 비충돌 MVP 범위는 전사 저장·불확실 구간 표시이며 **전사 수정 기능은 제외**한다. FR-F10에 따라 판독 불가·불확실 구간만으로 목표 행동 미관찰을 확정하지 않는다. 원본/수정본 버전 이력과 사람 검토 큐(FR-F16)는 현재 MVP의 미완료 필수 기능으로 두지 않고 후속 범위로 관리한다. 결과·추천이 사용한 발화 참조와 불확실 사유를 연결할 구체 필드는 TBD이며, 조립 상태가 `COMPLETE`여도 내용 정확도가 입증된 것은 아니다.

### 동적 목표 정의·근거·버전 — Proposed

최신 FR-C02·F06·F10과 기능명세 SYS-RECO-001의 정책은 **대화 근거로 목표를 정의하여 아동별 목록에 추가**, **4요소가 모두 있어야 연습 대상으로 사용**, **사람의 개별 승인 불필수**, **동일 행동의 정의 일관성**이다. 아래는 그 정책을 저장·추적하기 위한 논리 모델이다. 각 행을 별도 테이블로 만들거나 필드명을 그대로 채택하라는 확정 DDL이 아니다. 생성·검사·실패 처리의 Source of Truth는 [목표 생성 계약](result-pipeline.md#goal-generation-contract)이다.

| 논리 정보 | 저장·연결 원칙 |
| --- | --- |
| 아동별 목표 식별자 | 서버가 부여한 목표 ID와 대상 아동. 모델이 임의 생성한 ID·다른 아동의 개인 목표를 그대로 등록하지 않음 |
| 목표 정의 버전 | 행동 정의·기회 조건·상황 생성 조건·판정 기준의 4요소를 한 버전으로 연결. 사용한 버전은 불변으로 보존하고 변경 시 새 버전 생성 |
| 추천·근거 | 추천 이유와 현재/관련 과거 자료의 출처·원본 참조·구간. 아동 전사/보호자 입력을 구분하고 불확실 조립 상태를 추적. 원문을 여러 테이블·이벤트에 무조건 복제하지 않음 |
| 검사 결과 | 서버 형식/근거 검사와 별도 AI 의미 검토의 결과·이유·시각·사용한 모델/명세 버전 참조. `PASS/FAIL/UNCERTAIN`은 후보 공개 여부용이며 아동 반응 판정이 아님. 저장된 PASS가 정확성 보증을 뜻하지 않음 |
| 중복 확인·등록 참조 | 핵심 기능과 기회 조건이 동등한 기존 정의를 재사용한 관계와 해당 추천 근거. 이름 일치만으로 병합하지 않으며 애매한 후보는 공개하지 않음. 같은 등록 요청을 재처리해도 동일 목표·근거가 중복 생성되지 않게 식별 |
| 선택·실행 참조 | `PracticeGoalSelection` → 연습 계획/활동 → Scenario·PracticeAttempt → Cue·Evaluation·Result가 선택한 정의 버전을 추적. 구현에서는 불필요한 중복 컬럼 대신 관계로 연결 가능 |
| 작업 복구 정보 | 기술 실행 횟수와 내용 수정 횟수, 후보별 검사 결과, 등록/재사용한 정의 버전, 마지막 완료 단계. Worker 재시작·재선점으로 초기화하지 않음 |

**Realtime의 `practice`가 아동별 목표 정의·버전·목록·선택의 공식 등록/쓰기 진입점을 소유하고 Core의 `result`가 작업·추천 산출물·근거를 관리한다.** Core Worker는 생성/검사 성공 체크포인트 뒤 내부 HTTP의 원격 등록 계약을 사용하며 Realtime의 Repository를 직접 쓰지 않는다. 같은 후보/입력 버전·등록 요청으로 성공 후 응답 유실을 재확인하여 동일 목표·버전·근거를 중복 등록하거나 완료한 AI 단계를 재생성하지 않는다. 기존 result 소유 요청 Port/practice 구현 의존 방향은 원격 Adapter 경계로 보완하며 Endpoint/DTO·등록 원자성·물리 FK는 TBD다. [ADR-007](../ADR-007-module-boundaries.md)에 두 앱/원격 경계의 문서 반영을 완료했으며 위 구현 상세의 TBD는 유지한다.

개별 아동의 정의·버전·추천·근거·선택은 PostgreSQL에 저장한다. Neo4j는 공통 화용 지식을 관리하며, 생성된 개인 목표를 공용 지식으로 자동 승격하지 않는다. 공통 지식 참조나 정의명이 같다는 이유로 서로 다른 아동의 개인 자료를 합치지 않는다. 전체 그래프 완성은 생성 시험의 추가 선행 조건이 아니다.

정의 최신 버전의 등록만으로 진행 중 연습이나 과거 판정의 버전을 변경하지 않는다. 보호자 선택만으로 활동을 시작하지 않으며 시작 전에 소유권·자료 이용 가능·선택한 정의 버전의 사용 가능성을 확인한다. 선택한 정의 버전의 동일성은 서버가 유지하되, 그 4요소 전체나 판정 기준을 GPT-Live 대화 역할에 전달한다는 뜻은 아니다. 역할별 제한된 전달 정보는 [Cue 계약](protocol.md#cue-contract)과 FR-F15를 따른다.

근거가 부족하여 추천이 없는 정상 결과, 검사 실패/불확실 후보, 기술 오류, 이미 존재하여 재사용한 목표를 구별한다. 일부 후보만 통과하면 통과 후보의 등록 참조를 남기고 복구 때 재생성하지 않는다. 기술 재시도 **최초+추가 3회·5/15/30초**와 내용 수정 **작업 전체 누적 추가 1회**는 [result-pipeline.md](result-pipeline.md#goal-generation-contract)의 잠정 구현안을 따른다. `attempts` 하나로 두 종류의 횟수를 합치거나 재시작 때 한도를 새로 부여하지 않는다.

### 실시간 Cue의 생성·제공 기록

GPT-Live의 실시간 Cue 생성, 아동의 도움 동의, 첫 반응 보호, 도움 후 아동 반응 1회, 실제 제공 내용·종류·순서·시각 및 실제 재생 범위의 기록은 기존 기능 정책이다. 2026-10-02 사용자 채택 기본안은 `practice`가 제한된 Cue 요청을 준비하고 `voice`를 통해 GPT-Live가 생성·발화하며 서버가 제공 기록을 대조하는 흐름이다. 요청·실패 처리는 [Cue 계약](protocol.md#cue-contract), 최신성·실제 재생에 따른 진행은 [Cue 상태 처리](session-state.md#cue-lifecycle)가 소유한다. 아래 저장 필드와 물리 구조는 **Proposed**다.

| 논리 정보 | 반드시 구분할 사실 |
| --- | --- |
| 연습 문맥 | 활동·연습 시도·단계·선택한 목표 정의 버전·사용 Scenario. 다른 장면이나 구 활동의 Cue를 현재 반응에 연결하지 않음 |
| 요청·최신성 연관 | 서버 요청 ID·`opId`·현재 연결 ID·재생 연관 ID와 공급자가 실제 제공하는 이벤트/전사 참조. GPT-Live 음성이 Cue별 응답 ID나 완료 이벤트로 자동 분리된다고 가정하지 않음. 대응을 확인할 수 없으면 미확인으로 남기고 실제 키 이름은 프로토콜 계약에 맞춤 |
| 도움 동의 | 요청 전 동의 여부·시각과 허용된 응답/전사 참조. 거부·무응답을 동의로 만들지 않으며 도움 제안만으로 `제공됨` 기록을 만들지 않음 |
| 생성 요청 정보 | 제한된 CueBrief의 버전/참조와 도움 종류. 전체 행동 정의·판정 기준·보호자 원문을 대화 역할로 전달하거나 로그에 복제하지 않음 |
| 생성된 문장 | GPT-Live AI 출력 전사 참조·발화 출처·조립 상태. 아동 발화 및 보호자 입력과 구별. 생성 전사의 완료만으로 실제 제공 완료라고 저장하지 않음 |
| 실제 제공 근거 | 기기의 재생 시작·완료·중단 보고와 시각, 확인 가능한 재생 범위. 생성 전사 구간과 연결할 수 있을 때 그 관계를 기록. 매핑/보고가 불명확하면 `확인 불가`로 남김 |
| 제공 결과·실패 분류 | 요청 전 거부, 명확한 미수락, 수락 여부 불명확, 재생 시작, 완료, 부분 재생/중단, 실패, 재생 여부 확인 불가를 구분. 이를 하나의 성공 Boolean이나 생성 실패로 합치지 않음 |
| 내용 검사·판정 사용 제한 | 부적절 Cue 검사 결과·검출 시각·사유와 영향받은 Cue/아동 반응 참조, 판정 사용 가능 여부를 보존. 정답 노출 등 기준 위반이 확인된 반응은 실제 재생이 완료됐더라도 정상 판정 근거로 집계하지 않음 |
| 시간·재시도 근거 | 최초 요청 시각·전체 기한·수락/재생 근거·추가 요청 횟수·실패 분류. 재전달 여부를 결정할 근거를 남기고 추가 요청 때 전체 기한을 새로 시작하지 않음 |
| 도움 후 반응 | 실제 제공과 이후 아동 반응을 연결하되 첫 반응을 덮어쓰지 않음. 부분 제공/확인 불가일 때 제공 완료와 정상적인 도움 후 반응으로 자동 집계하지 않음 |

**생성된 문장 ≠ 실제 제공한 문장, 요청 ACK ≠ 실제 재생 완료**다. 확인된 기기 재생도 아동이 실제로 들었거나 이해했다는 보증은 아니다. 부분 재생 시 생성 전사 전체를 실제 제공 인용문으로 표시하지 않는다. 정확한 문장 구간을 연결할 수 없으면 확인 가능한 시간 범위·중단 사실과 `확인 불가`를 보존한다. 별도 STT를 새로 도입하거나 원음 저장 정책을 이 기록 모델로 변경하지 않는다.

Cue의 **최초 요청부터 실제 재생 시작까지 전체 5초**(구간 분할·전사 대응·검사·송신 대기 포함), **조건부 추가 재시도 최대 1회**는 2026-10-02 채택한 잠정 기본값이며 미측정이다. 추가 요청은 **일시 오류이고 명확히 미수락이며 재생되지 않은 것이 확인된 경우**에만 남은 전체 기한 안에서 허용한다. 수락/재생 여부가 불명확하면 자동 재요청·재생하지 않는다. 이 횟수는 도움 후 아동 반응 1회·상황 재생성 1회·ResultJob 기술 재시도와 별개다. 종료·취소·단계 변경·현재 동의/자료 사용 허용 검사에 실패한 늦은 응답은 새 출력이나 유효한 Cue 제공으로 반영하지 않는다.

재생 전에 버퍼 게이트가 상태·권한·최신성과 필요한 경량 의미 검사를 수행하며 승인된 동일 음성만 전달한다. 실제 제공 기록은 별도로 정답 문장 제시 금지 등 기능 기준과 판정 사용 가능성을 점검한다. 사후 검사·모델 교정 ACK가 재생 승인이나 게이트 품질 보장을 대신하지 않는다. 동료 AI 명세의 프롬프트·평가 기준 본문은 복제하지 않으며 정확한 파일·버전은 아직 제공되지 않았다. 전사 참조와 필요한 제공 사실을 연결하고 발화 원문을 오류 로그·이벤트 payload에 반복 저장하지 않는다.

검증 시에는 완전 재생, 부분 재생, ACK만 존재, 전사만 완성, 보고 누락, 동의 거부, 구 `opId`의 늦은 생성/보고, 재시도 전 수락 여부 불명확을 각각 확인한다. 현재 문서화는 이 동작의 구현·실측 완료를 뜻하지 않는다.

## 데이터 최소화와 접근

- 서비스는 아동 **원본 음성을 저장하지 않는** 기본 정책을 따른다([ADR-004](../ADR-004-communication-voice.md)). GPT-Live 주 WebSocket에서의 실제 공급자 저장 설정 필드/기본 보존 정책·Java SDK 적용은 TBD다. 없는 API 설정을 확정 구현값으로 쓰지 않고 실제 아동 데이터 사용 전 공급자 처리·보존·동의 조건을 확인한다.
- `SessionEvent.payload`와 결과 작업에 발화 원문을 중복 복제하지 않는다. 필요한 곳은 `Transcript`를 참조한다. 이 원칙은 추후 삭제·보존 정책을 적용할 때 삭제 대상을 명확하게 한다.
- `GuardianChild` 및 리소스 소유 관계를 API 요청마다 서버에서 확인한다. 동의는 인증 정보에 고정하지 않고 중요한 작업에서 현재 상태를 조회한다([ADR-008](../ADR-008-auth-access-control.md)).
