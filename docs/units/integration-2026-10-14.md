## 연결과 병합 처리

- Core V1~V7(36개 표), Realtime V1~V4(16개 표)를 함께 적용한다. 기존 마이그레이션 내용은 변경하지 않았다. 스키마 목록·이력·시작 버전 시험은 합쳐진 실제 SQL에 맞췄으며 기존 제약과 인덱스 검증을 보존했다.
- Core 시간 설정은 U6 result/report와 U7 push를 모두 바인딩한다. 의존성·API·시간 계약·편차 문서와 각 유닛 작업 기록을 모두 보존했다.
- `ActivityRecorded` 커밋 후 U5b 노출 정산과 U6 결과 작업 접수가 각각 실행된다. 두 처리 모두 기존 복구 경로를 유지한다.
- U5b 최종 목표 완료는 기존 종료 사건으로 U7 완료 푸시에 연결된다. 푸시 클릭은 세션 재조회 후 17로 이동하고, U6 결과 폴링으로 27 기록 화면에 연결된다. 기록 도착 전에는 REQUESTED로 계속 조회한다.
- 삭제 순서는 PUSH 60 → RESULT 70 → 활동 기록 90 → 활동 100 → 연습 150을 유지한다.

## 통합 중 보완

- U6 도움 횟수는 U5b `givenAt`이 있는 실제 제공 행만 센다. 거절·무응답·동의했지만 재생되지 않은 행은 기록은 남기되 도움 횟수에 넣지 않는다.
- 첫 동의값은 U5b가 정렬한 기록 순서를 따른다. 제공 시각이 없는 뒤의 행이 앞의 동의값을 덮지 않는다.
- U5b `SKIPPED`의 `TIME_OVER`와 `TIMEOUT`은 U6 시간초과 사유로 유지한다. 반응이 없는 경우 일반 활동 종료로 바뀌지 않도록 시험했다.
- 다음 목표의 첫 상황 준비에서 생산하는 `GENERATION_FAILED`·`VALIDATION_FAILED`·`UNAVAILABLE`도 상황 준비 실패로 유지한다.
- 위 소비 경계 회귀 시험 12사례를 추가했다. 기존 시험 단언과 커버리지 하한은 낮추지 않았다.
- main 병합 후 전체 앱 시험에서 Inbox 처리기 두 개가 연결을 점유한 채 U6의 동기 `AFTER_COMMIT` → `REQUIRES_NEW` 접수를 기다릴 수 있음을 확인했다. 명시적으로 닫는 `CoreWebApp` 시험 문맥만 풀을 3개로 설정해 후속 트랜잭션이 진행할 연결을 확보했다. 캐시되는 부분 문맥의 기본 2개, 운영 10개와 기존 삭제 단언은 유지한다.
- 기록 발행 회귀 시험은 Inbox `PROCESSED`뿐 아니라 해당 세션의 `AFTER_COMMIT` 이벤트 수신을 기다린 뒤, 기존 단일 발행·내용 단언을 수행한다. DB 커밋 가시성과 구독자 실행 완료를 같은 것으로 보지 않는다.
- U1 지표 시험은 수동 `tick`과 실제 주기 작업이 같은 표본 구간을 닫던 경합을 없앴다. 해당 시험에서만 자동 표본 주기를 30일로 두며, 스냅숏 주기 1초·실제 DB·게이지/로그 단언은 유지한다.

## 검증

로컬에서는 합쳐진 Core 설정·버전·출력/도움/미완료 사유 시험, 프런트 전체 시험·정적 검사·빌드를 실행한다. DB·전체 JVM 회귀·이미지·보안·Compose 기기 시뮬레이터 검증은 GitHub CI에서 확인하며 실행 번호와 최종 결과는 통합 PR에 기록한다. 로컬 Docker는 재시작하거나 정리하지 않는다.

Core 연결부 로컬 시험 75건은 통과했다. 프런트 로컬 실행은 969건 통과 뒤 U7 설정 시험용 worker 기동 시간초과 1건으로 실패했고, 같은 코드의 Linux CI는 전체 시험·빌드·U5b/U7 범위 검증을 통과했다. 첫 통합 CI의 기존 로그 시험은 정상 무작위 16진 traceId에 `bad`가 우연히 포함돼 실패했다. 잘못된 공급자 입력의 표식을 16진수에 들어갈 수 없는 `invalid`로 바꿔 유효한 ID 생성과 입력 비노출 단언을 그대로 유지했다.

## 별도 확인

지시서대로 U5b·U6의 실제 AI 공급자는 미연결이다. U7은 VAPID 환경 변수 세 개가 있어야 발송한다. 실제 기기 음성·Android 알림/PDF 저장·생성 내용 품질·운영 부하 검증은 자동 시험 통과로 대체하지 않는다.
