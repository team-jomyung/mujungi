# U5b 연습 연결 설계

## 기준과 상세 설계

이 문서는 U5b 작업에서 확인한 방침을 다른 유닛과 공유하기 위한 설계 요약이다. 상세 정본은 `aidlc/spaces/default/intents/261013-u5b-practice/construction/functional-design/`의 entities.md·rules.md·functional-spec.md·frontend-components.md·traceability.json이다. 근거는 같은 U5b 기록의 requirements.md 및 확인된 기능 설계 Q1~Q6다. 기존 `261008-mujoong-service` 인셉션과 U4b 기록을 읽기 전용으로 재사용한다.

U4b 조회 기준은 원격 브랜치 `unit/u4b-activity-realtime`, 커밋 `ffcfb8a09a523b2cb8fff885b1a9fadaefa27251`이다. 소스 검토를 실제 병합·CI 통과·담당자 합의로 취급하지 않는다.

## 1. Core 시작 준비

보호자·멱등 키에 준비 원본을 선점하고 sessionId·선택 목표·정의 버전·추첨 순서를 한 번 고정한다. 첫 상황은 별도 준비 권한 문맥으로 생성하며 C10의 ACTIVE 검사를 우회하지 않는다. 공통 상황 생성·내용 검증 로직은 재사용한다. 첫 상황 준비가 끝난 뒤에만 기존 REQUESTED 시작 경로에 같은 sessionId로 인계하여 REQUESTED 10초 시한을 유지한다.

첫 상황 내용 생성/재생성 두 번 실패는 422 SCENARIO_GEN_FAILED이며 Realtime 시작을 만들지 않는다. 기술 미연결·권한/동의 실패는 내용 실패와 구분한다. 중복 키는 같은 준비 원본을 사용하고 다른 요청 해시는 거절한다. 외부 호출 동안 계정 쓰기 잠금을 유지하지 않으며 저장 직전 재인가와 선점 세대를 확인한다.

새 준비 문맥 포트/API·영속 준비 저장·Core V7 이후 변경·처리 중 응답/재시도는 **I5/U4a 조정 후보**다. 현재 PracticeStart의 인자만으로 세션 ID가 전달된다고 가정하지 않는다. 준비 15초와 보호자 HTTP 요청 10초의 차이도 함께 합의한다. 통신 시한 초과는 준비 실패 증거가 아니며 같은 키를 보존한다.

FrozenGoal은 Core 준비 소유의 불변 값 객체다. goalSelectionId·이름·행동 정의 키/버전·판정 기준에 더해 서버 sortOrder·선택 내 순위 r·선택 수 N·준비 시 즐겨찾기·배수·가중치를 추첨 입력으로, order를 추첨 결과로 함께 고정한다. 같은 키 재처리에서 어느 필드도 재계산하지 않는다. C8 시작 패키지에는 기존 목표 필드와 judgmentCriteria 및 첫 목표의 firstScenario만 복사한다. Realtime SessionGoal의 judgmentCriteriaSnapshot은 이 기준을 내부 이름으로 저장한다. 순위·가중치 등은 Core에 남기고 C8 필드로 임의 추가하지 않는다. 준비 sessionId는 시작 요청과 SessionGoal에 동일하게 전달한다. 신규 준비 저장과 패키지 작성 포트는 I5/U4a 합의 대상이다.

## 2. 목표 순서

선택 수 N, 선택 목표 중 담은 순 순위 r(1부터)에 대해 가중치는 `(즐겨찾기 2, 일반 1) × (N-r+1)`이다. 남은 목표 가중치에 비례한 비복원 추첨으로 전체 순서를 한 번 저장한다. 같은 키 재시도·재조회·목록 삭제/별 변경으로 재추첨하지 않는다. 고정 시드와 1,000회 표본에서 첫 자리 기대 비율 ±5%p를 검증한다.

## 3. 연습 단계와 판정

참여 수락 뒤 상황 안내→첫 반응→판정→필요한 도움 동의→Cue→도움 후 반응 한 번→새 상황→다음 목표를 따른다. 공개 단계 enum 여섯 개를 유지하고 판정/생성 대기 내부 상태를 API enum에 임의 추가하지 않는다. 첫/새 상황은 Cue·정답·시범을 차단한다. Cue 브리프에는 판정 기준·정답·보호자 원문을 넣지 않는다.

첫 반응 20초, 도움 동의 10초, Cue 요청부터 실제 재생 시작까지 5초를 적용한다. 판정은 호출당 5초·재시도 한 번, 실패는 uncertain이다. 무반응은 평가자 호출 없이 NOT_PERFORMED/NO_RESPONSE다. 최초 기능 설계에서 미확정이었던 첫 무반응 이후 경로는 아래 CG-Q1의 승인된 U5b 로컬 결정으로 보완한다. 상위 메인/U4b Intent의 정책은 변경하지 않는다.

5초·재시도 1회는 U5b 브리프, 메인 계약 practice.judge-budget, 승인된 U5b FR7.6/NFR6에서 대조했다. Q6로 **유효 반응 수락부터 최종 결과의 원자적 커밋 완료까지 전체 12초 이내**를 이번 U5b 기준으로 확인했다. 최초 저장·큐·네트워크 왕복·검증·재시도 예약/간격·최종 DB 저장을 모두 포함한다. 최종화/DB 커밋 예산 R을 먼저 확보하고 C=수락+12초-R 이전까지만 공급자 호출을 허용한다. 각 호출은 min(5초, C까지 남은 시간)이며 재시도를 제한/생략한다. 시간 초과는 C부터 기존 반응을 보존한 채 uncertain을 원자적으로 저장하며, 12초 뒤 저장을 시작하지 않는다.

R은 저장/예약기 타임아웃과 부하 시험으로 검증할 기술 예산이며 임의 운영 기본값을 확정하지 않는다. 저장 장애·예약 지연으로 12초 내 커밋을 못 하면 원본 보존과 I2 실패/위반 관측으로 구분하고 확정 성공을 주장하지 않는다. 중복/재시작은 같은 예산 원본과 시도 횟수를 재사용한다. 실제 공급자·부하 시험 후 근거와 확인을 기록해 예산 버전을 조정할 수 있으나 이미 수락한 반응의 시한을 연장하지 않는다. 상세 WF3과 Clock 시험 표가 시간 경계의 정본이다.

도움 후·새 상황 반응은 실제 해당 재생 완료의 서버 수신 시각부터 각각 20초를 U5b 설계 제안으로 쓴다. U4b SILENCE는 변경하지 않는다. 재생 증거·일시정지·동시 종료 경합의 실제 통합은 합의 대기다.

## 4. 데이터·실노출·정산

Realtime V4의 SessionGoal·PracticeAttempt·PracticeResponse·CueDelivery·Evaluation이 원본을 소유한다. 반응과 도움은 실제 scenarioId에 귀속되고 첫 반응을 덮어쓰지 않는다. 판정 기준/근거/본문은 보호자 응답이나 로그에 노출하지 않는다.

반응 수락과 기회 닫기/PENDING 저장을 하나의 원자적 경계로 수행하고 저장 후에만 판정을 요청한다. 대기 label/closedAt은 null이며 uncertain을 임시값으로 쓰지 않는다. 유효 반응·판정 세대·실행 소유권의 승자만 최종 Evaluation과 동일 반응 label/closedAt/FINALIZED를 함께 원자적으로 저장한다. 중복 전달은 기존 결과를 재사용하며 이전 시도·낡은 세대의 결과는 덮어쓰지 않는다. 최종 커밋 뒤 완료 사건도 한 번만 단계에 반영한다.

종료와 최종 저장은 같은 정산 경계에서 직렬화한다. 종료가 먼저면 확보 반응은 로컬 TERMINATED_PENDING으로 보존하고 판정 세대를 무효화한다. 늦은 결과나 종료를 자동 uncertain/NOT_PERFORMED로 바꾸지 않는다. 이 로컬 상태의 U4b/U6 외부 표현·정산 창·스냅숏 재처리는 I2 합의 대상으로 유지하며 현재 계약 enum에 추가하지 않는다.

발급 ISSUED와 실제 노출을 분리한다. 합의된 실제 재생 증거가 있을 때만 exposedAt을 만들며, ActivityRecorded 뒤 Core reconcileExposures로 멱등 반영한다. 미재생·실패·생략을 EXPOSED로 바꾸지 않는다.

같은 목표의 NEW_SCENARIO 생성 실패·시간 초과는 내부에서 구분하고 기존 ORIGINAL 반응·판정·동의·도움·노출을 보존한다. 가짜 scenarioId나 장면 연결 행은 만들지 않는다. **목표 최종 상태·스냅숏 미실시 표현·후속 전이는 Q3에 따라 미확정**이며 DONE/skipReason 또는 SKIPPED를 임의 채택하지 않는다.

중간 종료는 남은 목표 NOT_REACHED를 정산하고 U4b의 스냅숏 직전에 practiceRecord를 제공한다. 연습 삭제 참가자는 Realtime 순서 150에서 자기 데이터를 지우며 세션 200보다 먼저다. Core 준비 원본 삭제도 I5에 포함한다.

## 5. U4b/U4a/U6 조정 요청

| ID | 조정 사항 | 합의 전 상태 |
|---|---|---|
| I1 | 실제 재생 시작/완료/실패/생략 증거·장면/세대·공급자 음성/내용·길이 한도·최초 자유 출력 차단 | 성공/실패가 구분된 시험 대역; 노출/기회/Cue 운영 통합 보류 |
| I2 | 확장점 예외와 정산 실패 때 연습 원본 보존·재처리·스냅숏 실패, 판정 대기 중 종료의 외부 표현/정산 창 | 자기 기록/대기 반응 보존만 독립 검증; 새 외부 상태를 확정하지 않음 |
| I3 | 후속 반응 시계와 기술 일시정지·SILENCE·동시 종료/반응/만료 관계 | U4b 정책 유지; 20초는 로컬 설계 제안 |
| I4 | 새 상황 생성 실패의 목표 상태·장면 없는 미실시 투영·후속 전이·U6 소비 | 원본 보존/내부 실패만 확정; 외부 표현 보류 |
| I5 | 별도 Core 준비 문맥/저장/API·시한/재시도·활성 원본 조회 어댑터·삭제 | U4a 합의 전 계약 편차 후보; Core 변경은 V7 이후 |

검토한 기존 PracticeSessionExtension의 onActive/onChildUtterance/onExtensionEvent/onSettle/practiceRecord와 출력 능력을 연결 기준으로 사용한다. LAST_GOAL은 기존 U4b 마무리 신호를 사용한다. 상대 실행기나 기록을 임의 수정하지 않는다.

## 6. 화면과 검증

18은 기존 선택/별/삭제·복구를 유지하고 시작만 연결한다. 12는 서버가 확인한 n/N·목표 이름·현재 단계만 표시한다. 상황 본문·진행 판정은 표시하지 않고, 부모 단계/건너뛰기 조작을 추가하지 않는다. 조회 실패를 아이 침묵이나 단계 실패로 바꾸지 않는다.

시험은 독립 부품·계약 대역·실제 통합을 구분한다. 태그 u5b, Realtime 자기 범위 줄 80% 및 기존 회귀/단언을 유지하고 프런트 변경에는 범위 파일을 둔다. U4b V3 병합 뒤 U5b V4를 실제 연결해 스냅숏·삭제·노출·시작/화면을 통합 검증한다. 미합의 AC는 traceability.json에서 Deferred다. 이 문서는 코드/시험 실행 또는 통합 완료 증거가 아니다.

## 7. Code Generation의 CG-Q1 추가 결정

사용자가 채택한 첫 무반응 이후 경로는 `FIRST_RESPONSE`의 실제 기회 시작부터 20초 만료 → `NOT_PERFORMED/NO_RESPONSE` 저장·판정 호출 없음 → `HELP_OFFER` 질문이다. 동의하면 Cue를 한 번 요청하고 실제 재생 시작/완료 증거 뒤 `AFTER_CUE_RESPONSE`를 연다. 거부 또는 도움 동의 10초 무응답이면 Cue 없이 새 상황을 준비한다.

도움 동의 10초는 새로 만든 수치가 아니다. 메인 계약 요약 7절 `practice.help-consent-wait`와 `contracts/timing.md` 2절에 예약된 값이다. 시작점은 질문 요청 시각이 아니라 실제 도움 질문 재생 완료의 서버 수신 시각이다. 중복 완료 사건은 시계를 연장하지 않는다. `DECLINED`와 `NO_RESPONSE`는 별도로 보존한다.

질문 출력 실패·중단·생략을 동의 무응답으로 바꾸지 않는다. 종료 선행 시 추가 질문·Cue·반응 기회를 만들지 않는다. 새 상황 생성 실패는 ORIGINAL 반응·도움을 보존하고 I4 합의 대기에서 멈춘다. 실제 재생 사건·종료 경합 우선순위·후속 20초와 SILENCE 연결은 I1/I3 미합의 상태를 유지한다. Q1~Q6와 기존 답변·감사 기록은 변경하지 않는다.

## 8. 독립 구현과 후속 연결

독립 소스는 U5b 소유 포트만 사용한다. 실제 `PracticeSessionExtension`, Core 준비 저장/API·`PracticeStart` 빈, 실제 `PracticeSessionContextPort`/`ScenarioRecordPort`, 화면 18 시작 활성화는 연결하지 않았다. V4 산출물은 자동 탐색 밖 `db/pending/realtime`에 두고 폐기 DB 시험에만 적용한다.

타입 있는 시간 설정은 자동 로드되지 않는 `practice/u5b-independent.yml`을 명시 바인딩하여 검증한다. 기존 `application.yml`과 설정 소유권 계약은 유지하며 운영 연결 때 별도 합의·등록한다. R은 기본값이 없다. 실제 판정 예약기와 평가자에는 같은 `EvaluationClock`을 주입하여 UTC 역행으로 전체 예산이 연장되지 않게 해야 한다. 저장소/예약기의 운영 상한과 실제 부하는 후속 통합에서 확인한다.

완료 경계는 승인된 코드 생성 계획의 INT-1~INT-5를 따른다. U4b V3 main 병합과 I1~I5 합의·최신 브랜치/CI/기준 커밋 비교 후 같은 Intent의 후속 Code Generation 계획에 별도 Plan Approval이 필요하다. 독립 부품 시험 성공으로 전체 U5b 통합 완료를 선언하지 않는다. 실제 실행 증거는 `report.md`를 참조한다.
