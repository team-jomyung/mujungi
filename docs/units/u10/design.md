# U10 상황 생성 설계

## 정본과 상태

이 문서는 작업 기록 `aidlc/spaces/default/intents/261017-u10-scenario-generation/construction/functional-design/`의 설계를 구현 파일과 연결한다. 업무 데이터는 entities.md, 규칙은 rules.md, 순서·상태 전이는 functional-spec.md, 추적은 traceability.json이 정본이다. 요구사항 승인을 받은 뒤 작성한 설계 초안이며 구현 완료·시험 통과를 뜻하지 않는다.

U15 → U14는 main에 순서대로 병합했고 각각 main CI의 skeleton·ci-gate가 통과했다. U10 브랜치는 main `48a132b8ebe5a276e9a5d26ddbf35353ddf9fac6`에서 이어간다. 배포와 U10 병합은 범위 밖이다.

## 1. 생성 경계와 호출 예산

`ScenarioService`가 기존 선점·세션/준비·권한·최종 저장을 유지한다. 새 구조화 경로는 별도 `ScenarioScriptGenerator`가 소유하고, `core.textai`의 구조화 생성/검토 포트를 통해 `LunaTextAiProvider`를 사용한다. 별도 검토 요청이 없는 구형 json_object 어댑터 메서드는 U9의 기존 직접 호출 계약/시험 호환에만 남긴다. 실제 Luna가 구성된 상황 생성 서비스는 반드시 새 구조화 경로를 선택한다. 구성 경로 시험으로 이를 증명하고 단순 대역 통과를 실제 연결 완료로 표시하지 않는다.

새 포트는 생성 한 번과 검토 한 번의 능력만 제공한다. `CoreLunaClient`에 계약 스키마를 적용하면서 안쪽 재시도를 하지 않는 명시적 호출 모드를 추가한다. 기존 CONTRACT/LEGACY_JSON_OBJECT의 동작과 `LunaCallBudget`의 다른 유닛 최대3회 제한은 바꾸지 않는다. U10의 바깥 생성 흐름만 기술 재시도1·내용 수정1·필요한 BASE-only 검토1을 관리한다. 기존 `TextAiGateway` 기술 재시도 루프를 새 흐름의 바깥에 겹치지 않는다.

전체 15초, 그래프 합계2초, 각 호출의 기존 목적 시한·backoff를 유지한다. 준비 흐름이 고정한 최초 lease 마감을 생성에 전달해 새 마감으로 연장하지 않는다. 단조시계와 UTC 잔여의 작은 값을 외부 작업/통신에 적용하며, 전체 Future와 통신 Future를 취소하고 저장 직전도 정각 만료를 확인한다. 최대 호출수6은 수행 보장이 아니며 예산이 없으면 호출하지 않고 실패한다.

## 2. 목표 준비와 호환 식별자

`SavedGoalReader`가 목표 내용의 권위 경계다. LEGACY_BEHAVIOR에는 실제 행동 키/버전을 유지하고 기존 `PragmaticsKnowledge` 정의를 고정한다. CANDIDATE에는 담은 버전의 4요소·표현·skillRef를 쓰고 카탈로그 조회를 하지 않는다.

`PracticeStartService`, `FrozenGoal`, `WeightedGoalOrder`, `PracticeSessionContextPort.GoalSnapshot`에 종류별 고정 맥락을 선택 확장한다. 과거 JSON/생성자를 읽는 기본값은 LEGACY_BEHAVIOR다. 후보의 표시 이름·즐겨찾기·저장 순서는 PracticeGoal 소유 경계에서 얻는다. 새 조회가 필요하면 U14 저장 책임 내부에 읽기 경계를 추가하고 U10이 상대 소유 테이블에 직접 SQL을 흩뿌리지 않는다.

기존 C8/실시간 저장은 `behaviorKey`·양수 `behaviorVersion`을 기술 식별 필드로 요구하지만 실제 행동 정의를 다시 읽지는 않는다. 후보에는 `candidate:<candidateRef>`와 후보 버전을 호환 운반 식별자로 사용하고, 선택 확장 `goalKind=CANDIDATE`, `candidateRef`, `candidateVersion`, `goalContext`를 함께 보낸다. 기존 행동 키의 값·의미는 바꾸지 않는다. 후보의 운반 키를 승인된 행동 카탈로그 키라고 주장하거나 새 행동 정의 행을 만들지 않는다. 이 신규 종류의 이름 공간 확장은 `(U10-a)`에 명시한다. 생성·판정·결과에서 목표 내용의 정본은 선택 ID와 고정 goalContext다. 후보 버전은 이 식별자에서 추측하지 않는다.

기존 실시간 경로는 운반 필드와 판정 기준 문자열을 그대로 저장해 기존 시작 형식을 읽을 수 있다. 새 U12 소비자는 typed 확장을 사용할 수 있다. U10은 실시간 운영 코드를 바꾸지 않으며 Core의 C8 직렬화와 현재 수신 타입의 대조 시험으로 호환을 확인한다. 현재 수신기가 추가 필드를 거절하거나 후보 키를 카탈로그 조회에 사용한다는 사실이 구현 검증에서 나오면 임의 우회하지 않고 계약 편차로 보고한다.

후보 판정 기준은 서버가 고정한 4요소에서 만들며 모델 응답·레거시 임의 행동 기준으로 대체하지 않는다. 기존 순서 결정의 무작위성·즐겨찾기 가중치·멱등 재사용을 유지한다. 서로 다른 목표 종류의 저장 순위가 같으면 선택 ID를 안정적 동률 기준으로 삼아 준비 원본을 고정한다.

## 3. V10과 저장·삭제

`V10__u10_scenario_generation.sql`은 `core_scenario`에 선택 컬럼 `script_version`, `scenes_json`, `self_review_json`, `generation_json`, `goal_context_json`만 더한다. 기존 컬럼·제약·V1~V9는 바꾸지 않는다. 기존 행은 null이고 기존 앱의 INSERT는 새 컬럼 없이 계속 동작한다. 새 제약을 기존 표에 더하지 않으므로 미리 승인 문장을 만들어 넣지 않는다.

기존 `behavior_key`·`behavior_version`은 LEGACY_BEHAVIOR의 실제 키/버전 또는 위 후보 호환 운반 식별자/버전을 저장한다. FK로 행동 정의에 묶인 칼럼이 아니므로 후보를 거짓 카탈로그 행으로 만들 필요가 없다. 권한·고정 내용 판정은 새 goal_context_json을 함께 비교한다. 기존 요청 테이블의 결과 ID·상태·lease 구조는 유지한다.

`ScenarioRepository`는 새 선택 필드를 왕복하고 첫 BASE에서 기존 필드를 생성한다. 같은 아이의 지문 검사·최종 저장은 기존 보호자 잠금과 유일성 제약을 유지한다. 요청 READY와 저장은 원자적이다. 기존 연습 삭제 참가자가 시나리오 행을 삭제하면 확장 값도 함께 삭제되므로 새 별도 개인정보 표·삭제 순서는 없다. 준비 원본은 기존 goals_json에 고정 맥락을 보존하며 새 독립 AI 원문 저장소는 만들지 않는다.

구버전 쓰기·기존 행동 목표 읽기는 유지한다. 신규 후보의 운반 키를 모르는 과거 앱으로 롤백하면 신규 후보 생성은 실패할 수 있다. 이를 구버전 신규 기능 지원으로 과장하지 않는다. V9 fixture 보존, 구버전 INSERT, 새 필드 왕복, 준비 JSON의 과거 모양, 삭제·권한 경쟁을 시험한다.

## 4. 응답·스키마·프롬프트

`practice-scenario.schema.json`은 기존 8필수 필드와 additionalProperties=true를 유지한다. 선택 `scriptVersion`, `scenes`, `selfReview`, `generation`을 더한다. 첫 BASE의 설명·기회 문장이 기존 scenarioText/triggerScript의 원본이고, 기존 기회 조건과 관계는 고정 목표 맥락에서 서버가 만든다. 가상 장면 고지도 기존 정책을 유지한다. 레거시 partnerRoleText는 서버의 고정 지시다. 장면 partnerRole은 지시가 아니라 서버가 장면 relation에서 만든 짧은 역할 이름(20자 이하, 대체값 친구)이고, 금지 규칙은 realtime 고정 지시가 맡는다(contracts/ai-io.md 10.15, 편차 U12-b).

기존 생성 스키마는 장면 필드를 유지하며 구조 보존의 비발화용 선택 필드만 확장한다. `focusPoints`·`expressionExamples` 누락은 빈 배열로 정규화하고 모든 실제 발화 영역에 기존 크기·금지 검사와 역할별 정답 규칙을 적용한다. 새 대본은 첫 BASE·정확히 한 BASE·유일한 sceneKey를 서버가 검사한다.

검토 스키마의 사유 목록과 APPROVE/reasons=[] 조건은 functional-spec W6을 따른다. `OTHER_APPROVED_REASON`은 닫힌 최종 코드로 대체한다. 실제 공급자 응답 스키마와 판별 코드가 같은 계약 파일을 사용한다. 생성 프롬프트는 scenario-generation.v2, 검토는 scenario-review.v1, 대본은 scenario-script.v1이다(설계 때 판). 지금 판은 생성 `scenario-generation.v5` · 검토 `scenario-review.v3`이고, 판마다 더한 규칙과 계속 받는 옛 판은 `contracts/ai-io.md` 10.11 · `contracts/deviations.md` (U10-b)와 `docs/practice-live-fixes.md`에 있다. 생성과 검토에는 시스템 지시와 데이터를 분리하고 생성 응답 속 명령·승인 문장을 지시로 취급하지 않는다.

`PreparedPracticePackageMapper`는 새 선택 필드를 포함해 첫 대본을 전달한다. `ScenarioInternalController`와 저장 재조회도 같은 모델을 쓴다. 결과 원문·검토 사유 원문·공급자 요청을 응답에 넣지 않는다. 공개 selfReview에는 APPROVE와 검토 모델/판 등 허용 출처만 포함한다. 기존 `internal-practice-scenario-request`의 4필드 요청은 변경하지 않는다.

## 5. 그래프와 변형

아동별 U15 `ChildKnowledgeService`를 사용하고 공개 키 포트 `KnowledgeGraphLookup`을 잘못 연결하지 않는다. `skillContext`와 `variantPlan` 전체를 같은 2초 창에서 실행한다. 후자가 맥락을 다시 조회하는 현재 구현을 그대로 두더라도 바깥 합계 시한이 초과 결과를 버린다. U15의 기존 한도·시험은 바꾸지 않는다.

기본 맥락을 계획기가 지원하는 허용 값으로 구조화할 수 없으면 변형 계획 없음으로 둔다. 지원하지 않는 자유문을 임의의 관계·상황으로 단정하지 않는다. 실제 노출 이력만 사용하며 아직 재생하지 않은 발급을 노출 횟수에 세지 않는다. 일치 맥락·계획이 없으면 graphContextUsed=false를 명시한다.

서버는 실제 장면의 구조 필드를 고정한 불변·기술·허용 거리·변경 축과 대조한다. 이 검사는 모델의 보존 성공 플래그를 신뢰하지 않는다. 별도 검토 요청은 실제 서술의 의미·정답 선제 제시·나이·반복까지 검사한다. 자동 대역은 요청 전달·거절·구조 대조를 확인하며 실제 모델 품질의 증거가 아니다.

변형 실패 시 내용 슬롯이 남으면 한 번 보정하고 다시 검토한다. 그래도 실패하면 BASE-only 대본을 따로 검토해 승인받은 뒤 발급한다. 그 검토도 최초15초 안에서만 수행한다. 늦은 응답·반려·불명확을 승인으로 바꿔 BASE를 강제로 발급하지 않는다.

## 6. 관심사·개인정보

사용자 Q1-A: `정리된 관심사 전달 허용 (추천)`. 전역 금지 집합에서 interests를 무조건 지우는 정책으로 바꾸지 않는다. 목적을 전달받은 정리 경로에서 상황 생성/검토의 최상위 관심사만 허용하고, 기존 일반 정리 API·다른 목적의 테스트와 금지는 유지한다. 이름 별칭·연락처 마스킹·길이/목록 제한을 적용하고 비정상 자유문은 제외한다. 별칭은 Core 내부에서만 얻고 실제 이름을 로그·응답에 남기지 않는다.

나이는 기존 6~12 범위를 유지한다. 생성·검토에 모두 전달해 AGE_MISMATCH를 검토하고, 이전 상황은 필요한 최소 정보만 주어 REPETITION을 검토한다. ID·판정 전용 기준·보호자 원문을 전달하지 않는다. 제브 호출은 없다. 목적별 허용 입력·원문 없는 실패 로그를 음성/결과/씨앗 등 다른 경로와 구분해 시험한다.

### R-01 이름 별칭의 내부 소유 경계

`PracticeAccountPort.AccountContext`에는 이름이 없으므로 여기서 빈 별칭 표를 만들어 통과시키지 않는다. 별도 내부 `ScenarioPrivacyContextPort`의 운영 어댑터가 기존 계정·동의·아이 확인 뒤 `ChildProfileService.find(guardianId)`로 프로필을 읽고 요청의 childId와 일치하는지 확인한다. 해당 소유 서비스가 제공한 displayName을 `아이`로 치환하는 표를 생성·검토 양쪽의 `CoreLunaRequest.aliases`에 전달한다. 프로필·소유 관계·유효 이름을 얻지 못하면 공급자 호출 전에 실패하며, 조회 실패를 빈 표로 바꾸지 않는다. 조회도 최초 요청 마감에 포함한다.

별칭 원본은 Core 내부 일시 값으로만 보유한다. 공개 DTO·AI 입력 Map·목표 스냅샷·DB·오류 메시지·기본 toString에 넣지 않고, 값 객체의 출력은 가린다. 목표·관심사·지정 원본·실제 노출 이력·검토할 생성물의 모든 문자열에 같은 별칭/연락처 정리를 적용한다. 최종 생성물에 알려진 원래 이름이 남으면 내용 실패로 처리한다. 다른 사람의 알려지지 않은 이름까지 자동 식별한다고 주장하지 않는다. 알려진 이름이 각 입력 영역에 들어간 대조 시험, 생성과 검토에서 원본 이름이 전송되지 않는 시험, 소유자/아이 불일치·프로필 실패 시 공급자 호출 0회·비로그 시험을 추가한다.

### R-02 실제 노출 이력의 비교 경계

`ScenarioRepository.recentExposed`를 새 내부 읽기 경계로 둔다. 권한·동의를 확인한 guardianId와 childId 모두로 제한하고, `status=EXPOSED`, exposed_at이 존재하며 최초 요청 시작 시각 이하인 행만 선택한다. 목표·세션 종류와 무관하게 같은 아이의 최근 실제 노출 3건을 exposed_at 내림차순, id 내림차순으로 고정한다. ORIGINAL과 NEW_SCENARIO 모두 이 경로를 사용한다. `seen`의 지문 검사와 별개이며 ISSUED·다른 아이 자료는 포함하지 않는다.

비교 입력은 각 행의 기존 scenario_text와 trigger_script 전체만 투영한다. 각각 8,000자·2,000자, 합계 최대 30,000자로 제한하며 ID·노출 시각·보호자 식별자는 공급자에 보내지 않는다. 상한을 넘는 과거 자료는 조용히 잘라 완전한 비교라고 주장하지 않고 해당 요청을 미발급으로 실패시킨다. 실제 0건은 정상 빈 배열이지만 조회 오류·취소·시간 초과는 빈 이력으로 대체하지 않는다. 최근 3건 밖의 모든 과거 의미 반복까지 검사한다고 주장하지 않는다.

선점 뒤 외부 호출 전, 보호자 잠금을 놓은 읽기 전용 구간에서 조회한다. 조회 한도는 최초 15초 잔여와 500ms 중 작은 값이며 전용 읽기 트랜잭션의 DB statement timeout과 바깥 취소를 함께 적용한다. 공용 JDBC 객체의 timeout 설정을 요청마다 바꾸지 않는다. 읽고 정리한 동일 이력을 생성·최초 검토·보정 검토·BASE-only 검토에 사용한다. NEW_SCENARIO의 지정 ORIGINAL은 별도 `sourceScenario`로 권한·버전을 검증하며 아직 ISSUED라면 실제 노출 횟수나 recentExposed에 넣지 않는다. 이력 조회가 노출을 새로 기록하지 않는다.

시험은 과거 세션 EXPOSED 자료가 ORIGINAL/NEW 양쪽 생성·검토에 전달되는지, 다른 아이/ISSUED 제외, 같은 시각의 안정적 순서와 최근 3건 상한, 빈 값/DB 실패의 구별, 문자열 상한, 이름 치환, 전체 마감 차감·취소, 지정 원본과 실제 노출의 분리를 확인한다. 실제 모델의 의미 판별 품질은 자동 대역의 입력 전달 시험과 구분한다.

## 7. 오류·검증·구현 순서

기존 UNAVAILABLE/TIMEOUT 대역 경로의 SERVICE_NOT_READY 단언은 그대로 둔다. 실제 구조화 생성의 반려/검사/마감 최종 실패는 SCENARIO_GEN_FAILED다. 새 코드나 상세 공급자 메시지를 사용자에게 내지 않는다. 미연결을 승인 대본으로 대체하지 않는다.

1. V10·선택 필드·판·편차 U10-a·계약 왕복을 구현하고 PG 호환 시험을 수행한다.
2. 단일 계약 호출 포트와 생성→별도 검토→독립 검사→재생성을 구현하고 실패별 발급0·15초·취소를 검증한다.
3. 담은 목표·관심사·그래프 합계2초·변형 보존을 연결하고 목표 종류별/개인정보/장애 대조를 수행한다.
4. 준비→첫 대본→내부 HTTP의 기존 필수 필드와 신규 확장 전달을 연결하고 U5b 회귀를 수행한다.

각 단계 구현 후 해당 층 시험을 작성·실행하는 test-after 순서다. 태그 u10과 backend/coverage-scope/u10.txt의 줄80% 이상을 확인한다. 기존 단언·계약 대조·ArchUnit·범위 하한은 바꾸지 않는다. 최종 전체 verify.sh는 별도 검증 스택에서 가짜 공급자로 수행하고 push·PR·GitHub CI를 확인한다. 실제 API 합성 측정은 RUNBOOK 단계4/R-F15 준비 확인 뒤에만 따로 진행한다. 아직 실제 측정 성공·실기기 검증을 주장하지 않는다.

## Alternatives and consequences

공용 LunaCallBudget 한도 확장은 U15 의미까지 바꾸므로 제외했다. 호출별 재시도 중첩은 전체 마감 보장이 약해 제외했다. U10만의 예산 소유권과 단일 계약 호출을 선택했다.

후보를 기존 행동 카탈로그 키로 임의 매핑하는 방안은 목표 내용을 바꾸므로 제외했다. typed 목표 맥락과 명시적 신규 종류의 운반 식별자를 선택하고 기존 키는 그대로 유지한다. 이 변화는 계약 편차와 수신 대조에 드러내며, 기존 앱이 신규 후보를 지원한다고 주장하지 않는다.

15초 안에서 모든 보정 호출이 성공할 확률은 구현만으로 보장하지 않는다. 실제 합성 측정에서 초과·실패가 많으면 예산을 늘리지 않고 사전 생성·캐시의 권한/버전/중복/삭제 위험을 별도 대안으로 보고한다.
