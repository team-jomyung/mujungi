# 사전 표현 연습 기록과 결과 해석

2026-10-28 · 사전 표현 연습과 상황극을 분리하는 흐름의 기록 계약.

## 기록 의미

| 사실 | 언제 확정하는가 | 뜻하지 않는 것 |
|---|---|---|
| `PREPRACTICE_PROVIDED` | 사전 안내·예시의 재생이 완료된 뒤 | 아이가 이해했다거나 목표 표현을 사용했다는 뜻이 아님 |
| `PREPRACTICE_ATTEMPTED` | 사전 연습에서 목표 표현을 실제로 시도했고 FULL·COPIED·PARTIAL 등으로 확인된 뒤 | 안내 수용만 한 말·침묵·판독 불가를 시도로 세지 않음. 동의가 목표인 맥락의 짧은 동의는 인정함. 상황극 성공이 아님 |

상황극 도입 재생이 끝나 실제 장면 행이 생길 때까지는 준비 기록을 세션 메모리에 보관한다. 같은 목표의 BASE와 VARIANT에 준비 조건을 붙이며 장면이 시작되지 않으면 상황극 결과를 만들지 않는다. 프로세스가 그 전에 종료되면 준비 기록만을 별도로 복구하지 않는다.

`IMMEDIATE`는 **그 장면 안에서 추가 도움 없이 첫 반응으로 표현한 것**이다. 사전 연습을 받은 장면의 IMMEDIATE를 평소 독립 능력·연습 전 기초 수행·장기 향상으로 해석하지 않는다. `AFTER_REASK`와 `AFTER_HELP`도 장면 안 조건이다. 사전 연습만으로 도움 횟수·AFTER_HELP·아이의 도움 요청을 만들어 내지 않는다.

부모 결과와 보고서에는 `사전 연습 후 · 바로 전달`처럼 조건을 붙인다. 관리자 도움 표의 `NOT_OFFERED`는 장면 안에서 코칭을 제안하지 않았다는 뜻이고, 준비 교육까지 없었다는 뜻이 아니다. 관리자 사유에도 사전 연습 후 수행이라는 조건을 표시한다.

## 저장·계약

`practice-record-v2.schema.json`의 `facts`에 두 코드를 추가한다. 봉투와 `flowVersion=practice-conversation-v1`, 기존 timing·chip 코드는 유지한다. Core는 새 사실을 파싱·재판정·보고서·다음 연습의 지원 이력에 보존한다.

장면의 선택 필드 `endedAt`를 추가한다. 준비 사실이 있는 새 세션은 서버에서 각 장면의 `startedAt`~`endedAt` 안에 완전히 포함된 발화만 재판정과 결과 문장·목표 후보 생성 입력에 전달한다. 준비·중간 안내·마무리 발화와 시각 미확인·역전·0길이·경계 걸침·중첩 장면 발화는 제외한다. 원본 전사 저장과 대화 기록 화면은 바꾸지 않는다. 준비 사실 없는 옛 기록은 기존 입력을 유지한다.

새 장면의 종료시각이 없으면 그 장면에 대한 입력 근거는 비게 된다. 기존 결과 생성은 시작된 장면이 있으면 호출할 수 있으므로, 근거 없는 장면은 `uncertain`으로 판단하도록 명시한다. 실제 생성 모델의 판단 보류 준수 여부는 별도의 합성/실서비스 검증 대상이다.

Realtime DB는 새 `V10__practice_preparation.sql`에서 `realtime_practice_preparation` 표만 추가한다. `scene_run_id`와 최초 확정된 `provided_at`·`attempted_at`만 저장하고 원문·프롬프트·대본·판정 입력은 저장하지 않는다. 같은 사실 재기록은 최초 시각을 유지한다.

기존 V7 `realtime_practice_scene_run.facts` 허용 목록을 바꾸지 않는다. 새 사실은 별도 표에 쓰고 저장소·복구·관리자 조회에서 기존 facts 앞에 합친다. 기존 앱이 모르는 enum을 기존 배열에 쓰지 않아 구 Realtime의 DB 읽기·쓰기가 유지된다. 장면을 지우면 준비 행도 같은 트랜잭션에서 CASCADE로 삭제되며 다른 보호자의 기록은 유지된다.

## 배포·호환성

1. V10을 적용한다. 기존 데이터·제약·Flyway V1~V9는 변경하지 않는다.
2. 새 facts를 이해하는 Core reader와 계약 검증기를 먼저 배포한다.
3. 새 Realtime writer를 배포한다.

V10은 기존 표 제약을 변경하지 않아 `infra/migration-approvals.txt`의 예외 승인을 추가하지 않는다. 기존 앱으로 Realtime만 되돌려도 새 표 때문에 DB 읽기가 깨지지는 않으나, 구 앱이 복구한 결과에는 준비 조건이 누락될 수 있다. 이미 새 사실을 쓴 활동을 구 reader로 재처리하거나 구 Core로 되돌리는 것은 결과 해석상 안전하지 않다. 필요한 경우 새 사실을 보존하는 reader를 유지한 채 기능만 비활성화한다.

## 검증 범위

- Fake AI: parser·재판정 요청·부모 문구·관리자 도움 의미·다음 연습 지원 이력의 구분.
- PostgreSQL: 새 표 권한/제약, 기존 facts 제약 유지, 저장·복구·관리자 조회, 멱등 시각, 보호자 삭제.
- 계약: 새 두 facts와 기존 사실이 동일 이벤트 형식에서 검증되는지 확인.
- 실제 음성·실제 AI·아동 대상 효과는 이 코드 변경의 자동 테스트에 포함하지 않는다.
